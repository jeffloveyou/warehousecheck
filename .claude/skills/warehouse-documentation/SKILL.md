# 開發手冊與文件同步

> 文件缺漏代表功能交付未完成。手冊是長期技術參考文件，**不放練習題或課後作業**。

## 必須同步的文件對照
| 發生的變更 | 必須更新 |
|---|---|
| 任何程式變更 | `docs/04-開發手冊.md` 對應章節、`docs/07-開發日誌.md` |
| 新增／修改測試或取得驗證結果 | `docs/05-驗收測試.md`（測試案例與執行證據） |
| 設計決策、技術選型、例外規則（如允許負庫存） | `docs/adr/NNNN-標題.md` 新增或更新 |
| 部署、發布、服務、NAS／PC 配置 | `docs/10-低負載與跨平台部署.md`、`docs/04` §10/§11 |
| 線上更新、回滾、健康檢查、Migration 流程 | `docs/11-線上更新與回滾.md`、`docs/04` §12 |
| 任務完成狀態 | `docs/09-任務清單.md` 勾選對應項目 |
| 未決事項被決定 | `docs/08-待決事項.md` 移除或標記結果 |
| 新增文件或 Skill | `README.md` 索引 |

## 撰寫規則
1. **只更新受影響的章節**，不重寫未變更內容。
2. **不在多份文件重複記錄同一技術細節**；詳細說明集中於對應專業文件，其他地方用連結或路徑指向。
3. **不寫未驗證的成果**：沒有使用者提供的實際輸出，就寫「待驗證」。不可預先填寫虛假已完成項目。
4. 繁體中文為主；程式識別字、檔案路徑、指令維持原文並放在 code span。
5. 手冊必須寫**實際檔案路徑與類別／方法名稱**，不能只寫抽象範例；API 或 schema 改動時同步更新路徑與指令。
6. 開發日誌使用簡潔格式，詳細原理放手冊。
7. 不可為了節省 Token 省略必要技術說明。

## `docs/04-開發手冊.md` 每章固定格式（§7）
1. 功能要解決的問題（現場語言）
2. 整體流程圖（資料從哪裡進、去哪裡）
3. 實際檔案路徑與類別
4. 重要程式碼逐段解說（邏輯、取捨、陷阱）
5. 資料庫表、約束及 Migration
6. 如何本機重現／操作（PowerShell 指令及預期結果）
7. 自動測試／人工驗收
8. 常見故障、錯誤訊息、查找步驟
9. 常見修改需求與操作說明（不提供練習題）
10. 本章關聯 Git commit、ADR、版本資訊

標題標出對應版本或 commit。

## `docs/07-開發日誌.md` 條目格式
依檔案內「日誌模板」：日期、任務 ID／標題、問題與需求、事前方案與使用者批准、修改檔案、程式執行原理、PowerShell 驗證指令、結果（不得推測）、已新增測試、已更新手冊、風險與未解事項、Git commit。新條目放在既有條目之後、`---` 模板分隔線之前。

## ADR 格式建議
檔名 `docs/adr/NNNN-簡短標題.md`（流水號延續既有 0001、0002）。內容：狀態（提案／已接受／已取代）、背景、決策、替代方案、後果與風險、驗證方式、日期。

## 功能交接卡
大型功能完成時，依 `templates/feature-handoff.md` 欄位整理，可附在開發日誌或手冊章節中，不另建重複文件。

## 交付前自我檢查
- [ ] 手冊中的路徑、類別、指令與實際程式一致。
- [ ] 日誌的「結果」欄只有真實結果或「待驗證」。
- [ ] 沒有在兩份文件寫重複的詳細規格。
- [ ] 沒有練習題、作業或強制獨立實作要求。
- [ ] 每個里程碑結束時，核對手冊指令與故障排查步驟是否仍正確。
