# 舊電腦低負載與效能調校

> 驗收對象是**公司既有低規格電腦**，不是開發機。效能數字以 M0 實測後核准的門檻為準，`docs/10` 中的數值只是擬議基線。

## 先讀文件（按需）
- `docs/10-低負載與跨平台部署.md`：§2 前端比較、§3 實作原則、§4 測試基線與記錄欄位。
- `docs/05-驗收測試.md`：`T-PERF-*` 測試。
- `docs/04-開發手冊.md`：§9 效能調校與排查。

## 硬性原則
1. 庫存正確性優先於效能；快取只能輔助查詢，不能判定庫存是否足夠。
2. 搜尋、篩選、排序、分頁在**伺服器**處理；API 強制最大 page size；不下載完整物料清單到瀏覽器。
3. 禁止：無限制查詢、無意義高頻輪詢、不必要的大型前端框架／動畫、常駐相機掃描器。
4. 相機掃碼程式只在需要時載入、離開時釋放攝影機；鍵盤模擬掃碼（HID／PDA）**不得**載入相機程式。
5. 圖片使用縮圖、適當格式、延遲載入。
6. 前端方案尚未定案：不預設 Blazor WebAssembly；Blazor Interactive Server 需評估長連線與更新影響。
7. 新增功能須評估：瀏覽器資源、API 反應時間、DB 查詢成本、傳輸量；必要時附修改前後數據。

## 後端檢查清單
- [ ] 唯讀查詢使用 DTO 投影（`Select`）＋ `AsNoTracking()`，不序列化整個 Entity graph。
- [ ] 沒有 N+1（迴圈內查 DB、延遲載入導覽屬性）；避免過多 JOIN。
- [ ] 常用條件有對應索引（ItemCode、NormalizedText、外鍵、狀態欄位）；用 `EXPLAIN (ANALYZE, BUFFERS)` 驗證並考量實際資料分布（正式 DB 上執行前注意成本）。
- [ ] 分頁有上限；大量匯出走背景／串流下載，不同步塞進 UI。
- [ ] 快取有失效策略，畫面顯示快取時標示時間與重新取得方式。
- [ ] 日誌可看出 API 處理時間與 RequestId。

## 前端檢查清單
- [ ] 搜尋框 debounce 或按 Enter 送出。
- [ ] 靜態資源有版本標記與快取；JS/CSS 精簡。
- [ ] 閒置時無持續 CPU 消耗；長時間使用無記憶體累積（事件監聽、計時器有釋放）。
- [ ] 不在每次按鍵或每秒觸發 API。
- [ ] 相機模組動態載入（例如僅在按下「相機掃碼」時 import）。

## 量測與紀錄
每次效能測試記錄（欄位來自 `docs/10` §4）：
硬體與 OS、瀏覽器版本、網路品質、同時使用者數、物料資料量、總傳輸量、CPU、RAM、p50/p95 延遲、成功率、查詢計畫、測試人、日期。

- 修改前後使用相同資料量與環境比較，不憑主觀感覺判斷。
- 測量工具：瀏覽器 DevTools（Network、Performance、Memory）、API 日誌耗時、EF Core SQL 日誌、PostgreSQL `EXPLAIN`。
- 由使用者執行並提供結果；未取得數據前標記「待驗證」，不得宣稱已達門檻。

## 交付時需說明
- 本次修改對傳輸量、查詢次數、索引、前端資源的影響。
- 需要新增的效能測試或更新的 `T-PERF-*` 案例。
- 結果寫入 `docs/05-驗收測試.md` 執行證據與 `docs/07-開發日誌.md`；排查方法更新 `docs/04` §9。

## 常見陷阱
- 為了「前端即時篩選」把全部料號載到瀏覽器。
- 用 `ToList()` 後再在記憶體裡 `Where`／`OrderBy`／`Skip`。
- 在開發機測很快就宣稱舊電腦可用。
- 為了效能把可用量檢查移到快取，破壞庫存正確性。
