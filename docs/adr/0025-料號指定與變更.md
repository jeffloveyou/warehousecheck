# ADR-0025：核准時指定料號、核准後變更料號、歷史料號（D-32）

- 狀態：已接受（Accepted），使用者 2026-10-27 核准
- 相關：AGENTS.md 第六節、ADR-0003 D-01、ADR-0011 決策 2／5（本 ADR 修訂）、ADR-0016、ADR-0023 決策 4、`docs/04` §3.12

## 背景
使用者 2026-10-27 提出：料號產生時可以先是流水號，物料管理員核准時要能依需求修改；核准後也要能修改，方便日後對齊分類。

原本的規則是：料號只在核准時由系統依分類前綴發放，發放後不可變更（ADR-0011 決策 2、5，`trg_items_protect_item_code`）。這個需求要放寬這條規則，所以寫成本 ADR。

使用者同時決定：
- 格式維持「前綴（2～4 碼英數）-至少 6 位數字」，前綴與號碼都可以自己選。
- 核准後分類仍然不可改（ADR-0023 決策 4 不變）。
- 核准後改料號要由系統管理員先開設定。
- 舊料號的處理方式在每次變更時選擇，選「釋出」要再確認一次。

## 決策
1. **核准時指定**：
   - 核准表單新增「正式料號（空白＝自動流水號）」欄位，API 的 `ApproveItemRequest.ItemCode` 也可以帶入。
   - 輸入會先去空白、轉大寫，再檢查格式。
   - 前綴必須是物料分類**往上整條路徑**上任何一個分類的前綴。所以子分類日後設了自己的前綴，就可以改成子分類的前綴。
   - 號碼不能被其他物料使用，也不能是其他物料保留中的歷史料號。
   - 自動核准（表單、匯入）一律自動發號。
2. **自動發號會跳過已占用的號碼**：
   - 計數器遇到被手動指定、或保留為歷史的號碼時，會往下跳。
   - 跳過的號碼不回收，所以料號可能出現空號；原本「沒有空號」的保證只限於自動發號的連續區段。
3. **核准後變更**（`ItemWorkflowService.ChangeItemCodeAsync`）的條件：
   - 物料管理員。
   - 系統設定 `items.allow_item_code_change` 開啟（預設關閉，變更設定會留下 `setting.update` 紀錄）。
   - 必須填寫原因，上限 200 字。
   - 前綴與占用規則同決策 1。
   - 單據、異動、結存、預留都以 `ItemId` 關聯，所以不受影響，歷史畫面會直接顯示新料號。
   - 審核紀錄新增動作 `CodeChange`，`item_code` 欄記新料號，意見記「舊 → 新；保留／釋出；原因」。
4. **歷史料號**（新表 `item_code_history`，只能新增）：
   - **保留**（預設）：舊號仍可以用搜尋（命中原因「舊料號」）、掃碼（`ScanMatch.OldItemCode`，`WH:ITEM:<舊號>` 舊標籤也可以）、單據與期初的料號欄、索引匯入（會加警告）找到同一個物料。舊號不會給其他物料使用，等於延續 ADR-0011「料號不重新分配」。物料自己可以改回自己保留的舊號。
   - **釋出**：要在確認欄再輸入一次舊料號。釋出後就查不到，其他物料可以使用。
   - 同一號碼可能有多筆紀錄（例如釋出後被其他物料使用、之後又被改掉），一律以**最新一筆**判斷是否保留。
5. **併發與防線**：
   - 自動發號、核准時指定、變更料號都會先取分類樹的共享鎖，再取**一個**「料號前綴」的 advisory lock（`AdvisoryLocks.LockItemCodePrefixesAsync`，鍵 `item-code-prefix:<前綴>`），然後才檢查占用。同前綴的發號與指定因此會排隊。
   - 變更料號只鎖新號的前綴，不鎖舊號的前綴。原因是匯入自動核准會在同一個交易裡逐列取前綴鎖，同時鎖兩個前綴可能和它死結（審查 🟠-1）。舊號提交前仍是本物料的料號，提交後變成歷史料號，別人的占用檢查一直看得到它，所以不需要另外鎖。
   - 同一號碼的「最新一筆」以 `item_code_history.seq`（identity）判斷，不用時間，避免時間相同時判斷不一致。
   - 手動指定時，號碼超過 6 位就不可以 0 開頭（例如不能指定 `ME-0000123`），避免和自動發出的 `ME-000123` 同時存在、容易看錯。
   - 輸入會先經過 NFKC（全形轉半形），與搜尋、掃碼相同。
   - 資料庫 trigger `items_protect_item_code` 改寫為：
     - 料號仍不可清除；有料號的物料仍不可刪除。
     - 只有交易內設定了 `warehouse.item_code_change = <物料 ID>`（`set_config(..., true)`）時才允許變更，擋住其他程式誤改。
     - 新料號不可等於其他物料保留中的歷史料號。
   - `items.item_code` 的唯一索引仍然有效。

## 後果
- Migration `M10_01_ItemCodeChange` 全部是 Expand：新表、放寬 `item_reviews` 的兩個 check constraint、改寫 trigger 函式。舊版程式不改料號、不讀新表，所以可以在新結構上執行。
- **A/B 相容窗口內的限制**（`docs/11` §7）：
  - 舊版槽位自動發號時不會跳號。號碼剛好被指定過時，會撞到唯一索引或 trigger，那次核准失敗，切換完成後重試即可。
  - 已有 `CodeChange` 審核紀錄後，如果**回滾到舊版**，舊版讀到這個動作時會出錯（列舉值不認得）。受影響的是物料明細頁與 API `GET /api/items/{id}`；另外舊標籤上的舊料號，在舊版的掃碼與搜尋都會找不到。
  - 操作建議：上線新版後，先**不要**開啟 `items.allow_item_code_change`，等舊槽位停止、確定不會回滾再開。這樣共存期間不會產生 `CodeChange` 紀錄。
- 庫存查詢（`/Stock`、異動、預留）的「料號」篩選只比對目前料號，沒有比對歷史料號；要用舊號查時，先到物料搜尋。`FindIdByItemCodeAsync`（掃碼頁登錄條碼、期初建議儲位）有加上歷史料號的備援查詢。
- 單據、期初、盤點的料號欄（`ScanCodes`）輸入格式像料號、但目前沒有物料使用的號碼時，會多一次查詢（查歷史表，走 `(code, seq)` 索引）；一般輸入目前料號時只多一次 `EXISTS`。
- Migration 放寬 `item_reviews` 的兩個 check constraint 時，會短暫取得 ACCESS EXCLUSIVE 鎖並掃描整張表（目前資料量為毫秒級）。
- `audit_logs` 裡記錄的舊料號文字維持原樣，可以透過 `item_code_history` 對回物料。
- AGENTS.md 第六節第一條同步修改。
