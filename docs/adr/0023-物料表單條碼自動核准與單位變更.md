# ADR-0023：物料表單登錄條碼、管理員自動核准、核准後變更單位與追蹤模式（M8-05）

- 狀態：已接受（Accepted），使用者 2026-10-26 核准
- 相關：AGENTS.md 第六節、ADR-0003 D-02（物料建檔與核准）、ADR-0011、ADR-0013、ADR-0016（原廠條碼）、`docs/04` §3.11

## 背景
使用者 2026-10-26 提出三點：
1. 「提出新物料」與「修改物料」表單要能直接填原廠條碼。原本只能等核准後，到物料頁的「搜尋索引」登錄。
2. 提出人是物料管理員時，表單要有「自動核准」勾選框，並用 cookie 記住上次的選擇。
3. 修改物料時，除了分類以外都要能改，包括基本單位與追蹤模式。物料已有交易時能不能改，由**系統管理員用系統設定開關決定**。

第 3 點放寬了 AGENTS.md 第六節「已有交易者不可改基本單位或追蹤模式」，所以寫成本 ADR。

## 決策
1. **條碼與物料在同一個交易**：
   - 提出時，`ItemWorkflowService.SubmitAsync(…, ItemSubmitOptions)` 開一個交易，依序完成提出、逐一登錄條碼、（可選）核准。任何一步失敗，整筆都不建立，錯誤訊息會指出是哪個條碼。
   - 一張表單最多登錄 10 個條碼（`ItemSubmitOptions.MaxBarcodes`）。
   - 修改時，`UpdateAsync(…, ItemUpdateOptions)` 在同一個交易內新增與停用條碼。程式會先寫入新的單位與追蹤模式，再依新設定檢查條碼的包裝數量。
2. **待核准或退回的物料可以先登錄條碼**：
   - 條碼一提出就先占用，避免核准前被別的物料登錄走。只有提出人或物料管理員能替未核准的物料登錄條碼，其他人不能替別人的申請占住條碼。
   - 未核准物料的條碼不能拿去出入庫，由三道關卡擋住：
     - 掃碼解析（`ScanResolver`）會拒絕。
     - 單據、期初、預留只接受有效的物料。
     - 盤點計數只接受有效或停用的物料（審查 🔴-1：盤點經 `ScanCodes.ItemsAsync` 解析料號時不檢查狀態）。
   - 過帳服務是最後一道防線：非已核准的物料一律拒絕過帳。
   - 物料被拒絕或撤回時，它的條碼會停用，條碼可以再給別的物料用。
   - 別名與關鍵字仍然只限有效物料。
3. **自動核准**：
   - 只有物料管理員看得到勾選框，服務也會再檢查一次（`RequireManager`）。
   - 核准步驟與手動核准共用 `ApproveItemAsync`：重新檢查分類與單位、重複候選、發號，審核紀錄寫入「提出時自動核准」。
   - 重複候選：使用者勾「仍要提出」時，畫面上列出的候選就算已確認。如果核准時又出現新的候選，整筆不建立，畫面重新列出候選。
   - 冪等：同一個 RequestId 重送時，回傳既有的物料與料號，不會再發一個號。
   - 物料核准原本就沒有「不可自核」的限制（D-07 只涵蓋期初、單據、盤點），自動核准沿用這個規則。
   - cookie `wh_item_autoapprove` 只記錄畫面偏好，設為 HttpOnly、SameSite=Lax，效期 1 年；沒有 cookie 時預設不勾。
4. **核准後的修改**：
   - **分類**一律不可改，因為正式料號的前綴來自分類。
   - **基本單位、追蹤模式**只有物料管理員能改，規則見 `CheckUnitTrackingChangeAsync`：
     - **沒有異動紀錄**：可以改。異動紀錄指出現在以下任一張表：`stock_movements`、`stock_balances`、`stock_document_lines`（含草稿）、`stock_reservations`、`stocktake_lines`、`inventory_lots`、`item_serials`。
     - **有異動紀錄**：系統設定 `items.allow_unit_tracking_change_with_activity` 必須開啟（預設關閉，只有系統管理員能改，變更留稽核）。另外要勾選「我了解舊紀錄的數量不會換算」並填寫原因，原因寫進審核紀錄。
     - **安全底線**：即使設定開啟，以下情況仍然擋下：
       - 有未完成的單據（草稿或待核准）、有效預留或進行中的盤點含此物料。
       - 改追蹤模式時結存不全為 0。現有庫存沒有對應的批號或序號，改了之後會無法出庫。
       - 改基本單位時，結存、條碼包裝數量或負庫存下限的小數位數超過新單位允許的位數。
       - 改成序號管理時，有包裝數量不是 1 的條碼。
       - 物料允許負庫存，卻要改成需要追蹤批號或序號。
   - **併發**：
     - 檢查前先 `SELECT … FOR UPDATE` 鎖住物料列。其他交易新增引用此物料的明細、異動或預留時，外鍵檢查會取 KEY SHARE 鎖，與 FOR UPDATE 互斥，所以檢查之後、提交之前不會冒出新的異動。
     - 但寫入方可能在被擋住之前就讀過物料設定。等修改提交後，它會照舊設定寫入（審查 🟠-2）。所以過帳與預留在取得 advisory 鎖之後，用 `FOR KEY SHARE` 重讀物料，並逐筆檢查：
       - 狀態必須是已核准。
       - 批號、序號必須符合追蹤模式：不追蹤時兩者都不可有；批號管理時必須有批號、不可有序號；序號管理時必須有序號。
       - 數量的小數位數必須符合單位。
     - 鎖的順序是「advisory → 物料列」，與負庫存設定相同，不會死結。
   - 條碼的檢查（序號管理只能用包裝數量 1 的條碼、包裝數量的小數位數要符合單位）在三個時機都會做：核准前改單位或追蹤模式時、重新送審時、核准時（含自動核准）。同一次送出要停用的條碼不列入檢查。
   - Domain（`Item.UpdateDetails`）是最後一道防線：核准後改分類一律丟例外；改單位或追蹤模式時，服務必須傳入「已檢查」的旗標。

## 後果
- 好處：
  - 建檔一次就能完成條碼登錄與核准。
  - 建錯單位或追蹤模式的物料，在還沒使用前可以直接修正，不必停用再重建。
- 代價與風險：
  - 有異動紀錄時改單位，**歷史數量不會換算**，報表上舊紀錄會以新單位顯示。所以預設關閉，只交給系統管理員開啟，每次修改都要寫原因並留稽核。
  - 待核准物料占用的條碼，要等拒絕或撤回才會釋放。
  - 「退回 → 修改並重新送審」同時有條碼異動時，是兩個交易：先儲存，再送審。送審失敗時，修改與條碼仍會保留。
  - 追蹤模式改變後，舊的批號、序號主檔（`inventory_lots`、`item_serials`），以及數量為 0 的結存列都會保留。過帳與出庫不受影響；批號或效期報表若沒有過濾數量為 0 的列，可能列出舊批號。
  - 一張表單裡的條碼依正規化文字去重並排序後再登錄。兩張表單以相反順序填同樣的條碼時，會排隊而不會死結。
- 不需要 Migration。系統設定沿用 `system_settings` 表，舊版程式讀不到新鍵也不受影響。
