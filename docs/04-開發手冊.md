## 2.1 一個請求怎麼走完（M0-04）
### 功能要解決的問題
在寫任何業務功能前，先確認「瀏覽器 → API → 資料庫」整條路是通的，並提供兩個健康檢查網址，讓之後的藍綠更新（docs/11 §5）知道新版本是否能接流量。

### 整體流程
```text
瀏覽器 GET /                         手機／PDA／其他程式 GET /api/system/info
  ▼                                    ▼
Warehouse.Web  Pages/Index.cshtml(.cs) ─┐（M0-09 起改為 Razor Page，伺服器端輸出 HTML，不需 JS）
  └── 呼叫 SystemEndpoints.GetSystemInfoAsync ◄┘ 頁面與 API 共用同一個方法
  ▼
Warehouse.Api   Endpoints/SystemEndpoints.cs ──┐
Warehouse.Api   HealthChecks/DatabaseHealthCheck.cs ─┤ 只認得介面
  ▼                                               │
Warehouse.Application  Abstractions/IDatabaseStatus.cs  ◄─┘
  ▲ 由 Infrastructure 實作（依賴反轉）
Warehouse.Infrastructure  Persistence/DatabaseStatus.cs → Persistence/WarehouseDbContext.cs
  ▼ EF Core + Npgsql
PostgreSQL（warehouse_dev）
```
`Warehouse.Web/Program.cs` 是組裝點：讀連線字串，呼叫 `AddWarehouseInfrastructure(...)`（註冊 DbContext 與 `IDatabaseStatus` 實作）與 `AddWarehouseApi()`（註冊健康檢查），再 `MapWarehouseApi()` 掛上所有網址。

### 為什麼 Api 不直接用 DbContext？
Api 不能參考 Infrastructure（分層規則）。所以 Application 定義「我需要知道資料庫能不能連」的介面 `IDatabaseStatus`，Infrastructure 負責實作，Web 在啟動時把兩者接起來。之後的 `InventoryPostingService`、各種 Repository 都會用同樣的模式。

### 網址與回應
| 網址 | 檢查內容 | 正常 | 異常 |
|---|---|---|---|
| `GET /health/live` | 不檢查任何依賴，只代表程序活著 | 200 | 程序沒回應 |
| `GET /health/ready` | 資料庫可連線（3 秒逾時） | 200 `Healthy` | 503 `Unhealthy` |
| `GET /api/system/info` | 版本、DB 是否連線、DB 版本、伺服器時間 | 200 | DB 不通時仍 200，`databaseConnected=false` |

- **live 與 ready 的差別**：DB 暫時斷線時程序本身沒壞，live 仍是 200，不需要重啟；ready 變 503，代表「先別把流量導過來」。反向代理切換版本時看 ready。
- **版本**：`Directory.Build.props` 的 `<Version>0.1.0</Version>`，SDK 會自動附上 Git commit（如 `0.1.0+53e226c…`），由 `src/Warehouse.Api/AppVersion.cs` 讀出，可確認目前接流量的是哪一版。
- 回應不包含例外訊息與連線字串；錯誤以 ProblemDetails 格式回傳並帶 `traceId`，可用來對照伺服器日誌。

### 連線字串放哪裡（不可提交 Git）
| 環境 | 位置 | 設定方式 |
|---|---|---|
| 開發（`dotnet run`） | user-secrets（存在 `%APPDATA%\Microsoft\UserSecrets\`，不在專案資料夾） | `dotnet user-secrets set "ConnectionStrings:Warehouse" "...;Timeout=3" --project src/Warehouse.Web` |
| 整合測試 | 使用者環境變數 `WAREHOUSE_TEST_DB`（指向 `warehouse_test`） | `[Environment]::SetEnvironmentVariable('WAREHOUSE_TEST_DB', '...', 'User')`，設定後重開終端機 |
| 正式環境 | 環境變數 `ConnectionStrings__Warehouse` 或受控設定檔 | M0-10 部署 PoC 時補充 |

資料庫與帳號由 `scripts/init-dev-db.ps1` 建立：登入角色 `warehouse_app`（非超級使用者），資料庫 `warehouse_dev`、`warehouse_test`（owner 皆為 `warehouse_app`）。已存在時會略過，不會改密碼。

使用的套件（2026-10-21 安裝）：`Npgsql.EntityFrameworkCore.PostgreSQL` 10.0.3（PostgreSQL License）、`Microsoft.AspNetCore.Mvc.Testing` 10.0.13（MIT，僅測試專案）。

> ⚠️ 用 `winget install PostgreSQL.PostgreSQL.17` 無人值守安裝時不會詢問密碼，超級使用者 `postgres` 的密碼是預設的 `postgres`。開發機可改成強密碼：`psql -h localhost -U postgres -c "ALTER ROLE postgres PASSWORD '新密碼'"`；正式環境必須使用強密碼並限制連線來源。

**忘記 `warehouse_app` 密碼時**：以 postgres 執行 `ALTER ROLE warehouse_app PASSWORD '新密碼'`，再更新 user-secrets 與 `WAREHOUSE_TEST_DB`。目前的值可用 `dotnet user-secrets list --project src/Warehouse.Web` 查看（只在你的電腦上）。

### 常見錯誤與查找
| 現象 | 原因 | 處理 |
|---|---|---|
| 啟動即失敗：`未設定連線字串 ConnectionStrings:Warehouse` | 沒有設定 user-secrets，或環境不是 Development | 依上表設定；確認 `launchSettings.json` 的 `ASPNETCORE_ENVIRONMENT` |
| ready 503、`databaseConnected=false` | PostgreSQL 服務未啟動、埠號錯、密碼錯 | `.\scripts\check-env.ps1` 檢查 5432；用 `psql -h localhost -U warehouse_app -d warehouse_dev` 試登入 |
| `28P01: password authentication failed` | 連線字串密碼與 `warehouse_app` 不符 | 以 postgres 執行 `ALTER ROLE warehouse_app PASSWORD '...'` 後更新 user-secrets／環境變數 |
| 整合測試失敗並提示設定 `WAREHOUSE_TEST_DB` | 環境變數未設定或終端機未重開 | 設定後重開 PowerShell／VS Code |
| 首頁 404 | Razor Pages 未註冊 | 確認 `Program.cs` 有 `AddRazorPages()` 與 `MapRazorPages()`，頁面位於 `src/Warehouse.Web/Pages/` |
| 樣式沒套用 | 靜態檔未提供 | 確認 `src/Warehouse.Web/wwwroot/css/site.css` 存在、`Program.cs` 有 `UseStaticFiles()` |
| 頁面原始碼中的中文變成 `&#x5DF2;` 這類實體 | Razor 預設只把 ASCII 原樣輸出 | `Program.cs` 已設定 `WebEncoderOptions` 允許 `UnicodeRanges.All`；若被移除，畫面仍正常但頁面變大、測試字串比對會失敗 |

## 6.1 內網 HTTPS 與相機掃碼（M0-05）
### 功能要解決的問題
手機瀏覽器只在「安全內容」（HTTPS 或 localhost）允許使用相機。公司內網沒有公開網域，所以自建一個內部 CA（憑證機構），由它簽發伺服器憑證，再讓電腦與手機信任這個 CA。

### 憑證架構
```text
Warehouse Dev Root CA（根憑證，5 年，私鑰只在開發者 Windows 帳號的憑證存放區，不可匯出）
  └─ 簽發 → 伺服器憑證 CN=DESKTOP-FMD51FK（397 天）
             SAN：DESKTOP-FMD51FK、localhost、192.168.0.86、127.0.0.1
             ↓ 匯出 %LOCALAPPDATA%\Warehouse\certs\warehouse-dev-server.pfx（隨機密碼）
Kestrel 讀 user-secrets：Kestrel:Certificates:Default:Path／Password
手機／電腦信任 warehouse-dev-root-ca.cer → 瀏覽器不再警告 → 可使用相機
```
- 397 天與 SAN／EKU 欄位：iOS 對 TLS 憑證有效期與欄位有限制，太長或缺 SAN 會被拒絕。
- 為什麼不直接用 `dotnet dev-certs`：它只簽 `localhost`，手機用 IP 連線時會不符。

### 相關檔案
| 檔案 | 用途 |
|---|---|
| `scripts/new-dev-certs.ps1` | 建立根 CA（已存在則沿用）、簽發伺服器憑證、信任根 CA、寫入 user-secrets；`-Remove` 全部移除 |
| `scripts/open-dev-firewall.ps1` | 開放 TCP 5443（只限「私人」網路設定檔）；需要系統管理員，會自動跳 UAC；`-Remove` 移除 |
| `src/Warehouse.Web/Properties/launchSettings.json` | `lan` profile：`https://0.0.0.0:5443;http://localhost:5046` |
| `src/Warehouse.Web/Pages/Dev/DevPageModel.cs` | 開發用頁面基底：非 Development 環境一律 404 |
| `src/Warehouse.Web/Pages/Dev/Ca.cshtml(.cs)` | `/dev/ca`：手機下載根 CA＋安裝步驟 |
| `src/Warehouse.Web/Pages/Dev/Camera.cshtml(.cs)` | `/dev/camera`：診斷安全內容、解碼器，按鈕才 `import()` 相機模組 |
| `src/Warehouse.Web/wwwroot/js/camera-scan.js` | 相機模組：BarcodeDetector 優先、jsQR 備援，每 200 ms 解碼，讀到即停止相機 |
| `src/Warehouse.Web/wwwroot/lib/jsqr/` | jsQR 1.4.0（Apache-2.0），`VERSION.txt` 記錄來源與 SHA-1 |

### 本機操作
```powershell
.\scripts\new-dev-certs.ps1          # 第一次會跳出 Windows「安全性警告」，按「是」
.\scripts\open-dev-firewall.ps1      # 跳出 UAC，按「是」
dotnet run --project src/Warehouse.Web --launch-profile lan
# 手機（同一個 Wi-Fi）開 https://192.168.0.86:5443/dev/ca 依頁面步驟安裝根憑證
# 再開 https://192.168.0.86:5443/dev/camera
```
開發機 IP 變了（例如換網路）：重新執行 `new-dev-certs.ps1`，根 CA 沿用、只重簽伺服器憑證，手機不用重新安裝。

### 相機模組重點（`camera-scan.js`）
- **延遲載入**：頁面只有一小段診斷程式；按下「開始」才 `import('/js/camera-scan.js')`，需要時再載入 jsQR（約 257 KB，未壓縮）。鍵盤／條碼槍掃碼頁完全不載入（T-PERF-05）。
- **解碼器選擇**：`BarcodeDetector.getSupportedFormats()` 含 `qr_code` 就用瀏覽器內建（Android Chrome）；否則用 jsQR（iPhone、Windows）。
- **省電**：每 200 ms 解碼一次、畫面縮到最長 640 px。
- **釋放相機**：讀到結果、按停止、`visibilitychange` 變 hidden、`pagehide` 時呼叫 `track.stop()`，手機相機指示燈應熄滅。
- iPhone 需要 `<video playsinline muted>`，否則會跳全螢幕播放。

### 風險
- 信任此根 CA 的裝置，會信任它簽發的**任何**憑證；根 CA 私鑰設為不可匯出、只存在開發者帳號中。測試結束可用 `-Remove` 及手機設定移除。
- 正式環境的 CA 與內網網域（D-09、D-27）在 M7 決定，不沿用開發用 CA。

### 常見錯誤與查找
| 現象 | 原因 | 處理 |
|---|---|---|
| 腳本錯誤「此作業不允許 UI」 | 從非互動環境（IDE、AI 工具）直接匯入受信任根憑證 | 腳本已改為另開視窗匯入；若視窗被擋住，在工作列找「安全性警告」 |
| 手機顯示「連線不是私人連線」 | 尚未安裝根 CA，或 iPhone 未開「完全信任」 | 依 `/dev/ca` 步驟；iPhone 一定要到「憑證信任設定」打開 |
| 手機連不上（逾時） | 防火牆未開、手機不在同一 Wi-Fi、Windows 網路設為「公用」 | 執行 `open-dev-firewall.ps1`；確認網路設定檔為「私人」 |
| 相機頁顯示「安全內容：否」 | 用 http 或 IP 不在憑證 SAN 內 | 改用 `https://`；IP 改變時重跑 `new-dev-certs.ps1` |
| `NotAllowedError` | 使用者拒絕相機權限 | 頁面會顯示重新允許的步驟 |
| 在開發機檢查憑證，簽發者是「Avast Web/Mail Shield Root」等防毒軟體名稱 | 防毒軟體的 HTTPS 掃描會攔截本機連線並改用自己的憑證 | 本機看到的不是伺服器真正送出的憑證；改用 `X509Chain` 只信任 Warehouse 根 CA 驗證 PFX（指令見 `docs/07` M0-05 歷程），或用手機檢查 |

### 9.1 前端比較量測工具（M0-08）
`poc/` 是獨立於正式程式的比較實驗（不在 `Warehouse.slnx` 內），用來回答「哪種前端在舊電腦與 Chrome 109 上最輕、最穩」。

```text
poc/
├─ CONTRACT.md          # 兩個 PoC 必須相同的網址與 DOM id（量測腳本靠它通用）
├─ Poc.Shared/          # FakeItemCatalog：固定種子產生 20,000 筆料號，伺服器端搜尋分頁
├─ Poc.RazorPages/      # port 5101；掃碼用 wwwroot/js/scan.js（JS 佇列＋fetch /api/items/{code}）
├─ Poc.BlazorSsr/       # port 5102；/scan 用表單送出、/scan-js 用同一份 scan.js
├─ Poc.BlazorWasm/      # 空白範本，只量首次載入
├─ Poc.Bench/           # Playwright 量測程式（Program.cs 的 Scenarios 類別＝各量測情境）
├─ publish-all.ps1      # 以 Release 發布三個 PoC 到 .publish/
└─ results/             # 量測輸出 JSON
```

**重跑量測**
```powershell
cd poc
.\publish-all.ps1                                         # 修改 PoC 後一定要重新發布
dotnet run --project Poc.Bench -c Release -- --quick      # 快速版（約 3 分鐘），確認腳本能跑
dotnet run --project Poc.Bench -c Release                 # 正式版（約 15 分鐘）
dotnet run --project Poc.Bench -c Release -- --target razor-pages --browser chromium-109   # 只跑一組
```
瀏覽器：Playwright 內建新版 Chromium（`playwright.ps1 install chromium` 安裝到 `%LOCALAPPDATA%\ms-playwright`），以及 `poc/.browsers/chromium-109/`（Chromium 官方快照 revision 1070054＝109.0.5414.0，不進 Git）。

**各指標怎麼讀**
| 欄位 | 意義 | 怎麼量 |
|---|---|---|
| `firstLoadSearch.transferKb` | 第一次開頁面（無快取）網路傳輸量 | Playwright `Request.SizesAsync()` 加總 |
| `searchLatency.p50Ms/p95Ms` | 按 Enter 到結果出現的時間 | 送出前在頁面放標記元素，等它消失且 `#total-count` 存在 |
| `scan.lostOrGarbled` | 50 筆連續掃碼（每字 10 ms）中遺失或變形的筆數 | 比對清單內容與送出的料號 |
| `idleCpu.cpuPercent` | 頁面閒置時瀏覽器主執行緒忙碌比例 | CDP `Performance.getMetrics` 的 `TaskDuration` 差值 |
| `longRunMemory` | 300 次查詢前後 JS 記憶體與 DOM 節點數 | 先強制 GC，再取 `JSHeapUsedSize`、`Nodes` |
| `serverMemory:*` | 伺服器程序記憶體（影響 NAS 與 A/B 雙實例） | `Process.WorkingSet64` |

- **CPU 節流 4 倍**：用 CDP `Emulation.setCPUThrottlingRate` 讓瀏覽器跑慢 4 倍，近似舊電腦；只是模擬，實機結果仍以 M7-11 為準。
- 量測腳本所有情境都包在 `Safe()` 裡：某一項失敗（例如舊瀏覽器不相容）會記錄錯誤訊息而不中斷，結果檔中看到 `error` 欄位即代表該項失敗。

**量測過程學到的陷阱（之後寫正式畫面時要注意）**
- 用「表單送出」做掃碼，伺服器回應會把輸入框重設為空白，條碼槍在回應前已輸入的下一筆字元會被吃掉（實測 50 筆遺失 44 筆）。掃碼一律用 JS 佇列：Enter 時取值、立刻清空、背景依序查詢。
- Blazor enhanced form／navigation 不是整頁導覽：回應抵達前使用者輸入的內容會被覆蓋；以 enhanced navigation 進入的頁面，頁面內 `<script>` 不會執行。

## 10. Windows PC 部署與維護教學（M0-10 PoC，2026-10-21 實測）
> 本節的服務只聽 `http://localhost:<埠>`；對外 HTTPS、反向代理與 A/B 切換見 §12。設計理由見 ADR-0008。

### 伺服器目錄（`C:\Warehouse`，可用 `-Root` 改）
```text
C:\Warehouse\
├─ releases\0.1.0-e2a5f49-win-x64-fdd\   # 每個版本一個資料夾，永不覆寫；回滾＝讓服務指回舊資料夾
├─ config\appsettings.Production.json    # 連線字串等；只有 Administrators、SYSTEM、服務帳號能讀
├─ certs\                                # 正式 HTTPS 憑證（M7）
├─ data\attachments\                     # 附件（服務帳號可寫）
└─ logs\                                 # 日誌（服務帳號可寫）
```
程式怎麼找到設定：服務的環境變數 `WAREHOUSE_CONFIG_DIR=C:\Warehouse\config` → `src/Warehouse.Web/ExternalConfiguration.cs` 載入該目錄的 `appsettings.json`、`appsettings.Production.json`（順序在環境變數之前，所以環境變數仍可覆寫）。

### 1. 發布（`scripts/publish.ps1`）
```powershell
.\scripts\publish.ps1 -Runtime win-x64                 # framework-dependent（伺服器需安裝 ASP.NET Core Runtime 10）
.\scripts\publish.ps1 -Runtime win-x64 -SelfContained  # 自含 Runtime
```
- 先檢查工作目錄乾淨（版本號含 commit），再跑全部測試，再 `dotnet publish -c Release -r <RID>`。
- 輸出 `artifacts\publish\<版本>-<commit7>-<RID>-<fdd|sc>\`（不進 Git），內含 `release.json`（版本、commit、RID、部署型式、檔案數、大小）。
- 實測：framework-dependent **37 檔、7.7 MB**；self-contained **367 檔、112.9 MB**。

### 2. 安裝成服務（`scripts/windows/install-service.ps1`）
```powershell
# 第一次安裝：先把連線字串寫進只有自己能讀的暫存檔，腳本讀取後會刪除（避免密碼出現在命令列）
.\scripts\windows\install-service.ps1 -ReleasePath artifacts\publish\<版本資料夾> -ConnectionStringFile <暫存檔> -VerifyRestart
```
預期輸出：
```text
已複製版本：C:\Warehouse\releases\...
已建立設定檔（連線字串不顯示）。
已建立服務 WarehouseA（帳號 NT SERVICE\WarehouseA，埠 5080）
服務已就緒：http://localhost:5080/health/ready = 200
重新啟動驗證：1.2 秒後恢復就緒
狀態：Running；帳號：NT SERVICE\WarehouseA；啟動類型：Auto；PID ...；記憶體 94 MB
```
腳本做的事：
- **虛擬服務帳號** `NT SERVICE\WarehouseA`：不用 LocalSystem（權限過大），也不用建立真的使用者與管理密碼。
- 啟動類型「自動（延遲）」：開機後等其他服務（例如 PostgreSQL）先起來。
- 失敗自動重啟：`sc.exe failure`，5 秒、10 秒後重試。
- 服務專屬環境變數寫在 `HKLM\SYSTEM\CurrentControlSet\Services\<名稱>\Environment`，只影響這個服務。
- `icacls` 設定目錄權限（見上方目錄圖）。
- 沒有提供連線字串時，會建立設定範本並停止，請編輯 `config\appsettings.Production.json` 後重跑。

### 3. 日常管理
```powershell
Get-Service WarehouseA                          # 狀態
Restart-Service WarehouseA                      # 重新啟動（需系統管理員）
Invoke-RestMethod http://localhost:5080/api/system/info   # 目前版本與 DB 狀態
Get-WinEvent -FilterHashtable @{LogName='System'; ProviderName='Service Control Manager'} -MaxEvents 20 |
    Where-Object Message -like '*WarehouseA*'   # 服務安裝、啟動、停止紀錄
```
程式的警告與錯誤會寫入「事件檢視器 → Windows 記錄 → 應用程式」，來源為程式名稱。

### 4. 移除與回滾
```powershell
.\scripts\windows\uninstall-service.ps1               # 移除服務，保留 C:\Warehouse 全部內容
.\scripts\windows\uninstall-service.ps1 -RemoveData   # 連同設定與資料全部刪除（無法復原）
```
回滾到舊版：M0-12 起改用 `switch-release.ps1 -Rollback`（見 §12）。資料庫結構相容性見 §12 與 `docs/11`。

### 常見錯誤
| 現象 | 原因 | 處理 |
|---|---|---|
| 啟動失敗「錯誤 1053：服務沒有及時回應」 | 程式啟動即拋例外（例如缺連線字串、設定目錄不存在） | 事件檢視器「應用程式」查例外；確認 `config\appsettings.Production.json` 內容 |
| `WAREHOUSE_CONFIG_DIR 指向的設定目錄不存在` | 服務環境變數路徑錯誤 | 檢查登錄 `Services\<名稱>\Environment` |
| 頁面樣式消失、首頁 404 | 服務模式下工作目錄是 `C:\Windows\System32` | `Program.cs` 已在服務模式把內容根目錄設為程式目錄；若被移除會發生 |
| `/health/ready` 503 | 連不到資料庫 | 檢查 PostgreSQL 服務與連線字串 |
| 存取被拒（讀 config、寫 logs） | ACL 未包含服務帳號 | 重新執行安裝腳本的權限步驟，或依上方目錄圖用 `icacls` 補上 |
| 埠已被占用 | 另一個實例或程式使用同一埠 | `Get-NetTCPConnection -LocalPort 5080`；A/B 兩個實例要用不同埠 |

## 11. Linux 部署與維護教學（M0-11 PoC，2026-10-21 於 WSL2 Ubuntu 24.04 實測）
> 決策與數據見 ADR-0009。尚未在實體 NAS 驗證；取得型號後補「NAS 實機」小節（CPU、RAM、OS、容器環境、HTTPS、備份、A/B 能否並存）。

### 11.1 開發機的 Linux 測試環境（WSL2）
- `%USERPROFILE%\.wslconfig` 設 `networkingMode=mirrored`：Linux 內的 `localhost` 就是 Windows 的 `localhost`，可直接連 Windows 上的 PostgreSQL。
- 發行版 `Ubuntu-24.04`，`/etc/wsl.conf` 已啟用 systemd；已安裝 .NET SDK 10（`/usr/share/dotnet`，連結 `/usr/bin/dotnet`）、Docker Engine（官方 apt 套件庫）、QEMU binfmt（arm64）。
- 從 PowerShell 執行 Linux 指令：`$env:WSL_UTF8=1; wsl -d Ubuntu-24.04 -u root -- bash -c '<指令>'`（`WSL_UTF8` 讓中文輸出不變亂碼；複雜指令寫成 `.sh` 檔再執行，避免 PowerShell 與 bash 的引號互相干擾）。
- 在 Linux 跑測試：`git clone /mnt/c/CodeProject/物料管理系統 ~/warehouse` 後 `dotnet test Warehouse.slnx`；`WAREHOUSE_TEST_DB` 可用 `$env:WSLENV='WAREHOUSE_TEST_DB'` 從 Windows 傳入。

### 11.2 原生 systemd 服務
```bash
# Windows：.\scripts\publish.ps1 -Runtime linux-x64   → artifacts/publish/<版本>-linux-x64-fdd
sudo ./scripts/linux/install-service.sh --release <發布資料夾> --connection-string-file <只含連線字串的檔案> --verify-restart
sudo ./scripts/linux/uninstall-service.sh            # 保留 /opt、/etc、/var/lib 下的資料；--remove-data 全刪
```
| 路徑 | 擁有者／權限 | 用途 |
|---|---|---|
| `/opt/warehouse/releases/<版本>/` | root，唯讀 | 發布檔，每版一個資料夾 |
| `/etc/warehouse/appsettings.Production.json` | root:warehouse 0640 | 連線字串（`--connection-string-file` 讀完即刪除該檔） |
| `/var/lib/warehouse/{data,keys}` | warehouse 0750 | 服務可寫入的唯一位置 |
| `/etc/systemd/system/warehouse-a.service` | root | `Type=notify`、`Restart=on-failure`、加固設定 |

程式如何配合 systemd：`Program.cs` 的 `AddSystemd()` 只在被 systemd 啟動時作用——日誌改成 journald 格式、啟動完成才送出「就緒」通知（所以 `systemctl start` 會等到程式真的能服務），收到 SIGTERM 時正常關閉。在 Windows 或一般執行時不做任何事，與 `AddWindowsService()` 並存。

常用維護指令：
```bash
systemctl status warehouse-a
journalctl -u warehouse-a -n 50 --no-pager      # 最近日誌；-f 持續追蹤
curl -s localhost:5081/health/ready             # 版本＋DB 檢查
systemctl show warehouse-a -p MemoryCurrent     # 服務實際記憶體（cgroup）
```

### 11.3 容器（Docker）
```bash
docker build -f deploy/docker/Dockerfile --build-arg RELEASE_DIR=artifacts/publish/<版本資料夾> -t warehouse:<版本> .
docker run -d --name warehouse-c --network host --restart unless-stopped \
  --group-add "$(getent group warehouse | cut -d: -f3)" \
  -e ASPNETCORE_URLS=http://localhost:5082 -v /etc/warehouse:/config:ro warehouse:<版本>
docker stats --no-stream warehouse-c
```
- 映像只包含發布檔，與原生部署是同一份；連線字串不在映像內，由掛載的 `/config` 提供。
- ARM64：`docker build --platform linux/arm64`，RELEASE_DIR 指向 `linux-arm64` 發布資料夾。開發機需先 `docker run --privileged --rm tonistiigi/binfmt --install arm64`；這是**模擬**，速度約慢 8～10 倍，只用來確認能啟動。

### 11.4 常見錯誤
| 錯誤訊息／現象 | 原因 | 處理 |
|---|---|---|
| 容器啟動即結束（exit 139），日誌「未設定連線字串 ConnectionStrings:Warehouse」 | 容器內 UID 1654 讀不到 `0750 root:warehouse` 的 `/etc/warehouse` | `docker run` 加 `--group-add <warehouse gid>` |
| `install-service.sh`：「服務 warehouse-a 已存在」 | 重複安裝 | 先 `uninstall-service.sh`，或用 `--name warehouse-b --port 5082` |
| 「已建立設定範本 …，請填入連線字串後重新執行」 | 第一次安裝未給 `--connection-string-file` | 編輯該檔或改用參數重跑 |
| 「找不到 dotnet」 | framework-dependent 版本需要 ASP.NET Core Runtime 10 | 安裝 Runtime，或改發布 `-SelfContained` |
| PowerShell 呼叫 `wsl` 的輸出是亂碼 | `wsl.exe` 預設輸出 UTF-16 | 先設定 `$env:WSL_UTF8=1` |

### 11.5 已知限制
- 腳本需要 `bash`、`systemd`、`curl`、`bc`、`python3`；NAS 系統需逐項確認。
- ~~Data Protection 金鑰只存在記憶體~~：M0-12 起 `install-service.sh` 設定 `DataProtection__KeysDirectory=/var/lib/warehouse/keys`，重啟與 A/B 之間都沿用同一組金鑰（§12）。

## 12. 線上更新與回滾教學（M0-12 PoC，2026-10-21 實測）
> 決策與實測數據見 ADR-0010；設計目標與非目標見 `docs/11`。尚未涵蓋：庫存交易切版冪等（M4）、PWA 更新（尚未實作 PWA）、Schema 變更流程實演（目前無 Migration）。

### 12.1 架構與名詞
```text
手機／PC ──HTTPS 5443──> WarehouseProxy（src/Warehouse.Proxy，YARP）
                              │ 只轉到 upstream.json 指定的槽位
                 ┌────────────┴────────────┐
       槽位 A：WarehouseA :5080      槽位 B：WarehouseB :5081   （只聽 localhost）
                 └──── 同一 config\、data\keys\、PostgreSQL ────┘
```
- **槽位**：固定的服務名稱＋埠。更新時新版裝到「待命槽位」，舊槽位停止後保留供回滾。
- **upstream.json**（`C:\Warehouse\proxy-config\`）：`ActiveSlot` 與代理目的地。這是唯一的切換開關。
- 伺服器目錄新增：`proxy-config\`（代理專用，含憑證密碼，只給代理帳號讀）、`certs\warehouse-server.pfx`、`data\keys\`（A/B 共用金鑰）、`logs\deploy.log`（切換紀錄）。
- **`upstream.json` 不要手動編輯**：格式錯誤時代理會回 503；一律用 `switch-release.ps1`。
- 權限（審查後修正）：安裝腳本先執行 `Set-RootAcl`，`C:\Warehouse` 改為不繼承 `C:\`、擁有者 Administrators，一般使用者完全無法讀取；各服務帳號只拿到需要的目錄權限。檢查：`icacls C:\Warehouse` 應只有 Administrators、SYSTEM。

### 12.2 程式怎麼運作
| 檔案 | 作用 |
|---|---|
| `src/Warehouse.Proxy/Program.cs` | `AddReverseProxy().LoadFromConfig("ReverseProxy")`、`MapReverseProxy()`；也呼叫 `AddWindowsService`／`AddSystemd` |
| `src/Warehouse.Proxy/UpstreamFile.cs` | 從 `WAREHOUSE_CONFIG_DIR` 載入 `upstream.json`，`reloadOnChange: true`：檔案一改，YARP 收到設定變更，**新請求**改送新目的地；已在舊目的地處理中的請求不受影響 |
| `src/Warehouse.Proxy/appsettings.json` | 固定路由 `{**catch-all}` → cluster `app`；YARP 日誌降為 Warning（避免每個請求一行） |
| `src/Warehouse.Proxy/Warehouse.Proxy.csproj` | 以連結編譯共用 `src/Warehouse.Web/ExternalConfiguration.cs` |
| `src/Warehouse.Web/SharedDataProtection.cs` | `DataProtection:KeysDirectory` 有值時金鑰存到該目錄（Windows 加 DPAPI）；ApplicationName 固定 `Warehouse` |
| `src/Warehouse.Web/Program.cs` | `UseForwardedHeaders`：讀代理加的 `X-Forwarded-Proto`，程式才知道外部是 HTTPS（之後 Cookie `Secure`、重新導向需要） |

為什麼 ApplicationName 要固定：框架預設用「內容根目錄路徑」區分應用程式，A、B 安裝在不同版本資料夾，預設值不同，即使共用金鑰目錄也互相解不開（`DataProtectionSharingTests` 驗證）。

### 12.3 第一次安裝（Windows，需系統管理員；非管理員會跳 UAC）
```powershell
.\scripts\publish.ps1 -Runtime win-x64                      # 主程式 → artifacts\publish\<版本>-win-x64-fdd
.\scripts\publish.ps1 -Project Proxy -Runtime win-x64       # 代理   → artifacts\publish\proxy-<版本>-win-x64-fdd
.\scripts\windows\install-service.ps1 -ReleasePath <主程式資料夾> -ServiceName WarehouseA -Port 5080   # 第一次需 -ConnectionStringFile
# PFX 密碼寫進暫存檔，腳本讀取後刪除
.\scripts\windows\install-proxy.ps1 -ReleasePath <代理資料夾> -PfxPath <pfx> -PfxPasswordFile <暫存檔>
```
預期：`代理已啟動：https://localhost:5443/health/ready = 200`。之後使用者一律連 `https://<主機>:5443/`。

### 12.4 更新與回滾
```powershell
.\scripts\windows\switch-release.ps1 -ReleasePath artifacts\publish\<新版資料夾>   # 更新
.\scripts\windows\switch-release.ps1 -Rollback                                     # 切回待命槽位的版本
Get-Content C:\Warehouse\logs\deploy.log -Tail 20                                  # 切換紀錄
```
更新的預期輸出：
```text
開始更新：A（0.1.0+0a6bd14…）→ B（0.1.0+a86fabe…）
已建立服務 WarehouseB（帳號 NT SERVICE\WarehouseB，埠 5081）
服務已就緒：http://localhost:5081/health/ready = 200
冒煙測試通過：版本 0.1.0+a86fabe…、資料庫已連線
流量已切換：A → B（0.5 秒確認）
排空 10 秒，讓槽位 A 處理完進行中的請求…
已停止槽位 A（WarehouseA，保留供回滾）
完成：目前槽位 B，版本 0.1.0+a86fabe…
```
每一步的理由：
1. **裝到待命槽位**：不動正在服務的版本；失敗時使用者完全不受影響。
2. **readiness＋冒煙**：`/health/ready`（含 DB）通過、`/api/system/info` 版本正確才往下走。
3. **原子改寫 upstream.json 後經代理確認版本**：只看「檔案寫入成功」不夠（檔案監看可能延遲或失效），要從使用者的入口確認。
4. **排空**：切換後舊槽位可能還有請求在處理；等待 `-DrainSeconds`（預設 10）再停止。停止時 ASP.NET Core 也會等進行中的請求結束（預設最多 30 秒）。
5. **舊槽位改「手動」**：重開機後只會啟動目前槽位，不浪費記憶體。

### 12.5 確認目前狀態
```powershell
(Get-Content C:\Warehouse\proxy-config\upstream.json | ConvertFrom-Json).ActiveSlot   # A 或 B
Invoke-RestMethod https://localhost:5443/health/ready                                 # 使用者實際接到的版本
Get-Service WarehouseA, WarehouseB, WarehouseProxy
```

### 12.6 常見錯誤
| 現象／訊息 | 原因 | 處理 |
|---|---|---|
| 「槽位 B 新版未就緒，更新中止，流量維持 A」 | 新版啟動失敗或連不到 DB | 事件檢視器查 WarehouseB；流量未受影響，修正後重跑 |
| 「冒煙測試失敗：版本 …」 | 發布資料夾與 release.json 不一致 | 重新發布，不要手動改發布資料夾內容 |
| 「代理未在 15 秒內轉到槽位 B，已改回槽位 A」 | 代理沒載入新的 upstream.json（服務停止、檔案權限） | `Get-Service WarehouseProxy`；`icacls C:\Warehouse\proxy-config` 應含 `NT SERVICE\WarehouseProxy:(R)` |
| 「待命槽位 B 沒有安裝服務，無法回滾」 | 從未更新過 | 用 `-ReleasePath <舊版>` 部署舊版 |
| 更新失敗後 `-Rollback` 回到壞版本 | 更新會覆蓋待命槽位 | 用 `-ReleasePath` 重新部署要的版本 |
| 代理回 502 | 目前槽位服務停止 | 啟動該槽位，或 `-Rollback` |
| `dotnet run --launch-profile lan` 埠 5443 被占用 | 代理服務正在用 5443 | 開發時停止 `WarehouseProxy` 或改用其他 profile |
| 表單送出 400（防偽權杖無效） | A/B 金鑰目錄或 ApplicationName 不一致 | 檢查服務環境變數 `DataProtection__KeysDirectory`；`data\keys` 應只有共用的 `key-*.xml` |

### 12.7 Linux（WSL 簡測，精簡腳本）
```bash
sudo ./scripts/linux/install-service.sh --release <主程式> --name warehouse-a --port 5180
sudo ./scripts/linux/install-service.sh --release <代理> --name warehouse-proxy --port 5480 \
     --config-dir /etc/warehouse-proxy --upstream-port 5180
sudo ./scripts/linux/switch-release.sh --release <新版> --proxy-url http://localhost:5480 --port-a 5180 --port-b 5181
sudo ./scripts/linux/switch-release.sh --rollback --proxy-url http://localhost:5480 --port-a 5180 --port-b 5181
```
- WSL mirrored 網路與 Windows 共用 localhost 埠，所以 Linux 測試改用 5180／5181／5480，避免與 Windows 的 5080／5081／5443 衝突；實際 NAS 可用預設值。
- 代理以獨立使用者 `warehouse-proxy` 執行（`install-service.sh` 依 release.json 的 `entry` 自動切換），讀不到 `/etc/warehouse` 的連線字串與 `/var/lib/warehouse/keys`。
- Linux 簡測的代理只聽 HTTP；NAS 實機的 HTTPS 設定待取得設備後補（`Kestrel:Endpoints` 與憑證放在 `/etc/warehouse-proxy/appsettings.Production.json`）。
- 紀錄在 `/var/log/warehouse-deploy.log`。
