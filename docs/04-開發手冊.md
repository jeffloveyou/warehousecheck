# 開發手冊｜從第一天開始寫、隨功能成長

> **v1.0（2026-10-27，V1 交付）**：本手冊記錄 V1 實際程式（M0～M8-06）的位置、資料流、修改方式與除錯方法，之後每次變更仍要同步更新對應章節。正式環境的操作步驟另見 `docs/12`～`docs/15`。

## 0. 文件用途與閱讀方式
本手冊持續記錄一個完整請求的路徑：`Web 頁面 → HTTP API → Application Service → Domain Rule → EF Core → PostgreSQL → 回傳結果`。接著了解 DTO、依賴注入、Migration、測試與日誌。看得懂比「AI 一次做完」重要。

### 依賴方向（只允許外層 → 內層）
```text
Web ──> Api ────────────> Application ──> Domain
 └────> Infrastructure ──────┘

Proxy（獨立，不參考任何 Warehouse 專案；只以連結編譯共用 Web/ExternalConfiguration.cs）
```
- 由各 `.csproj` 的 `ProjectReference` 決定；Domain 沒有任何專案參考。
- `Warehouse.Api` 是類別庫，以 `<FrameworkReference Include="Microsoft.AspNetCore.App" />` 使用 ASP.NET Core 型別，由 `Warehouse.Web` 載入（ADR-0006）。
- 防護測試：`tests/Warehouse.UnitTests/Architecture/LayerDependencyTests.cs` 檢查 Domain、Application 沒有實際使用 EF Core、ASP.NET Core、Npgsql 或外層組件；透過 `src/Warehouse.Domain/AssemblyMarker.cs`、`src/Warehouse.Application/AssemblyMarker.cs` 取得組件。編譯器只保留實際用到的引用，所以這是「實際使用」的檢查。
- 為什麼 Proxy 不參考其他專案：它只轉送 HTTP，不需要業務程式；保持獨立才能用很少的記憶體執行，也不會因為主程式改版而必須重新部署。

## 2.1 一個請求怎麼走完（M0-04）
### 功能要解決的問題
在寫任何業務功能前，先確認「瀏覽器 → API → 資料庫」整條路是通的，並提供兩個健康檢查網址，讓之後的藍綠更新（docs/11 §5）知道新版本是否能接流量。

### 整體流程
```text
瀏覽器 GET /                         手機／PDA／其他程式 GET /api/system/info
  ▼                                    ▼
Warehouse.Web  Pages/Index.cshtml(.cs) ─┐（M0-09 起改為 Razor Page，伺服器端輸出 HTML，不需 JS）
  └── 呼叫 SystemEndpoints.GetSystemInfoAsync ◄┘ 頁面與 API 共用同一個方法
  ▼
Warehouse.Api   Endpoints/SystemEndpoints.cs ──┐
Warehouse.Api   HealthChecks/DatabaseHealthCheck.cs ─┤ 只認得介面
  ▼                                               │
Warehouse.Application  Abstractions/IDatabaseStatus.cs  ◄─┘
  ▲ 由 Infrastructure 實作（依賴反轉）
Warehouse.Infrastructure  Persistence/DatabaseStatus.cs → Persistence/WarehouseDbContext.cs
  ▼ EF Core + Npgsql
PostgreSQL（warehouse_dev）
```
`Warehouse.Web/Program.cs` 是組裝點：讀連線字串，呼叫 `AddWarehouseInfrastructure(...)`（註冊 DbContext 與 `IDatabaseStatus` 實作）與 `AddWarehouseApi()`（註冊健康檢查），再 `MapWarehouseApi()` 掛上所有網址。

### 為什麼 Api 不直接用 DbContext？
Api 不能參考 Infrastructure（分層規則）。所以 Application 定義「我需要知道資料庫能不能連」的介面 `IDatabaseStatus`，Infrastructure 負責實作，Web 在啟動時把兩者接起來。之後的 `InventoryPostingService`、各種 Repository 都會用同樣的模式。

### 網址與回應
| 網址 | 檢查內容 | 正常 | 異常 |
|---|---|---|---|
| `GET /health/live` | 不檢查任何依賴，只代表程序活著 | 200 | 程序沒回應 |
| `GET /health/ready` | 資料庫可連線（3 秒逾時） | 200 `Healthy` | 503 `Unhealthy` |
| `GET /api/system/info` | 版本、DB 是否連線、DB 版本、伺服器時間 | 200 | DB 不通時仍 200，`databaseConnected=false` |

- **live 與 ready 的差別**：DB 暫時斷線時程序本身沒壞，live 仍是 200，不需要重啟；ready 變 503，代表「先別把流量導過來」。反向代理切換版本時看 ready。
- **版本**：`Directory.Build.props` 的 `<Version>0.1.0</Version>`，SDK 會自動附上 Git commit（如 `0.1.0+53e226c…`），由 `src/Warehouse.Api/AppVersion.cs` 讀出，可確認目前接流量的是哪一版。
- 回應不包含例外訊息與連線字串；錯誤以 ProblemDetails 格式回傳並帶 `traceId`，可用來對照伺服器日誌。

### 連線字串放哪裡（不可提交 Git）
| 環境 | 位置 | 設定方式 |
|---|---|---|
| 開發（`dotnet run`） | user-secrets（存在 `%APPDATA%\Microsoft\UserSecrets\`，不在專案資料夾） | `dotnet user-secrets set "ConnectionStrings:Warehouse" "...;Timeout=3" --project src/Warehouse.Web` |
| 整合測試 | 使用者環境變數 `WAREHOUSE_TEST_DB`（指向 `warehouse_test`） | `[Environment]::SetEnvironmentVariable('WAREHOUSE_TEST_DB', '...', 'User')`，設定後重開終端機 |
| 正式環境 | `WAREHOUSE_CONFIG_DIR` 指向的 `appsettings.Production.json`（Windows `C:\Warehouse\config\`、Linux `/etc/warehouse/`） | 安裝腳本以 `-ConnectionStringFile`／`--connection-string-file` 建立，見 §10、§11 |

資料庫與帳號由 `scripts/init-dev-db.ps1` 建立：登入角色 `warehouse_app`（非超級使用者），資料庫 `warehouse_dev`、`warehouse_test`（owner 皆為 `warehouse_app`）。已存在時會略過，不會改密碼。

使用的套件見 §2.2。

> ⚠️ 用 `winget install PostgreSQL.PostgreSQL.17` 無人值守安裝時不會詢問密碼，超級使用者 `postgres` 的密碼是預設的 `postgres`。開發機可改成強密碼：`psql -h localhost -U postgres -c "ALTER ROLE postgres PASSWORD '新密碼'"`；正式環境必須使用強密碼並限制連線來源。

**忘記 `warehouse_app` 密碼時**：以 postgres 執行 `ALTER ROLE warehouse_app PASSWORD '新密碼'`，再更新 user-secrets 與 `WAREHOUSE_TEST_DB`。目前的值可用 `dotnet user-secrets list --project src/Warehouse.Web` 查看（只在你的電腦上）。

### 本機操作
```powershell
dotnet run --project src/Warehouse.Web
# 瀏覽器開 http://localhost:5046 ：顯示版本與「資料庫已連線」
# 另開視窗：
Invoke-RestMethod http://localhost:5046/health/ready
Invoke-RestMethod http://localhost:5046/api/system/info
```
模擬 DB 故障：停止 Windows 服務 `postgresql-x64-17` → `/health/ready` 變 503、`/health/live` 仍 200；重新啟動服務後恢復。

### 自動測試
`tests/Warehouse.IntegrationTests/HealthEndpointTests.cs`（對應 docs/05 T-M0-04-01～04）以 `WarehouseWebFactory` 在記憶體中啟動整個 Web 程式。工廠設定環境為 `Testing`（避免讀到開發用 user-secrets），並用 `UseSetting` 注入連線字串——因為 `Program.cs` 在 `Build()` 前就讀連線字串，用 `ConfigureAppConfiguration` 會太晚生效。

### 常見錯誤與查找
| 現象 | 原因 | 處理 |
|---|---|---|
| 啟動即失敗：`未設定連線字串 ConnectionStrings:Warehouse` | 沒有設定 user-secrets，或環境不是 Development | 依上表設定；確認 `launchSettings.json` 的 `ASPNETCORE_ENVIRONMENT` |
| ready 503、`databaseConnected=false` | PostgreSQL 服務未啟動、埠號錯、密碼錯 | `.\scripts\check-env.ps1` 檢查 5432；用 `psql -h localhost -U warehouse_app -d warehouse_dev` 試登入 |
| `28P01: password authentication failed` | 連線字串密碼與 `warehouse_app` 不符 | 以 postgres 執行 `ALTER ROLE warehouse_app PASSWORD '...'` 後更新 user-secrets／環境變數 |
| 整合測試失敗並提示設定 `WAREHOUSE_TEST_DB` | 環境變數未設定或終端機未重開 | 設定後重開 PowerShell／VS Code |
| 首頁 404 | Razor Pages 未註冊 | 確認 `Program.cs` 有 `AddRazorPages()` 與 `MapRazorPages()`，頁面位於 `src/Warehouse.Web/Pages/` |
| 樣式沒套用 | 靜態檔未提供 | 確認 `src/Warehouse.Web/wwwroot/css/site.css` 存在、`Program.cs` 有 `UseStaticFiles()` |
| 頁面原始碼中的中文變成 `&#x5DF2;` 這類實體 | Razor 預設只把 ASCII 原樣輸出 | `Program.cs` 已設定 `WebEncoderOptions` 允許 `UnicodeRanges.All`；若被移除，畫面仍正常但頁面變大、測試字串比對會失敗 |

### 常見修改
- 新增其他就緒檢查（例如附件儲存位置可寫入）：在 `src/Warehouse.Api/HealthChecks/` 新增 `IHealthCheck`，於 `AddWarehouseApi()` 以 `tags: ["ready"]` 註冊。
- 調整逾時：`DatabaseHealthCheck` 與 `SystemEndpoints` 中的 3 秒，以及連線字串的 `Timeout=3`。

| `units` | `code`（PCS…）、`name`、`decimal_places` | `code` 唯一、大寫英數；小數位數 0～4 |
| `item_categories` | `code`、`name`、`parent_id`、`item_code_prefix` | `code` 唯一；頂層必有前綴（2～4 碼大寫英數）；有子分類／物料時不可刪 |

| 約束 | 規則 |
|---|---|
| `ix_items_request_no`、`ix_items_item_code` | 唯一（`item_code` 可多筆 NULL） |

| 檔案 | 作用 |

為什麼規則寫兩次（Domain＋資料庫）：Domain 讓使用者得到清楚的中文錯誤；資料庫保證就算有人用 psql 直接改資料、或日後程式寫錯，也不會存進違規資料。

EF 對應的兩個細節：
- 狀態與追蹤模式在 C# 是 enum，資料庫存文字（`HasConversion<string>()`）。
- 有資料庫預設值的欄位加了 `ValueGeneratedNever()`：EF 會把「等於 C# 預設值」的欄位省略不送，若不加，bool 預設 true 的欄位存 false 時會被資料庫改成 true。

### 3.7 常見修改
- 新增欄位：在 Domain 實體加屬性 → `Configurations` 設長度／約束 → 新增 Migration → 檢查產生的 SQL。新欄位要可為 NULL 或有預設值（Expand），舊版程式才能繼續運作。
- 新增內建單位或分類：改 `SeedData.cs` → 新增 Migration（不要改舊 Migration）。
- 改欄位長度、改名、刪欄位：屬於破壞性變更，依 `warehouse-db-migration` Skill 拆成 Expand → Migrate → Contract。
- 新增狀態或追蹤模式的值：先發布「能讀新值」的版本，確定不再回滾到舊版後，才開始寫入新值（舊版讀到不認得的文字會出錯）；修改 CHECK 可用 `NOT VALID` 再 `VALIDATE` 減少鎖表。
- M1-03 編輯畫面：版本號是 `xmin`（shadow property `Version`），編輯表單要把版本帶到前端、送出時設回 `Entry(item).Property("Version").OriginalValue`，樂觀併發才跨請求有效。

### 3.8 申請單號、正式料號與審核流程（M1-02）
**狀態流程**（規則在 `Item` 的方法，非法轉換丟 `DomainRuleException`）：
```text
提出 Submit ──> PendingApproval ──核准 Approve（發料號）──> Active <──停用／啟用──> Inactive
                 │   ^    │  │
          退回 Return │    │  └─拒絕 Reject（含判定重複）──> Rejected
                 v   │重送 │
                Returned ──撤回 Withdraw────────────────────> Rejected
```
- 待核准也可以撤回。已拒絕是終點（申請單號與紀錄保留）。
- 核准前可以改全部欄位。核准後分類一律不可改；基本單位、追蹤模式依 §3.11（ADR-0023）；料號依 §3.13（ADR-0025）；其他欄位可以改（`UpdateDetails`）。
- 誰可以做：核准、退回、拒絕、停用、啟用只限物料管理員；修改、重送限提出人或管理員；**撤回只限提出人**（管理員要不核准就用退回或拒絕，必須寫原因）；核准後的修改只限管理員。
- **提出是冪等的**：`SubmitAsync(requestId, …)` 的 `requestId` 由畫面開表單時產生，直接當物料 ID。逾時重送、連點時回傳第一次的申請單號，不會多一筆；別人用同一個 ID 會被拒絕（`item.request_id_conflict`）。其他動作有 xmin 版本保護，重送只會得到版本衝突，畫面應重新載入。

**號碼怎麼產生**（`src/Warehouse.Infrastructure/Items/ItemNumberGenerator.cs`）：
| 號碼 | 來源 | 併發 | 失敗時 |
|---|---|---|---|
| 申請單號 `MR-000125` | sequence `item_request_no_seq` 的 `nextval` | PostgreSQL 保證不重號 | 跳號（可接受） |
| 正式料號 `EL-000125` | `item_code_counters` 每個前綴一列：`INSERT … ON CONFLICT (prefix) DO UPDATE SET last_number = last_number + 1 RETURNING` | 該列鎖到核准交易結束，其他核准排隊 | 交易回滾，號碼一起退回（不跳號） |

- 子分類沒有前綴時，往上找第一個有前綴的分類（最多 8 層）。
- 退回、拒絕、撤回不碰計數器，所以不占料號。
- 就算計數器被手動改小，也不會重複發號：`ix_items_item_code` 唯一索引會讓核准失敗，而已發號的物料不能刪除（trigger）。
- D-32 起，核准時可以指定料號，自動發號遇到已被指定、或保留為歷史料號的號碼會往下跳（§3.13）。

**重複候選**（`ItemWorkflowService.FindDuplicateCandidatesAsync`）：
- 比對兩個欄位：
  - `normalized_part_no`：型號經 NFKC、轉大寫，再去掉空白與 `- . / _`。`MR-J4-10A` 和 `mr j4 10a` 視為相同。
  - `normalized_name`：品名經 NFKC、轉大寫，連續空白合併。
- 規則在 `src/Warehouse.Domain/Text/TextNormalizer.cs`；兩個欄位都有索引，最多回傳 50 筆。
- 比對範圍包含待核准、退回、有效、停用的物料，不含已拒絕的。
- 核准時：
  - 交易內會**重新查一次**候選，也重新確認分類與單位仍啟用。
  - 如果有候選不在 `acknowledgedCandidateIds`（核准者確認看過的清單）內，丟 `DuplicateCandidatesUnconfirmedException`，物料不會被核准。判斷用不限筆數的 `EXISTS`，不受顯示上限 50 筆影響；顯示時型號相同的排最前面。
  - 核准後的物料改品名或型號時（`UpdateAsync`），同樣要確認候選，否則兩筆有效物料可能變成重複。
  - 因為待核准的物料也算候選，兩筆重複的申請不論誰先核准，都會在另一筆核准時被擋下。所以不需要另外加鎖（測試 T-M1-02-11）。

**審核紀錄** `item_reviews`：
- 每個動作寫一筆：誰（`actor_id`＋名稱快照）、何時、從哪個狀態到哪個狀態、意見、發出的料號、重複於哪個物料。
- 只能新增：trigger `trg_item_reviews_append_only` 會拒絕 UPDATE 和 DELETE（23001）。
- 物料有紀錄後，因為外鍵是 RESTRICT，物料本身也刪不掉。

**一個動作怎麼執行**（`ItemWorkflowService.MutateAsync`）：
1. 開交易，讀物料。
2. 比對版本：呼叫端帶來的 xmin 跟目前不同，就丟 `ConcurrencyConflictException`。
3. 檢查權限。
4. 呼叫 `Item` 的方法改狀態。
5. 寫審核紀錄。
6. `SaveChanges`：UPDATE 帶 `WHERE xmin = 讀到的版本`，讀取之後才被別人改掉的情況也會擋下。
7. Commit。

例：同一筆物料被兩人同時核准時：
1. 第二人在計數器那一列等待。
2. 第一人 commit 後，第二人拿到下一號。
3. 第二人更新物料時版本不符，整個交易回滾，號碼一起退回。

**錯誤**（`src/Warehouse.Application/Errors/AppException.cs`，`ErrorCode` 是固定英文代碼）：
| 例外 | ErrorCode | 何時 |
|---|---|---|
| `NotFoundException` | `item.not_found` | 物料 ID 不存在 |
| `ConcurrencyConflictException` | `item.concurrency_conflict` | 版本不符（別人先改了） |
| `PermissionDeniedException` | `item.permission_denied` | 不是管理員、不是提出人 |
| `DuplicateCandidatesUnconfirmedException` | `item.duplicate_unconfirmed` | 核准時有未確認的候選（附 `Candidates`） |
| `DomainRuleException` | （M1-03 對應 `domain_rule`） | 非法狀態轉換、必填、格式、分類或單位已停用 |

**psql 除錯**：
```sql
SELECT action, from_status, to_status, item_code, comment, actor_name, occurred_at
  FROM item_reviews WHERE item_id = (SELECT id FROM items WHERE request_no = 'MR-000125') ORDER BY occurred_at;
SELECT * FROM item_code_counters ORDER BY prefix;          -- 各前綴最後發出的流水號
SELECT last_value FROM item_request_no_seq;                 -- 最後發出的申請單號
```

**測試**：
- `tests/Warehouse.UnitTests/Domain/ItemWorkflowTests.cs`：狀態機與修改限制。
- `TextNormalizerTests.cs`：正規化規則。
- `tests/Warehouse.IntegrationTests/ItemWorkflowTests.cs`：
  - 20 筆並行提出、20 筆並行核准（連號）、同一筆並行核准。
  - 不占號、重複候選、權限。
  - 審核紀錄不可修改。
  - 每個測試建立自己的分類（前綴 `Q001`…），料號從 000001 起算。

**常見修改**：
- 改料號格式：改 `ItemNumberGenerator.NextItemCodeAsync`，並同步改 `Item.ItemCodePattern` 和 CHECK `ck_items_item_code_format`（要新增 Migration）。
- 改重複比對規則：改 `TextNormalizer`，並新增 Migration 回填 `normalized_*`。回填 SQL 可參考 `M1_02_ItemWorkflow`。注意 SQL 回填只是**近似**規則：PostgreSQL 的 `upper()` 依資料庫 locale，與 C# `ToUpperInvariant` 對少數字元（如希臘字母）結果不同。M1-02 之前沒有經程式寫入的物料，所以目前沒有影響；日後若大量回填，應改用程式重算。
- **用 SQL 直接寫入有料號的物料時，必須同步更新 `item_code_counters`**（`last_number` 至少等於該前綴最大流水號），否則下次核准會撞到 `ix_items_item_code`（23505），核准失敗但不會重複發號。
- 正規化後的品名、型號長度上限 400 字（`Item.NormalizedMaxLength`），避免特殊字元展開後超過索引單列大小。

**API**（給手機／PDA 程式；網頁畫面不經過 API，直接呼叫同一組 Application 服務）：
```text
GET  /api/items?keyword=&status=&categoryId=&page=&pageSize=
GET  /api/items/{id}                          # 含 version（xmin）
GET  /api/items/duplicate-candidates?name=&partNo=&excludeItemId=
POST /api/items                               # {requestId, name, categoryId, baseUnitId, trackingMode, brand?, manufacturerPartNo?, specification?}
POST /api/items/{id}/approve                  # {version, acknowledgedCandidateIds?, comment?} → {itemCode}
POST /api/items/{id}/return                   # {version, comment}
POST /api/items/{id}/reject                   # {version, comment, duplicateOfItemId?}
```
- 錯誤一律是 ProblemDetails，`errorCode` 欄位見 §3.8 的錯誤表；`domain_rule` 是 400，衝突是 409（重複候選會附 `candidates`），權限是 403，找不到是 404。
- 列舉以文字傳遞（`"PendingApproval"`）。
- 寫入請求必須是 `Content-Type: application/json`，否則回 415（`JsonOnlyFilter`）。這是 API 不需要 antiforgery 的前提：跨站的 HTML 表單送不出 JSON。SameSite 不看埠號，同一台主機的其他網站算同站，不能只靠 SameSite。
- 帳號必須先改密碼時，API 回 403，`errorCode` 為 `auth.must_change_password`。

**請求怎麼走**（以「管理員在明細頁按核准」為例）：
1. 瀏覽器 POST `/Items/Details/{id}?handler=Approve`，表單帶 antiforgery token、`Version`、勾選的 `AcknowledgedIds`。
2. Cookie 驗證通過；`UseMustChangePassword` 確認不是「必須改密碼」的帳號；Razor 慣例確認有 `Items.Read`。
3. `DetailsModel.OnPostApproveAsync`：以 `User.ToActor()` 把登入身分轉成 `Actor`，呼叫 `IItemWorkflowService.ApproveAsync`。
4. `ItemWorkflowService` 檢查 `actor.IsItemManager`，再走 §3.8 的交易流程。
5. 成功時轉址回明細頁並顯示訊息（PRG，重新整理不會重送）；`DomainRuleException`、`AppException` 會顯示在頁面上。

**三層驗證各做什麼**：
| 層 | 位置 | 目的 |
|---|---|---|
| 畫面 | `Pages/Items/ItemForm.cs` 的 DataAnnotations、HTML `required`／`maxlength` | 立即提示，減少來回 |
| Domain | `Item`、`ItemCategory`、`Unit` 的方法 | 真正的規則；API 與畫面共用 |
| 資料庫 | CHECK、唯一索引、trigger（§3.2、§3.8） | 最後防線；手寫 SQL 也擋得住 |

**樂觀併發（表單帶版本）**：
- 明細、修改、分類、單位的表單都有隱藏欄位 `Version`，值是讀取當時的 `xmin`。
- 送出時服務會比對版本。若開表單之後別人先改過，畫面會顯示「已被他人修改，請重新載入」，不會蓋掉對方的修改。

**分類與單位規則**（`MasterDataService`）：
- 代碼不可改。不提供刪除，只能停用。
- 上層分類不可形成循環，例如把 A 移到自己的孫分類底下。最多 8 層，搬移時連同底下的子分類一起算。
- 修改分類樹時取 advisory lock `item_categories_tree`，兩人同時互設上層也不會形成循環。
- 前綴已發過料號（`item_code_counters` 有那一列）後不可修改或移除，也不能給其他分類使用。
- 核准發號時會取同一把鎖的「共享」模式（`AdvisoryLocks.LockCategoryTreeAsync`）：發號和修改前綴不會同時發生。
- 子分類原本沿用上層前綴時，可以改設自己的前綴或搬到別的上層；已發的料號不變，之後的新物料用新前綴。
- 單位已有物料使用時，不可改小數位數。

**登入與安全設定**（`src/Warehouse.Web/Security/IdentitySetup.cs`）：
- Cookie `Warehouse.Auth`：HttpOnly、Secure、SameSite=Strict，8 小時滑動到期。
- 連續 5 次密碼錯誤鎖 15 分鐘。
- 每 5 分鐘重新檢查 security stamp。
- `/api` 未登入回 401、無權限回 403。網頁轉址到登入頁只送**相對路徑**；經 YARP 代理時，絕對網址會指向內部槽位（127.0.0.1:5080）。
- 改密碼頁輸入錯誤的目前密碼也計入失敗次數，滿 5 次會鎖定並登出。
- 不需登入的頁面與端點列在 `Program.cs`（`AllowAnonymousToPage`）和 `DependencyInjection.MapWarehouseApi`（`AllowAnonymous`）。新增頁面時預設就要登入，不必另外設定。

**索引調整**（M1-01 審查 #11）：
- 移除 `ix_items_status`。
- 改為 `ix_items_updated_at`（清單預設排序）和 `ix_items_status_updated_at`（依狀態篩選，例如待核准清單，再依時間排序）。
- 品名、型號的部分比對（`ILIKE '%…%'`）用不到一般索引。資料量大時由 M2 的搜尋索引負責。

**常見錯誤**：
| 現象 | 原因 | 處理 |
|---|---|---|
| 登入後又回到登入頁 | 用 http 連內網 IP（非 localhost），Secure Cookie 不會被存 | 經代理的 `https://…:5443` 連線 |
| 一直被導到「改密碼」 | 帳號是初始或重設後的密碼 | 改完密碼即可 |
| API 回 401 | 沒帶 Cookie 或已過期 | 重新登入 |
| API 回 403 | 角色不足，或帳號必須先改密碼 | 確認角色（`users list`） |
| 「帳號已暫時鎖定」 | 連續 5 次錯誤 | 等 15 分鐘，或 `users reset-password` |
| `users create` 顯示 `PasswordRequiresUniqueChars` | 只有手動指定密碼時會發生；命令列產生的密碼不會 | — |
| 開發機 `users …` 找不到連線字串 | 沒設 `ASPNETCORE_ENVIRONMENT=Development`，所以沒讀 user-secrets | 依上方指令設定 |

### 3.10 物料功能程式導覽：DTO、驗證、錯誤碼與常見修改（M1-04）
> 給日後自己修改程式的人看：一個請求經過哪些檔案、資料在每一層長什麼樣子、要改功能時從哪裡下手。

#### 「提出物料」完整資料流
```text
瀏覽器表單 /Items/Create（Input.Name、Input.CategoryId…、隱藏欄位 RequestId、__RequestVerificationToken）
  │ POST
  ▼
Web   Pages/Items/Create.cshtml.cs  CreateModel.OnPostAsync
  │   ① ModelState：ItemFormInput 的 DataAnnotations（必填、長度）→ 有錯就重顯表單
  │   ② 還沒勾「仍要提出」→ IItemWorkflowService.FindDuplicateCandidatesAsync → 有候選就列出、停止
  │   ③ Input.ToDraft() 轉成 ItemDraft；User.ToActor() 把登入身分轉成 Actor
  ▼
Application  Items/ItemWorkflowContracts.cs  IItemWorkflowService.SubmitAsync(requestId, draft, actor)   ← 只有介面
  ▼
Infrastructure  Items/ItemWorkflowService.cs  SubmitAsync
  │   ④ 同一個 requestId 已存在 → 回傳原本的申請單號（冪等）
  │   ⑤ 開交易；分類、單位必須存在且啟用
  │   ⑥ ItemNumberGenerator.NextRequestNoAsync → nextval('item_request_no_seq') → MR-000125
  ▼
Domain  Items/Item.cs  Item.Submit(...)
  │   ⑦ 必填、長度、格式、追蹤模式、負庫存規則；計算 NormalizedName／NormalizedPartNo
  │      違規 → DomainRuleException（中文訊息）
  ▼
Infrastructure  db.Items.Add + db.ItemReviews.Add(ItemReview.Record(Submit…)) → SaveChanges → Commit
  ▼
PostgreSQL  items、item_reviews 的 CHECK／唯一索引／外鍵再檢查一次
  ▼
Web  TempData 訊息 → RedirectToPage("/Items/Details", id)（PRG：重新整理不會重送）
```
「核准」的流程見 §3.9「請求怎麼走」，交易內的步驟見 §3.8。API（`POST /api/items`）從 `ItemEndpoints.SubmitAsync` 進入，之後完全相同；錯誤由 `ApiExceptionHandler` 轉成 JSON。

#### 為什麼 DTO 和 Entity 分開
| 型別 | 位置 | 用途 | 為什麼不直接用 `Item` |
|---|---|---|---|
| `Item`（Entity） | Domain | 規則與狀態；屬性都是 `private set` | 只能透過方法改變，外面不能任意設定狀態或料號 |
| `ItemFormInput` | Web | 表單綁定（可為 null、有 DataAnnotations） | 表單會有半填的資料；直接綁 Entity 會讓使用者能送出 `Status`、`ItemCode` 等不該改的欄位（overposting） |
| `ItemDraft` | Application | 提出／修改的輸入 | 畫面與 API 共用同一個輸入格式 |
| `SubmitItemRequest` 等 | Api | JSON 請求 | API 契約要穩定；Entity 改欄位不能讓手機程式壞掉 |
| `ItemListRow`、`ItemDetails` | Application | 查詢結果 | 只投影需要的欄位（`AsNoTracking`＋`Select`），不載入整個 Entity、不會序列化出內部欄位；`ItemDetails.Version` 帶 xmin 給表單 |
| `DuplicateCandidate`、`CategoryRow`、`UnitRow` | Application | 清單用的精簡資料 | 同上 |

規則：**Entity 不離開 Infrastructure／Domain**。Web 與 Api 只看得到 DTO 和服務介面。分層測試（`LayerDependencyTests`）擋住 Application 引用 EF Core。

#### 驗證放在哪一層
| 規則 | 畫面（`ItemFormInput`） | Domain（`Item`） | 服務（`ItemWorkflowService`） | 資料庫 |
|---|---|---|---|---|
| 品名必填、長度 | ✓（提示） | ✓ | | `ck_items_name_not_blank`、varchar(200) |
| 分類、單位存在且啟用 | 下拉只列啟用的 | 不可為空 | ✓ 查資料庫 | 外鍵 |
| 狀態轉換 | 按鈕依狀態顯示 | ✓ | | `ck_items_code_matches_status`、trigger |
| 誰可以做 | 按鈕依角色顯示；頁面政策 | | ✓（`Actor`） | |
| 重複候選 | 列出 | | ✓ 核准、核准後改名 | |
| 料號唯一、不重新分配 | | 格式 | 計數器 | 唯一索引、trigger |
| 版本（併發） | 隱藏欄位 `Version` | | ✓ 比對 xmin | `UPDATE … WHERE xmin` |

原則：
- 畫面的驗證只是方便，一定要有伺服器端的對應。
- 需要查資料庫的規則（存在、重複、權限）放服務。
- 只看物件本身就能判斷的規則放 Domain。
- 資料庫是最後防線。

#### 錯誤碼總表
API 回應的 `errorCode`。網頁不回錯誤碼，直接顯示中文訊息。
| errorCode | HTTP | 來源 | 意義 |
|---|---|---|---|
| `domain_rule` | 400 | `DomainRuleException` | 輸入或狀態不符合規則（訊息說明哪一條） |
| `item.not_found` | 404 | `NotFoundException` | 物料（或指定的重複物料）不存在 |
| `item.permission_denied` | 403 | `PermissionDeniedException` | 角色或身分不符（例如非提出人撤回） |
| `item.concurrency_conflict` | 409 | `ConcurrencyConflictException` | 版本不符，請重新讀取 |
| `item.request_id_conflict` | 409 | 同上 | 提出用的 requestId 已被別人使用 |
| `item.duplicate_unconfirmed` | 409 | `DuplicateCandidatesUnconfirmedException` | 有未確認的重複候選；回應附 `candidates` |
| `category.not_found`、`unit.not_found` | 404 | `MasterDataService` | 分類、單位不存在（目前只有網頁會用到） |

| `auth.must_change_password` | 403 | `IdentitySetup.UseMustChangePassword` | 帳號要先在網頁改密碼 |

### 3.11 表單登錄條碼、自動核准、核准後改單位與追蹤模式（M8-05，ADR-0023）
#### 功能要解決的問題
- 建檔時就能把包裝上的原廠條碼一起登錄。
- 物料管理員自己建的物料可以送出就核准。
- 建錯單位或追蹤模式時能修正，但不能讓既有庫存的數量或批號對不上。

#### 資料流
```text
提出單（Create）──SubmitAsync(requestId, draft, ItemSubmitOptions)── 一個交易 ─┐
  1. SubmitAsync（原本的提出，BeginOrJoin 加入交易）                           │
  2. AddBarcodesAsync → ItemIndexService.AddAsync（待核准物料也可登錄條碼）      │ 任一步失敗
  3. AutoApprove：ApproveItemAsync（與手動核准共用：重複檢查、分類樹鎖、發號）     │ → 整筆回滾
  Commit ──────────────────────────────────────────────────────────────────┘
修改單（Edit）──UpdateAsync(…, ItemUpdateOptions)── MutateAsync 交易：
  核准後改單位／追蹤 → EnsureUnitTrackingChangeAllowedAsync（FOR UPDATE 鎖物料列 → 規則檢查 → 審核意見）
  → ApplyDraftAsync → 有條碼異動時先 SaveChanges，再停用／新增條碼 → 寫 item_reviews → Commit
```

#### 相關檔案
| 檔案 | 內容 |
|---|---|

| `Infrastructure/Items/ItemWorkflowService.cs` | `SubmitAsync` 新多載、`UpdateAsync` 新多載、`CheckUnitTrackingChangeAsync`、`EvaluateUnitTrackingChangeAsync`（規則）、`ReleaseBarcodesAsync`（拒絕或撤回時停用條碼） |
| `Infrastructure/Items/ItemIndexService.cs` | 條碼可登錄在待核准或退回的物料，但只限提出人或物料管理員；別名與關鍵字仍只限有效物料 |
| `Infrastructure/Inventory/InventoryPostingService.cs` | 過帳與預留取得 advisory 鎖後用 `FOR KEY SHARE` 重讀物料（`LoadItemsAsync(lockRows: true)`），逐筆檢查已核准、批號序號符合追蹤模式、小數位數 |

## 4. 搜尋別名：技術說明（M2）
設計決策見 ADR-0013；規格見 `docs/03`。

### 4.1 為什麼料號、別名、關鍵字分開
| 種類 | 範例 | 唯一性 | 命中時代表 |
|---|---|---|---|
| 正式料號 `items.item_code` | `EL-000125` | 全系統唯一，永不重新分配 | 就是這一個物料 |
| 專屬別名 `item_aliases` | 「J4-40B 維修備品」 | 有效的別名全系統唯一 | 只會對應一個物料 |
| 共用關鍵字 `item_keywords` | 「伺服AMP」 | 同一物料不重複，可掛多個物料 | 可能是其中幾個，要人選 |

- 如果把俗稱當成唯一識別碼，「伺服AMP」只能給一個物料，第二個物料就加不進去；如果把料號當成一般文字，又可能被誤判。所以三者分開存放、各自有不同規則。
- 共用關鍵字**永遠不會**被當成唯一識別。測試 `ItemIndexTests.共用關鍵字可掛多個物料_*` 確認同一個關鍵字可以掛在兩個物料上。

### 4.2 資料表與約束（Migration `M2_01_ItemAliasesKeywords`）
兩張表欄位相同：
- `id`、`item_id`、`text`（原文，用於顯示）、`normalized_text`（比對用）。
- `created_by_id`／`created_by_name`／`created_at`。
- `is_active`、`deactivated_by_id`／`deactivated_by_name`／`deactivated_at`。
- `xmin`（版本）。

| 約束 | 規則 |
|---|---|
| `ux_item_aliases_active_normalized_text` | 有效別名的 `normalized_text` 全系統唯一（`WHERE is_active`） |
| `ux_item_keywords_active_item_text` | 同一物料的有效關鍵字不重複 |
| `ix_item_keywords_normalized_text`、`ix_item_aliases_item_id` | 搜尋與明細頁查詢用 |
| `ck_*_text_not_blank`、`ck_*_deactivation` | 不可空白；「有效」與「沒有停用資訊」一致 |
| trigger `trg_item_aliases_protect`、`trg_item_keywords_protect`（函式 `item_index_protect()`） | 禁止刪除、禁止改 id／文字／物料／建立者、禁止把已停用改回有效、禁止改寫已停用紀錄的停用者與時間（23001） |
| trigger `trg_*_no_truncate` | 禁止 `TRUNCATE` 整批清除 |

**`NormalizedText` 的用途**：
- 使用者輸入的寫法各式各樣，例如「ｓｅｒｖｏ　Amp」「Servo  AMP」。
- `TextNormalizer.Normalize` 統一處理：NFKC（全形轉半形）、轉大寫、移除零寬空白等看不見的字元、合併空白，結果都是「SERVO AMP」。
- 移除看不見的字元是為了防止外觀相同的別名重複建立，例如在「伺服AMP」中夾一個零寬空白。
- 唯一約束與搜尋比對都用正規化後的文字；畫面一律顯示原文 `text`。

**為什麼別名的唯一要靠資料庫**：
- 程式先查詢「有沒有人用過」再寫入，兩人同時送出時，兩邊都會查到「沒有」。
- 部分唯一索引讓資料庫只接受第一筆。`ItemIndexService.AddAsync` 捕捉 23505 後重新查詢，回報被哪個料號占用。
- 測試 `二十個物料同時新增同一個專屬別名_*` 驗證只有一筆成功。

### 4.3 新增「伺服AMP」時資料怎麼走
1. 物料明細頁 `/Items/Details/{id}` 的「搜尋索引」表單，以 POST 送到 handler `AddIndex`（`DetailsModel.OnPostAddIndexAsync`）。
2. 呼叫 `IItemIndexService.AddAsync(itemId, Keyword, "伺服AMP", actor)`，實作在 `src/Warehouse.Infrastructure/Items/ItemIndexService.cs`。
3. 開交易，`SELECT … FOR UPDATE` 鎖住物料那一列：同一物料的新增會排隊，物料也不會在檢查後被停用。物料必須是有效狀態。
   - 每個物料最多 20 筆有效別名、100 筆有效關鍵字（`index.limit_exceeded`）。
4. Domain：`ItemKeyword.Create` 檢查長度與空白、做正規化、拒絕料號格式。檔案在 `src/Warehouse.Domain/Items/ItemIndexEntry.cs`。
5. `EnsureNoConflictAsync` 檢查兩件事：
   - 別名：是否已被其他物料占用。
   - 本物料是否已有相同文字：別名或關鍵字都算。想把關鍵字「升級」成別名時，要先停用那個關鍵字。
6. `SaveChanges`；資料庫的唯一索引做最後把關。
7. 轉址回明細頁，表格顯示這個關鍵字目前「使用中料號數」。

API 用法相同：
- 查詢：`GET /api/items/{id}/index`，物料不存在時回 404。明細頁與 API 都只回有效索引，加上最近 50 筆已停用的。
- 新增：`POST /api/items/{id}/keywords`（或 `/aliases`），本文 `{"text":"伺服AMP"}`。
- 停用：`POST /api/items/{id}/keywords/{entryId}/deactivate`，本文 `{}`。
- 網頁的新增、停用 handler 會在伺服器端再檢查 `Items.Index` 政策，和 API 相同。

**錯誤碼**：
| 錯誤碼 | HTTP | 意義 |
|---|---|---|
| `index.alias_taken` | 409 | 別名已被其他物料使用，附 `holderItemId`、`holderLabel`；畫面提供「改加為共用關鍵字」 |
| `index.duplicate` | 409 | 本物料已有相同的別名或關鍵字 |
| `index.limit_exceeded` | 409 | 超過每個物料的有效索引上限 |
| `index.item_not_active` | 409 | 物料不是有效狀態 |
| `index.not_found` | 404 | 索引不存在 |
| `index.permission_denied` | 403 | 不是建立者，也不是管理員 |

**除錯 SQL**：

```sql
  FROM item_keywords WHERE item_id = (SELECT id FROM items WHERE item_code = 'EL-000125') ORDER BY created_at;
SELECT i.item_code, i.name FROM item_keywords k JOIN items i ON i.id = k.item_id
```

### 4.4 搜尋：排序、命中原因、限制（M2-03）
**入口**：
- 網頁：`/Search`，導覽列「搜尋」。
- API：`GET /api/search?q=&includeInactive=&page=&pageSize=`。
- 兩者都呼叫 `IItemSearchService.SearchAsync`，實作在 `src/Warehouse.Infrastructure/Search/ItemSearchService.cs`。

**比對前的處理**：
- 查詢字串截到 100 字，用 `TextNormalizer.Normalize` 正規化。
- 依空白拆成詞，最多 5 個（`ItemSearch.SplitTerms`）。單一英數或符號（如「A」「-」）不做部分比對，否則幾乎每筆都會比中；單一中文字（如「閥」）保留。被略過的詞會在搜尋頁上方提示。
- 另外算一個「去符號型號」（`NormalizePartNo`），讓 `mr j4 40b` 能找到 `MR-J4-40B`。

**排序**（同一物料取最優先的一層；同層依料號排序）：
| 層 | 條件（SQL） | 命中原因（`HitReason`） |
|---|---|---|
| 1 | `item_code = q` 或 `request_no = q` | 料號／申請單號 |
| 2 | 有效別名 `normalized_text = q` | 專屬別名 |
| 3 | `normalized_part_no = 去符號(q)` 或 `normalized_name = q` | 型號／品名 |
| 4 | 有效關鍵字 `normalized_text = q` | 共用關鍵字 |
| 5 | 每個詞都 `LIKE %詞%` 出現在料號、品名、品牌、型號、規格、有效別名或有效關鍵字其中之一（品牌、規格比對正規化欄位 `normalized_brand`／`normalized_specification`，全形「ＤＣ２４Ｖ」也能用「24V」查到） | 部分符合（列出比中的欄位） |

**一句 SQL**：
- WHERE 是「第 1～4 層任一成立」OR「每個詞都部分符合」，同一個條件組合也用來算總筆數。
- 別名、關鍵字的精確比對寫成 `item_id IN (SELECT … WHERE normalized_text = q)`，PostgreSQL 可以先用索引找出少數幾筆，不必對每個物料各跑一次子查詢。
- ORDER BY 用 `CASE WHEN … THEN 1 …` 算出層級；`CASE` 與 WHERE 的精確條件要逐項一致。
- 多詞條件用 Expression 組合（`AllTermsMatch`、`Combine`），EF 會轉成參數化 SQL，沒有字串拼接。
- 「哪個別名、哪些欄位比中」只對當頁 ≤ 50 筆在記憶體中計算（`DescribePartial`）。

**限制**（docs/03 §8、§9）：
- 每頁 20 筆、最多 50。
- 預設只找有效物料，勾「包含停用」才會列出停用物料；待核准、已拒絕的永遠不會出現。
- 限流：每位使用者每分鐘 60 次，網頁與 API 共用。可用設定 `Search:RateLimitPerMinute` 調整。
  - 超過時 API 回 429，`errorCode` 為 `search.rate_limited`，`Retry-After` 是這個視窗剩下的秒數；網頁顯示「請 N 秒後再試」和回搜尋的連結。
  - 開啟搜尋頁或加索引頁本身（即使還沒輸入）也算一次。
  - 計數存在每個執行中的程式的記憶體：A/B 切換期間兩個槽位各自計數，上限暫時最多變成兩倍（`docs/11` §10）。
- 按「搜尋」才查詢，不做邊打字邊查。

**搜不到時**（M2-04，情境 F）：
1. 搜尋頁下方有「把『q』加為既有物料的搜尋索引」，連到 `/Search/AddIndex?text=q`，需要 `Items.Index` 權限。
2. 在這頁用另一個條件找目標物料，點「選這個」。
3. 到物料明細頁時文字已預填（`?indexText=`），看過規格後按「新增」。
- 這個流程**不能建立物料**（情境 H）。新物料只能走 `/Items/Create` 的審核流程。

**重複候選**：
- 新物料的品名等於某物料的有效專屬別名時，也會列為候選，原因顯示「別名相同」。
- 共用關鍵字不比對（ADR-0013 決策 8）。

**常見修改**：
| 想做的事 | 改哪裡 |
|---|---|
| 調整排序層級 | `ItemSearchService.SearchAsync` 的 `exact` 條件與 `Tier` 的 `CASE`（兩處要一致），以及 `HitReason` |
| 部分比對多查一個欄位 | `AllTermsMatch` 與 `DescribePartial` |
| 改每頁筆數、字數或詞數上限 | `Application/Search/ItemSearchContracts.cs` 的 `ItemSearch` |
| 改限流 | 設定 `Search:RateLimitPerMinute`；程式在 `Api/Endpoints/SearchEndpoints.cs` |
| 命中原因的中文 | `Web/Display.cs` |

## 5. 出庫交易：技術說明與除錯手冊（M4-06）
程式細節見 §16（過帳服務）、§17（單據）、§19（預留）、§20（異常追蹤）；決策見 ADR-0004「併發控制」、ADR-0014、ADR-0015。

### 5.1 為什麼「先查到有 10 件」不足以避免兩人同時出庫？
```text
時間  甲（出 7）                  乙（出 7）
t1    SELECT 結存 → 10 ✔
t2                                SELECT 結存 → 10 ✔   ← 甲還沒寫入，乙看到的仍是 10
t3    UPDATE 結存 = 3
t4                                UPDATE 結存 = -4 ✘   ← 超賣
```
「查」和「寫」之間有空檔，別人可以插進來。本系統的做法：
1. 先取「料號＋倉庫」的 advisory lock：同料同倉的扣減與預留排隊，乙要等甲 commit 才拿得到鎖。
2. **寫入之後**才在同一交易用新語句檢查可用量（READ COMMITTED 下新語句看得到甲已 commit 的結果），不足就丟例外、整筆回滾。
3. 資料庫再加一層：不允許負庫存的物料，結存變負由 trigger `trg_stock_balances_floor` 擋下（就算有人繞過程式直接寫也一樣）。
- 驗證：`PostingTests.並行出庫20筆_結存10_恰好10筆成功`、`PostingHardeningTests.兩張出倉單同時送審_只有一張成功`。

### 5.2 哪裡用到交易、條件式更新、資料列鎖？
| 位置 | 機制 | 為什麼 |
|---|---|---|
| `StockDocumentService.IdempotentCoreAsync` | `BEGIN` … `COMMIT`；`SELECT … FROM stock_documents FOR UPDATE` | 同一張單同時只有一個人在確認／核准 |
| `StockDocumentService.PostCoreAsync` | 儲位依 id `FOR UPDATE` | 過帳期間儲位不會被停用；同一結存列的寫入者先搶同一把儲位鎖 |
| `InventoryPostingService.ApplyCoreAsync` | 倉庫 `FOR SHARE`、`pg_advisory_xact_lock(料號＋倉庫)`（依鍵值排序）、預留 `FOR UPDATE`、`INSERT … ON CONFLICT DO UPDATE` 批次 upsert | 排隊、避免死結、原子更新結存 |
| 可用量檢查 | 寫入後的新語句（post-check） | 看得到排在前面已 commit 的交易 |
| `ReserveManyAsync` | 倉庫 `FOR SHARE` → advisory（全部鍵一次排序） | 預留與出庫互斥；多料號預留不會和過帳互相等待 |
| `ExpireDueReservationsAsync` | `FOR UPDATE SKIP LOCKED`、`LIMIT 500` | 背景工作不等鎖、不擋過帳 |
| `SetAsync`（負庫存設定） | 料號 advisory → `items FOR UPDATE` | 與造成負數的出庫排隊 |
- 每個交易 `SET LOCAL lock_timeout = '5s'`：等不到鎖或死結時回 `stock.busy`，交易回滾，使用者重按即可。
- 鎖順序固定（§16.5）：新程式要取鎖，必須插在這個順序裡，否則可能死結。

### 5.3 為什麼 Movement 與 Balance 要同一次提交？
結存（`stock_balances`）是「目前有多少」，異動帳（`stock_movements`）是「怎麼變成這樣」。兩者分開提交時，中間當機就會出現「結存變了卻沒有異動」或相反，之後對帳永遠對不起來，也無法追查。本系統：
- 結存、異動帳、單據狀態、預留沖銷、稽核、冪等紀錄全部在**同一個交易**，任何一步失敗全部回滾（`PostingHardeningTests.中途失敗_整筆回滾不留痕`）。
- 異動帳只能新增（trigger），更正用沖銷單。
- 對帳 SQL 見 §14.4 第 4 段（結存應等於異動加總，正常沒有任何一列）。

### 5.4 HTTP 逾時但後端其實成功了，怎麼避免重試扣第二次？
- 畫面開表單時產生一個冪等鍵（隱藏欄位 `IdempotencyKey`；API 用 `Idempotency-Key` 標頭）。重送同一個表單＝同一個鍵＋同一個版本。
- 後端在**同一交易**寫入 `processed_commands(key, command_type, request_hash, result_ref)`。同一個鍵再來時：
  - 內容相同（命令＋單據＋版本＋操作者的雜湊相同）→ 直接回成功，不再過帳。
  - 內容不同 → `idempotency.key_reused`（409），不會覆蓋原請求。
- 兩個同鍵請求同時到：鎖住單據後再查一次冪等紀錄，後到的看到先到的結果。
- 建單用請求 ID 當單據 ID；預留建立也有冪等鍵。
- 實測：API 同鍵並行 5 次只過帳一次（T-M4-06-05）；**A/B 切換期間連續出庫，同鍵重試，無遺失、無重複**（T-M4-06-06，`docs/11` §10）。

### 5.5 從追蹤碼（RequestId）查到失敗的請求與交易
1. API 錯誤回應有 `errorCode` 與 `traceId`；頁面錯誤訊息顯示中文原因。
2. 被拒的送審／確認／核准／建立預留會寫 `stock_posting_failures`（交易已回滾，另一條連線寫入）：
   ```sql
   SELECT occurred_at, actor_name, command, doc_no, error_code, message
     FROM stock_posting_failures WHERE trace_id = '<traceId>';        -- 或 WHERE doc_no = 'OUT-000123'
   ```
   畫面：`/Stock/Anomalies?tab=failures`。
3. 日誌以同一個 TraceId 搜尋（`C:\Warehouse\logs\` 或 Windows 事件檢視器）。
4. 單據層面：`SELECT * FROM audit_logs WHERE entity_id = '<單據 id>' ORDER BY occurred_at;`；冪等：`SELECT * FROM processed_commands WHERE result_ref = '<單據 id>';`。

## 6.1 內網 HTTPS 與相機掃碼（M0-05）
### 功能要解決的問題
手機瀏覽器只在「安全內容」（HTTPS 或 localhost）允許使用相機。公司內網沒有公開網域，所以自建一個內部 CA（憑證機構），由它簽發伺服器憑證，再讓電腦與手機信任這個 CA。

### 憑證架構
```text
Warehouse Dev Root CA（根憑證，5 年，私鑰只在開發者 Windows 帳號的憑證存放區，不可匯出）
  └─ 簽發 → 伺服器憑證 CN=DESKTOP-FMD51FK（397 天）
             SAN：DESKTOP-FMD51FK、localhost、192.168.0.86、127.0.0.1
             ↓ 匯出 %LOCALAPPDATA%\Warehouse\certs\warehouse-dev-server.pfx（隨機密碼）
Kestrel 讀 user-secrets：Kestrel:Certificates:Default:Path／Password
手機／電腦信任 warehouse-dev-root-ca.cer → 瀏覽器不再警告 → 可使用相機
```
- 397 天與 SAN／EKU 欄位：iOS 對 TLS 憑證有效期與欄位有限制，太長或缺 SAN 會被拒絕。
- 為什麼不直接用 `dotnet dev-certs`：它只簽 `localhost`，手機用 IP 連線時會不符。

### 相關檔案
| 檔案 | 用途 |
|---|---|
| `scripts/new-dev-certs.ps1` | 建立根 CA（已存在則沿用）、簽發伺服器憑證、信任根 CA、寫入 user-secrets；`-Remove` 全部移除 |
| `scripts/open-dev-firewall.ps1` | 開放 TCP 5443（只限「私人」網路設定檔）；需要系統管理員，會自動跳 UAC；`-Remove` 移除 |
| `src/Warehouse.Web/Properties/launchSettings.json` | `lan` profile：`https://0.0.0.0:5443;http://localhost:5046` |
| `src/Warehouse.Web/Pages/Dev/DevPageModel.cs` | 開發用頁面基底：非 Development 環境一律 404 |
| `src/Warehouse.Web/Pages/Dev/Ca.cshtml(.cs)` | `/dev/ca`：手機下載根 CA＋安裝步驟 |
| `src/Warehouse.Web/Pages/Dev/Camera.cshtml(.cs)` | `/dev/camera`：診斷安全內容、解碼器，按鈕才 `import()` 相機模組 |
| `src/Warehouse.Web/wwwroot/js/camera-scan.js` | 相機模組：BarcodeDetector 優先、jsQR 備援，每 200 ms 解碼；`/dev/camera` 讀到即停止，M5 面板用連續模式（§6.2） |

### 本機操作
```powershell
.\scripts\new-dev-certs.ps1          # 第一次會跳出 Windows「安全性警告」，按「是」
.\scripts\open-dev-firewall.ps1      # 跳出 UAC，按「是」
dotnet run --project src/Warehouse.Web --launch-profile lan
# 手機（同一個 Wi-Fi）開 https://192.168.0.86:5443/dev/ca 依頁面步驟安裝根憑證

```

### 相機模組重點（`camera-scan.js`）
- **延遲載入**：頁面只有一小段診斷程式；按下「開始」才 `import('/js/camera-scan.js')`，它再載入 `camera-decoder.js` 與解碼器。鍵盤／條碼槍掃碼頁完全不載入（T-PERF-05）。
- **解碼器選擇**（2026-10-30 起，`camera-decoder.js`）：內建 `BarcodeDetector` 同時支援 `qr_code`、`ean_13`、`code_128` 才用（Android Chrome）；否則載入本機 zxing-wasm（iPhone、Windows，QR＋一維碼）；WASM 載入失敗退回 jsQR（只讀 QR）。詳見 §6.2「相機入口與一維碼」。
- **省電**：每 200 ms 解碼一次；影格縮到最長 640 px（jsQR）／960 px（zxing-wasm，一維碼線條細）。
- **釋放相機**：讀到結果、按停止、`visibilitychange` 變 hidden、`pagehide` 時呼叫 `track.stop()`，手機相機指示燈應熄滅。
- iPhone 需要 `<video playsinline muted>`，否則會跳全螢幕播放。

### 風險
- 信任此根 CA 的裝置，會信任它簽發的**任何**憑證；根 CA 私鑰設為不可匯出、只存在開發者帳號中。測試結束可用 `-Remove` 及手機設定移除。
- 正式環境的 CA 與內網網域（D-09、D-27）在 M7 決定，不沿用開發用 CA。

### 常見錯誤與查找
| 現象 | 原因 | 處理 |
|---|---|---|
| 腳本錯誤「此作業不允許 UI」 | 從非互動環境（IDE、AI 工具）直接匯入受信任根憑證 | 腳本已改為另開視窗匯入；若視窗被擋住，在工作列找「安全性警告」 |

| 相機頁顯示「安全內容：否」 | 用 http 或 IP 不在憑證 SAN 內 | 改用 `https://`；IP 改變時重跑 `new-dev-certs.ps1` |
| `NotAllowedError` | 使用者拒絕相機權限 | 頁面會顯示重新允許的步驟 |
| 在 LINE 裡點連結打不開 | LINE 等 App 的內建瀏覽器不信任自建憑證、也常不給相機 | 用 Safari／Chrome 開（M0-05 實測） |
| 條碼槍掃中文變亂碼，或兩筆黏成一筆 | 鍵盤模擬只能送鍵盤上有的字；中文的 UTF-8 位元組被當成按鍵 | 條碼只用英數（D-28）；新設備可試 Unicode 模式並用 `/dev/scanner` 測 |

| 條碼槍送出全小寫 | 電腦開著大寫鎖定 | 不影響系統比對（D-29）；`/dev/scanner` 會顯示「大寫鎖定：開」 |

### 條碼槍與 PDA 實測步驟（M0-05）

## 6.2 三種設備掃碼（M5，2026-10-22～23，ADR-0016）
### 功能要解決的問題
倉管人員用 USB 條碼槍（電腦）、Android PDA（Keyboard Wedge）或手機相機掃儲位、物料，一筆接一筆加入單據明細，不能掉字、不能重複、不能掃到錯的物料。沒有條碼時，搜尋＋點選仍然能完成全部作業（ADR-0003）。

### 資料流
```text
條碼槍／PDA（鍵盤＋Enter／Tab）─┐
手機相機（camera-scan.js）───────┴→ scan-input.js 佇列（一次處理一筆、照順序）
                                     │  GET ?handler=ScanResolve&code=…（單據、期初）或 /Scan?code=（查料）或 /api/scan
                                     ▼
              ScanInput（去尾碼、過短拒絕）→ ScanCodeParser（WH:LOC／WH:ITEM／其他）
              → ScanResolver：儲位 QR → 料號 → 原廠條碼 → 專屬別名 → 指定倉庫的儲位碼 → 其他文字（只做精確比對）
                                     │ JSON（kind、location、item 含包裝數量、IsActive）
                                     ▼
              doc-scan.js 依步驟填欄位 → 欄位齊了：跳數量欄／序號自動加入／逐件累加
                                     │ POST ?handler=ScanAddLine（JSON＋RequestVerificationToken）
                                     ▼
              StockDocumentService／OpeningService.AddLineAsync（MergeIfSame）→ 回傳重繪的明細表（不重新載入頁面）
```
加入明細只寫草稿，不動庫存；過帳仍要按「確認過帳」，走 `InventoryPostingService`。

**表單相機資料流**
```text
按「相機掃碼」→ import camera-scan.js（帶 ?v=，_Layout 的 meta wh-camera-scan-v）→ start(continuous)（先停掉頁面上其他相機）
 → 讀到一筆（同一碼要離開畫面 1.5 秒才再算）→ 依序處理（working 佇列）→ 寫到「當前欄」：
   item     /api/scan → 物料才填（停用、外箱依規則）；儲位／查不到 → 放錯欄提示
   location /api/scan(warehouseId) → 儲位才填；物料 → 放錯欄提示
   raw      /api/scan → 已登錄的物料／儲位（含 WH: QR）是放錯欄；否則填原文（條碼列不重複）
   item-search 物料碼 → 填料號並送出搜尋；否則只填原文

   沒有空白欄 → 焦點移到 data-scan-next 或數量欄，相機目標不變（逐件累加時目標回到料號欄）

```

**數量方式（盤點、建立預留）**：表單內 `<select data-camera-qty-mode="stocktake.qtyMode|reservation.qtyMode">`，記在帳號常用設定（`UserPreferenceKeys`）。料號欄 `data-camera-qty="<數量欄 id>"`。
| 方式 | 行為 |
|---|---|
| manual 手動（預設） | 外箱條碼拒絕；數量由人輸入；序號物料帶 1 |
| pack 帶入包裝量 | 接受外箱條碼；數量＝包裝量（單件 1） |
| each 逐件累加 | 同一物料每掃一次加一個包裝量；數量 > 0 時掃到別的物料不填，提示先按記錄／建立 |

**幫新表單加相機**：在 `<input>` 加 `data-camera-field="item|location|raw|item-search"`（選填見 `camera-field.js` 開頭註解），頁面 `Scripts` 區依序載入 `scan-input.js`、`scan-field.js`、`camera-field.js`。JS 會把欄位包進 `.camera-field`（表單格線不會亂），按鈕列放在第一個相機欄位所在區塊前面；要指定位置就在表單內放 `<div data-camera-bar></div>`。整塊換掉的 HTML 要呼叫 `window.WhCameraField.enhance(新區塊)`，換掉前呼叫 `release(舊區塊)`。
**碼制與輸出**：QR、EAN-13、EAN-8、UPC-A、UPC-E、Code 128、Code 39、Code 93、ITF、Codabar（另含 Data Matrix）。文字一律字串、不轉數字。
⚠ zxing-wasm（iPhone、Windows）把 **UPC-A 輸出成 13 碼**（前面補 0，碼制顯示 EAN-13）、**UPC-E 展開成 13 碼**；Android 內建與多數條碼槍是 12／8 碼。使用者決定這次不轉換（計畫 4A），同一個 UPC 商品用不同設備登錄可能對不到；遇到時先在物料頁看登錄的是哪一種長度。台灣商品多為 EAN-13（471 開頭），不受影響。

**效能（2026-10-30，tools/DecodeCheck，Chromium 109、Windows 11、Ryzen 9 8940HX、15 GB RAM）**：zxing 下載 961 KB（未壓縮，Service Worker 以 `?v=3.1.6` 快取）、初始化約 60 ms、每格解碼 5～22 ms（200 ms 一次）。舊電腦與手機實機未量。

**換 zxing-wasm 版本**：`npm pack zxing-wasm@<版本>` → 換 `lib/zxing-wasm` 兩個檔案 → 改 `camera-decoder.js` 的 `ZXING_VERSION` 與 `VERSION.txt`（版本、雜湊）→ 跑 `tools/DecodeCheck`。

**除錯**
| 現象 | 原因 | 處理 |
|---|---|---|
| 按「相機掃碼」旁顯示「目前不是安全連線」 | 用 http 或 IP 不在憑證內 | 改用 https（§6.1） |
| 欄位下方「這一欄是○○，沒有填入」 | 掃到的碼類型和當前欄不符 | 先點要填的欄位再掃（相機不用關） |
| 送出後相機沒有自動開 | 瀏覽器要求手勢或權限被收回 | 按鈕旁會提示，按「相機掃碼」繼續 |
| 相機狀態「掃描中（只讀 QR）」 | zxing-wasm 載入失敗，退回 jsQR | F12 → Network 看 `/lib/zxing-wasm/*.wasm` 是否 404 或 MIME 不是 `application/wasm` |
| 「畫面有多個條碼，請只對準一個」 | 同一格讀到兩個不同的碼 | 靠近或遮住其他條碼；不會自動選一個 |
| 兩個碼並排，其中一個太小 | 解碼器只讀得到一個，會當成單一碼 | 多碼偵測只對讀得到的碼有效，掃前仍要對準 |
| 掃到了但欄位顯示「外箱條碼…」 | 數量方式是「手動」時數量是基本單位，外箱碼不換料號（與鍵盤同規則） | 掃單件條碼、輸入料號，或把數量方式改成帶入包裝量／逐件累加；庫存查詢欄允許外箱碼 |
| 盤點儲位欄「別的倉庫」 | 儲位 QR 不是本盤點單的倉庫 | 正確，伺服器 `/api/scan?warehouseId=` 拒絕 |
| 換版後手機還在用舊相機程式 | 舊頁面還開著 | 重新整理；模組網址帶 `?v=` 版本 |

### 9.1 前端比較量測工具（M0-08）
`poc/` 是獨立於正式程式的比較實驗（不在 `Warehouse.slnx` 內），用來回答「哪種前端在舊電腦與 Chrome 109 上最輕、最穩」。

```text
poc/
├─ CONTRACT.md          # 兩個 PoC 必須相同的網址與 DOM id（量測腳本靠它通用）
├─ Poc.Shared/          # FakeItemCatalog：固定種子產生 20,000 筆料號，伺服器端搜尋分頁
├─ Poc.RazorPages/      # port 5101；掃碼用 wwwroot/js/scan.js（JS 佇列＋fetch /api/items/{code}）
├─ Poc.BlazorSsr/       # port 5102；/scan 用表單送出、/scan-js 用同一份 scan.js
├─ Poc.BlazorWasm/      # 空白範本，只量首次載入
├─ Poc.Bench/           # Playwright 量測程式（Program.cs 的 Scenarios 類別＝各量測情境）
├─ publish-all.ps1      # 以 Release 發布三個 PoC 到 .publish/
└─ results/             # 量測輸出 JSON
```

**重跑量測**
```powershell
cd poc
.\publish-all.ps1                                         # 修改 PoC 後一定要重新發布
dotnet run --project Poc.Bench -c Release -- --quick      # 快速版（約 3 分鐘），確認腳本能跑
dotnet run --project Poc.Bench -c Release                 # 正式版（約 15 分鐘）
dotnet run --project Poc.Bench -c Release -- --target razor-pages --browser chromium-109   # 只跑一組
```
瀏覽器：Playwright 內建新版 Chromium（`playwright.ps1 install chromium` 安裝到 `%LOCALAPPDATA%\ms-playwright`），以及 `poc/.browsers/chromium-109/`（Chromium 官方快照 revision 1070054＝109.0.5414.0，不進 Git）。

**各指標怎麼讀**
| 欄位 | 意義 | 怎麼量 |
|---|---|---|
| `firstLoadSearch.transferKb` | 第一次開頁面（無快取）網路傳輸量 | Playwright `Request.SizesAsync()` 加總 |
| `searchLatency.p50Ms/p95Ms` | 按 Enter 到結果出現的時間 | 送出前在頁面放標記元素，等它消失且 `#total-count` 存在 |
| `scan.lostOrGarbled` | 50 筆連續掃碼（每字 10 ms）中遺失或變形的筆數 | 比對清單內容與送出的料號 |
| `idleCpu.cpuPercent` | 頁面閒置時瀏覽器主執行緒忙碌比例 | CDP `Performance.getMetrics` 的 `TaskDuration` 差值 |
| `longRunMemory` | 300 次查詢前後 JS 記憶體與 DOM 節點數 | 先強制 GC，再取 `JSHeapUsedSize`、`Nodes` |
| `serverMemory:*` | 伺服器程序記憶體（影響 NAS 與 A/B 雙實例） | `Process.WorkingSet64` |

- **CPU 節流 4 倍**：用 CDP `Emulation.setCPUThrottlingRate` 讓瀏覽器跑慢 4 倍，近似舊電腦；只是模擬，實機結果仍以 M7-11 為準。
- 量測腳本所有情境都包在 `Safe()` 裡：某一項失敗（例如舊瀏覽器不相容）會記錄錯誤訊息而不中斷，結果檔中看到 `error` 欄位即代表該項失敗。

**量測過程學到的陷阱（之後寫正式畫面時要注意）**
- 用「表單送出」做掃碼，伺服器回應會把輸入框重設為空白，條碼槍在回應前已輸入的下一筆字元會被吃掉（實測 50 筆遺失 44 筆）。掃碼一律用 JS 佇列：Enter 時取值、立刻清空、背景依序查詢。
- Blazor enhanced form／navigation 不是整頁導覽：回應抵達前使用者輸入的內容會被覆蓋；以 enhanced navigation 進入的頁面，頁面內 `<script>` 不會執行。

## 10. Windows PC 部署與維護教學（M0-10 PoC，2026-10-21 實測）
> 本節的服務只聽 `http://localhost:<埠>`；對外 HTTPS、反向代理與 A/B 切換見 §12。設計理由見 ADR-0008。

### 伺服器目錄（`C:\Warehouse`，可用 `-Root` 改）
```text
C:\Warehouse\
├─ releases\0.1.0-e2a5f49-win-x64-fdd\   # 每個版本一個資料夾，永不覆寫；回滾＝讓服務指回舊資料夾
├─ config\appsettings.Production.json    # 連線字串等；只有 Administrators、SYSTEM、服務帳號能讀
```

### 1. 發布（`scripts/publish.ps1`）
```powershell
.\scripts\publish.ps1 -Runtime win-x64                 # framework-dependent（伺服器需安裝 ASP.NET Core Runtime 10）
.\scripts\publish.ps1 -Runtime win-x64 -SelfContained  # 自含 Runtime
```
- 先檢查工作目錄乾淨（版本號含 commit），再跑全部測試，再 `dotnet publish -c Release -r <RID>`。
- 輸出 `artifacts\publish\<版本>-<commit7>-<RID>-<fdd|sc>\`（不進 Git），內含 `release.json`（版本、commit、RID、部署型式、檔案數、大小）。
- 實測：framework-dependent **37 檔、7.7 MB**；self-contained **367 檔、112.9 MB**。

### 2. 安裝成服務（`scripts/windows/install-service.ps1`）
```powershell
# 第一次安裝：先把連線字串寫進只有自己能讀的暫存檔，腳本讀取後會刪除（避免密碼出現在命令列）
.\scripts\windows\install-service.ps1 -ReleasePath artifacts\publish\<版本資料夾> -ConnectionStringFile <暫存檔> -VerifyRestart
```
預期輸出：
```text
已複製版本：C:\Warehouse\releases\...
已建立設定檔（連線字串不顯示）。
已建立服務 WarehouseA（帳號 NT SERVICE\WarehouseA，埠 5080）
服務已就緒：http://localhost:5080/health/ready = 200
重新啟動驗證：1.2 秒後恢復就緒
狀態：Running；帳號：NT SERVICE\WarehouseA；啟動類型：Auto；PID ...；記憶體 94 MB
```
腳本做的事：
- **虛擬服務帳號** `NT SERVICE\WarehouseA`：不用 LocalSystem（權限過大），也不用建立真的使用者與管理密碼。
- 啟動類型「自動（延遲）」：開機後等其他服務（例如 PostgreSQL）先起來。
- 失敗自動重啟：`sc.exe failure`，5 秒、10 秒後重試。
- 服務專屬環境變數寫在 `HKLM\SYSTEM\CurrentControlSet\Services\<名稱>\Environment`，只影響這個服務。
- `icacls` 設定目錄權限（見上方目錄圖）。
- 沒有提供連線字串時，會建立設定範本並停止，請編輯 `config\appsettings.Production.json` 後重跑。

| `WAREHOUSE_CONFIG_DIR 指向的設定目錄不存在` | 服務環境變數路徑錯誤 | 檢查登錄 `Services\<名稱>\Environment` |
| 頁面樣式消失、首頁 404 | 服務模式下工作目錄是 `C:\Windows\System32` | `Program.cs` 已在服務模式把內容根目錄設為程式目錄；若被移除會發生 |
| `/health/ready` 503 | 連不到資料庫 | 檢查 PostgreSQL 服務與連線字串 |
| 存取被拒（讀 config、寫 logs） | ACL 未包含服務帳號 | 重新執行安裝腳本的權限步驟，或依上方目錄圖用 `icacls` 補上 |
| 埠已被占用 | 另一個實例或程式使用同一埠 | `Get-NetTCPConnection -LocalPort 5080`；A/B 兩個實例要用不同埠 |

### Data Protection 金鑰（M0-12 已處理）
- 服務環境變數 `DataProtection__KeysDirectory=C:\Warehouse\data\keys`（Linux：`/var/lib/warehouse/keys`），A/B 共用；程式見 `src/Warehouse.Web/SharedDataProtection.cs`，說明見 §12。

### 11.1 開發機的 Linux 測試環境（WSL2）

### 11.2 原生 systemd 服務

| 路徑 | 擁有者／權限 | 用途 |
|---|---|---|

| `/etc/warehouse/appsettings.Production.json` | root:warehouse 0640 | 連線字串（`--connection-string-file` 讀完即刪除該檔） |

## 12. 線上更新與回滾教學（M0-12 PoC，2026-10-21 實測）
> 決策與實測數據見 ADR-0010；設計目標與非目標見 `docs/11`。庫存交易切版冪等已於 M4-06 實測（`docs/11` §10、T-M4-06-06）；尚未涵蓋：PWA 更新（尚未實作 PWA）、Schema 變更流程實演（目前無 Migration）。

### 12.1 架構與名詞
```text
手機／PC ──HTTPS 5443──> WarehouseProxy（src/Warehouse.Proxy，YARP）
                              │ 只轉到 upstream.json 指定的槽位
                 ┌────────────┴────────────┐
       槽位 A：WarehouseA :5080      槽位 B：WarehouseB :5081   （只聽 localhost）
                 └──── 同一 config\、data\keys\、PostgreSQL ────┘
```
- **槽位**：固定的服務名稱＋埠。更新時新版裝到「待命槽位」，舊槽位停止後保留供回滾。
- **upstream.json**（`C:\Warehouse\proxy-config\`）：`ActiveSlot` 與代理目的地。這是唯一的切換開關。
- 伺服器目錄新增：`proxy-config\`（代理專用，含憑證密碼，只給代理帳號讀）、`certs\warehouse-server.pfx`、`data\keys\`（A/B 共用金鑰）、`logs\deploy.log`（切換紀錄）。
- **`upstream.json` 不要手動編輯**，一律用 `switch-release.ps1`。M7-10 起內容無效時代理保留上一份有效目的地並記錄錯誤（不再 503），但代理重新啟動時檔案無效會啟動失敗。
- **M7-10 強化**：代理回應加 `X-Warehouse-Slot`（目前槽位），`switch-release` 以槽位＋版本確認切換；同時只能一個 `switch-release`（具名 Mutex／`flock`）；`C:\Warehouse\deploy-state.json` 記錄各槽位版本與是否曾成功上線，`-Rollback` 拒絕切到更新失敗留下的版本，回滾前也做冒煙。
- 權限（審查後修正）：安裝腳本先執行 `Set-RootAcl`，`C:\Warehouse` 改為不繼承 `C:\`、擁有者 Administrators，一般使用者完全無法讀取；各服務帳號只拿到需要的目錄權限。檢查：`icacls C:\Warehouse` 應只有 Administrators、SYSTEM。

### 12.2 程式怎麼運作
| 檔案 | 作用 |
|---|---|
| `src/Warehouse.Proxy/Program.cs` | 註冊 `UpstreamConfigProvider` 為 YARP 的 `IProxyConfigProvider`、`MapReverseProxy()`；也呼叫 `AddWindowsService`／`AddSystemd` |
| `src/Warehouse.Proxy/UpstreamFile.cs` | （M7-10）`UpstreamFile.Parse` 驗證 `upstream.json`；`UpstreamConfigProvider` 監看 `WAREHOUSE_CONFIG_DIR` 的檔案，有效時換新設定（**新請求**改送新目的地，進行中的請求不受影響），無效時記 Error、保留上一份；路由 `{**catch-all}` → cluster `app` 與 `X-Warehouse-Slot` 回應標頭寫在程式 |
| `src/Warehouse.Proxy/appsettings.json` | `Proxy:ActivityTimeout`（預設 100 秒；M7-10 前的鍵 `ReverseProxy:Clusters:app:HttpRequest:ActivityTimeout` 已不使用）；YARP 日誌降為 Warning（避免每個請求一行） |
| `src/Warehouse.Proxy/Warehouse.Proxy.csproj` | 以連結編譯共用 `src/Warehouse.Web/ExternalConfiguration.cs` |
| `src/Warehouse.Web/SharedDataProtection.cs` | `DataProtection:KeysDirectory` 有值時金鑰存到該目錄（Windows 加 DPAPI）；ApplicationName 固定 `Warehouse` |
| `src/Warehouse.Web/Program.cs` | `UseForwardedHeaders`：讀代理加的 `X-Forwarded-Proto`，程式才知道外部是 HTTPS（之後 Cookie `Secure`、重新導向需要） |

為什麼 ApplicationName 要固定：框架預設用「內容根目錄路徑」區分應用程式，A、B 安裝在不同版本資料夾，預設值不同，即使共用金鑰目錄也互相解不開（`DataProtectionSharingTests` 驗證）。


### 12.4 更新與回滾
```powershell
.\scripts\windows\switch-release.ps1 -ReleasePath artifacts\publish\<新版資料夾>   # 更新
.\scripts\windows\switch-release.ps1 -Rollback                                     # 切回待命槽位的版本
Get-Content C:\Warehouse\logs\deploy.log -Tail 20                                  # 切換紀錄
```
更新的預期輸出：
```text
開始更新：A（0.1.0+0a6bd14…）→ B（0.1.0+a86fabe…）
已建立服務 WarehouseB（帳號 NT SERVICE\WarehouseB，埠 5081）
服務已就緒：http://localhost:5081/health/ready = 200
冒煙測試通過：版本 0.1.0+a86fabe…、資料庫已連線
流量已切換：A → B（0.5 秒確認）
排空 10 秒，讓槽位 A 處理完進行中的請求…
已停止槽位 A（WarehouseA，保留供回滾）
完成：目前槽位 B，版本 0.1.0+a86fabe…
```
每一步的理由：
1. **裝到待命槽位**：不動正在服務的版本；失敗時使用者完全不受影響。
2. **readiness＋冒煙**：`/health/ready`（含 DB）通過、`/api/system/info` 版本正確才往下走。
3. **原子改寫 upstream.json 後經代理確認版本**：只看「檔案寫入成功」不夠（檔案監看可能延遲或失效），要從使用者的入口確認。
4. **排空**：切換後舊槽位可能還有請求在處理；等待 `-DrainSeconds`（預設 10）再停止。停止時 ASP.NET Core 也會等進行中的請求結束（預設最多 30 秒）。
5. **舊槽位改「手動」**：重開機後只會啟動目前槽位，不浪費記憶體。

```powershell
Invoke-RestMethod https://localhost:5443/health/ready                                 # 使用者實際接到的版本
Get-Service WarehouseA, WarehouseB, WarehouseProxy

```

### 12.6 常見錯誤
| 現象／訊息 | 原因 | 處理 |
|---|---|---|
| 「槽位 B 新版未就緒，更新中止，流量維持 A」 | 新版啟動失敗或連不到 DB | 事件檢視器查 WarehouseB；流量未受影響，修正後重跑 |
| 「冒煙測試失敗：版本 …」 | 發布資料夾與 release.json 不一致 | 重新發布，不要手動改發布資料夾內容 |
| 「代理未在 15 秒內轉到槽位 B，已改回槽位 A」 | 代理沒載入新的 upstream.json（服務停止、檔案權限） | `Get-Service WarehouseProxy`；`icacls C:\Warehouse\proxy-config` 應含 `NT SERVICE\WarehouseProxy:(R)` |
| 「待命槽位 B 沒有安裝服務，無法回滾」 | 從未更新過 | 用 `-ReleasePath <舊版>` 部署舊版 |
| 更新失敗後 `-Rollback` 回到壞版本 | 更新會覆蓋待命槽位 | 用 `-ReleasePath` 重新部署要的版本 |
| 代理回 502 | 目前槽位服務停止 | 啟動該槽位，或 `-Rollback` |
| `dotnet run --launch-profile lan` 埠 5443 被占用 | 代理服務正在用 5443 | 開發時停止 `WarehouseProxy` 或改用其他 profile |
| 表單送出 400（防偽權杖無效） | A/B 金鑰目錄或 ApplicationName 不一致 | 檢查服務環境變數 `DataProtection__KeysDirectory`；`data\keys` 應只有共用的 `key-*.xml` |

### 12.7 Linux（WSL 簡測，精簡腳本）
```bash
sudo ./scripts/linux/install-service.sh --release <主程式> --name warehouse-a --port 5180
sudo ./scripts/linux/install-service.sh --release <代理> --name warehouse-proxy --port 5480 \
     --config-dir /etc/warehouse-proxy --upstream-port 5180
sudo ./scripts/linux/switch-release.sh --release <新版> --proxy-url http://localhost:5480 --port-a 5180 --port-b 5181
sudo ./scripts/linux/switch-release.sh --rollback --proxy-url http://localhost:5480 --port-a 5180 --port-b 5181
```
- WSL mirrored 網路與 Windows 共用 localhost 埠，所以 Linux 測試改用 5180／5181／5480，避免與 Windows 的 5080／5081／5443 衝突；實際 NAS 可用預設值。
- 代理以獨立使用者 `warehouse-proxy` 執行（`install-service.sh` 依 release.json 的 `entry` 自動切換），讀不到 `/etc/warehouse` 的連線字串與 `/var/lib/warehouse/keys`。
- Linux 簡測的代理只聽 HTTP；NAS 實機的 HTTPS 設定待取得設備後補（`Kestrel:Endpoints` 與憑證放在 `/etc/warehouse-proxy/appsettings.Production.json`）。
- 紀錄在 `/var/log/warehouse-deploy.log`。

### 13.3 儲位 QR Code（M3-04，選配）
- 內容格式：`WH:LOC:<倉庫碼>:<儲位碼>`，例 `WH:LOC:W1:W1-A-01-03-02`；物料是 `WH:ITEM:EL-000125`。
- 儲位頁面會顯示這段文字。V1 不產生 QR 圖片、不列印標籤（ADR-0003），可用任何 QR 產生器自製。
- 沒有條碼時，在 `/Warehouses/Locations` 用儲位碼、名稱、區、架搜尋。儲位碼的大小寫、全形都能查到。

### 13.4 常見錯誤
| 現象 | 原因 | 處理 |
|---|---|---|
| 「這個倉庫已經有相同的儲位碼」 | 同倉重複 | 換一個儲位碼；不同倉庫可以重複 |
| 「倉庫已停用，不能新增儲位」 | 倉庫停用 | 先啟用倉庫 |
| `23001 稽核紀錄只能新增` | 試圖修改或刪除稽核 | 稽核不可改；更正要用新的紀錄 |
| 修改儲位時「資料已被他人修改」 | 開表單後別人先改了 | 重新開啟頁面 |

## 14. 庫存帳與期初建帳（M3-02、M3-03、M3-05）

### 14.1 資料表（Migration `M3_03_StockLedger`）
| 表 | 用途 | 重點約束 |
|---|---|---|
| `stock_documents` | 單據表頭（目前只有 `Opening`），單號 `OB-000001` | 不可刪除；已過帳或已取消的不可改（trigger）；`ck_stock_documents_posted` |
| `stock_document_lines` | 明細（`item_id` 為 NULL＝整個儲位確認為空） | 單內 `ux_stock_document_lines_key` 唯一；只有草稿可改（trigger） |
| `stock_balances` | 即時結存 | `ux_stock_balances_dimension`（NULLS NOT DISTINCT）、`ux_stock_balances_serial_in_stock`、序號 ≤ 1、不可為負（M4 起改由 trigger，依物料負庫存設定，§16） |
| `stock_movements` | 異動帳 | 只能新增（trigger） |
| `inventory_lots`、`item_serials` | 批號（有效期限）、序號 | 同一物料內唯一 |
| `processed_commands` | 冪等鍵 | 主鍵唯一 |
| `locations.opening_document_id` | 做過期初的單據 | NULL＝尚未清點 |

### 14.2 期初流程與畫面
1. **作業員或倉庫主管**在 `/Opening` 選倉庫，建立期初單。
2. 在 `/Opening/Details/{id}` 逐行加入明細：
   - 儲位碼（可掃儲位 QR，或手動輸入）。
   - 料號（大小寫、全形都可以）。
   - 數量：依物料的基本單位，小數位數依單位限制。
   - 批號（加有效期限），或序號（每個序號一行、數量 1）。
   - 沒有東西的儲位，勾選「確認為空」。
     - 匯入時料號儲存格空白也表示確認為空。
     - D-33 起，空儲位的數量必須是 0，也不能帶批號、序號、有效期限（`OpeningService.AddLineAsync`），否則被拒。這是為了避免料號漏填時，有庫存的儲位被記成空的。
     - 期初明細匯入的「料號」欄是必要標題：上傳沒有這一欄的檔案（例如核對用的對照表）會整檔被拒。
3. 「送出核准」之後，明細就不能再改。
4. **倉庫主管**核准，系統立即過帳；也可以退回並寫明原因。
   - D-07 預設建立者不能核准自己的單，可在 `/Settings` 開啟自核。
5. `/Stock` 依倉庫、儲位碼、料號查結存與最近異動；選倉庫時也會列出尚未清點的儲位。

### 14.3 核准時程式怎麼走（`OpeningService.ApproveAsync`）
1. 檢查冪等鍵：處理過且內容相同就直接結束（連點、重送、逾時重試都只過帳一次）。
2. 開交易，鎖單據（`FOR UPDATE`），再查一次冪等鍵。
3. 檢查狀態與版本、是否為倉庫主管、自核設定（`StockDocument.MarkPosted`）。
4. 依 id 排序鎖住儲位，並對倉庫加共享鎖，然後重新確認：
   - 儲位屬於這個倉庫、沒停用、沒做過期初。
   - 倉庫仍啟用。
   - 物料仍是有效狀態。
5. 批號、序號依（物料, 號碼）排序後 upsert，沒有就建立。已存在的批號若有效期限不同，或序號登記在別的批號下，拒絕。結存一律寫 Available，可用與否看儲位狀態。
6. 呼叫 `InventoryPostingService.ApplyAsync`：upsert 結存、寫異動。序號已在庫時，唯一索引擋下，回傳中文訊息，整張單回滾。
7. 標記儲位已期初、單據已過帳，寫稽核與冪等紀錄，然後 commit。
- 交易內等鎖最多 5 秒；死結或逾時會回「有其他人同時在處理…請稍後再按一次核准」，交易已回滾，重按即可。

API：`POST /api/stock/opening/{id}/approve`
- 標頭：`Idempotency-Key: <8～100 字>`，缺少時回 400。
- 本文：`{"version": <讀取時的 version>}`。
- 結果：成功回 204；同一鍵重送也是 204。

### 14.4 用 SQL 追查期初交易（M3-05）
```sql
-- 1. 找單據：狀態、建立者、核准者
SELECT id, doc_no, status, created_by_name, created_at, approved_by_name, posted_at
  FROM stock_documents WHERE doc_no = 'OB-000001';
-- 2. 明細與解析出的批號、序號
SELECT line_no, l.code AS location, i.item_code, d.lot_no, d.serial_no, d.quantity, d.lot_id, d.serial_id
  FROM stock_document_lines d JOIN locations l ON l.id = d.location_id LEFT JOIN items i ON i.id = d.item_id
  WHERE d.document_id = '<單據 id>' ORDER BY line_no;
-- 3. 這張單產生的異動（每行一筆；quantity_delta、balance_after）
SELECT occurred_at, i.item_code, l.code, m.stock_status, m.quantity_delta, m.balance_after, m.actor_name
  FROM stock_movements m JOIN items i ON i.id = m.item_id JOIN locations l ON l.id = m.location_id
  WHERE m.document_id = '<單據 id>';
-- 4. 對帳：結存應該等於所有異動的加總
SELECT b.item_id, b.location_id, b.quantity, COALESCE(SUM(m.quantity_delta), 0) AS movements_sum
  FROM stock_balances b LEFT JOIN stock_movements m
    ON m.item_id = b.item_id AND m.location_id = b.location_id AND m.stock_status = b.stock_status
   AND m.lot_id IS NOT DISTINCT FROM b.lot_id AND m.serial_id IS NOT DISTINCT FROM b.serial_id
  GROUP BY b.id HAVING b.quantity <> COALESCE(SUM(m.quantity_delta), 0);   -- 正常應該沒有任何一列
-- 5. 哪些儲位還沒清點
SELECT code FROM locations WHERE warehouse_id = '<倉庫 id>' AND opening_document_id IS NULL AND status <> 'Inactive';
-- 6. 冪等紀錄與稽核
SELECT * FROM processed_commands WHERE result_ref = '<單據 id>';
SELECT occurred_at, actor_name, action, after FROM audit_logs WHERE entity_id = '<單據 id>' ORDER BY occurred_at;
```

### 16.2 `ApplyAsync` 怎麼走（呼叫端已開交易）
```text
SET LOCAL lock_timeout = '5s'
① 儲位依 id FOR UPDATE（停用 → 拒絕）
② 倉庫依 id FOR SHARE（停用 → 拒絕）
③ 讀物料設定 → advisory lock：有扣減的（料號,倉庫）＋允許負庫存物料的（料號），依鍵值排序 → 重讀物料設定
④ 依預留出庫：預留列 FOR UPDATE，逐行沖銷 min(扣減量, 剩餘量)
⑤ 同維度（物料＋儲位＋批號＋序號＋狀態）合計淨值 → 扣減的維度先、再依維度排序 → 一次 unnest upsert（trigger 檢查不可為負）
⑥ 一次寫入全部異動帳（異動後結存＝最終值 − 淨值，再逐行累加；增加在前、扣減在後）
⑦ 寫入後檢查（新語句，看得到排在前面已 commit 的交易）
   a. 負數只能在「Available 結存＋有效儲位」
   b. 一般物料：本次讓（料號,倉庫）可用量變少時，可用量 ≥ 0
   c. 允許負庫存物料：本次讓料號可用量變少時，全倉合計可用量 ≥ −下限
⑧ 稽核（stock.negative、reservation.consume）加入 EF，呼叫端 SaveChanges 一起寫入
```
- **可用量**＝Σ（`stock_status = 'Available'` 且 `locations.status = 'Available'` 的結存）− Σ（Open 預留的 `remaining_quantity`）。
- **只在淨效果 < 0 時檢查**：有效儲位之間移庫（淨 0）不會被「儲位改待驗造成的既有不足」擋住；移到待驗儲位（淨 −）會檢查。
- **入庫不取鎖**：只會讓可用量變大；預留、出庫在鎖後重新計算，最多因看不到未 commit 的入庫而保守拒絕，不會超賣。
- **扣減先寫**：序號唯一索引（數量 > 0）逐列檢查，序號移庫或從待驗改回可用時，舊位置要先歸零（M4-01 審查 #1）。序號每筆變化必須是 ±1，CHECK 也要求整數。
- **為什麼是 AFTER trigger**：`INSERT … ON CONFLICT DO UPDATE` 會先用「預定插入列」（數量＝扣減量，為負）觸發 BEFORE INSERT 與 CHECK。同理，序號的 CHECK 從 `IN (0, 1)` 改成 `<= 1`，不可為負交給 trigger（序號物料不能開負庫存）。
- 500 行一次過帳：開發機約 40 ms（T-M4-01-19）。

### 16.3 預留
- `ReserveAsync`：倉庫 FOR SHARE → 取（料號,倉庫）與（料號）兩把鎖 → 讀物料設定 → 插入 → 倉庫可用量 ≥ 0，否則 `stock.insufficient`。**負庫存物料也不能預留不存在的庫存**，且預留後全倉合計仍要 ≥ −下限（`stock.negative_limit`）。
- 倉庫還有 Open 預留時不能停用（`WarehouseService.SetWarehouseActiveAsync`）。
- 依預留出庫：`StockChange.ReservationId`；超過剩餘量的部分當一般出庫（使用者 2026-10-22）。待驗儲位也可依預留出庫（沖銷後可用量變多，不擋）。
- `ReleaseReservationAsync`：只把 Open 改 Released，不取鎖；已結束回傳 false（重送不出錯）。

### 16.4 負庫存（ADR-0004 決策一）
- 只有 `items.allow_negative_stock = true`（只限 `TrackingMode=None`）可以變負；下限是**料號全倉合計可用量 ≥ −`negative_stock_limit`**（使用者 2026-10-22），單一儲位不設下限。
- 變負的異動 `is_negative = true`，並寫稽核 `stock.negative`（待補帳清單 M4-08 的來源）。
- 修改負庫存設定（M4-08）必須先取 `StockItemKey` 再 `items FOR UPDATE`，才能和造成負數的過帳排隊。

### 16.5 鎖順序（新增程式要取鎖時必須插在這個順序中）
單據 `FOR UPDATE` → 儲位依 id `FOR UPDATE` → 倉庫依 id `FOR SHARE` → 批號／序號 upsert（期初、M4 單據）→ 庫存 advisory 鎖（依鍵值）→ 預留列依 id `FOR UPDATE` → 結存批次 upsert → 異動帳、檢查、冪等、稽核。
- 呼叫端若要自己鎖儲位（例如期初檢查 `opening_document_id`），必須在批號／序號 upsert **之前**。
- `StockKey`／`StockItemKey` 的算法**不可變更**（A/B 兩版同時運作要鎖到同一把）。
- advisory 鎖占用 PostgreSQL 共用鎖表空位（約 `max_locks_per_transaction ×（max_connections＋預備交易數）`，預設 64 × 100）；500 行單據最多約 1000 把（負庫存物料每料號多一把料號鎖）。部署到 NAS 前確認設定（`docs/10`）。
- 儲位用 `FOR UPDATE`（不是 FOR SHARE）：寫同一結存列的交易先搶同一把儲位鎖，結存列的寫入順序（扣減先寫）才不會造成死結；代價是同一儲位的過帳排隊。**改成 FOR SHARE 前必須重新檢視結存列的寫入順序。**

### 16.6 用 SQL 查可用量與預留
```sql
-- 某料號在某倉的可用量（與程式同一公式）
SELECT COALESCE((SELECT SUM(b.quantity) FROM stock_balances b JOIN locations l ON l.id = b.location_id
                 WHERE b.item_id = '<物料 id>' AND l.warehouse_id = '<倉庫 id>'
                   AND b.stock_status = 'Available' AND l.status = 'Available'), 0)
     - COALESCE((SELECT SUM(remaining_quantity) FROM stock_reservations
                 WHERE item_id = '<物料 id>' AND warehouse_id = '<倉庫 id>' AND status = 'Open'), 0) AS available;

  FROM stock_reservations WHERE item_id = '<物料 id>' AND status = 'Open' ORDER BY created_at;
-- 目前負結存（待補帳）

  JOIN items i ON i.id = b.item_id JOIN locations l ON l.id = b.location_id WHERE b.quantity < 0;
```

**物料匯入的自動核准與原廠條碼欄（D-31，2026-10-27）**
- 範本多一個選填欄「原廠條碼」：多個用頓號、逗號、分號（含全形）分隔，不以空白分隔；包裝數量為 1 個基本單位（其他包裝數量到物料頁登錄）。
  - 這一欄在 xlsx 裡是**數字儲存格**時列為錯誤（`ImportRow.IsNumber`）：Excel 會去掉前導零、把第 16 位以後改成 0，讀到的已不是包裝上的條碼。
- 所有自動核准（表單、匯入）先取 `AdvisoryLocks.LockItemAutoApproveAsync` 排隊：提出與核准在同一個交易，提交前別人看不到這筆新物料，不排隊時兩個同名的自動核准會互相看不到、都被核准。
  - 代價：自動核准匯入的試算與確認期間，別人的表單自動核准要等；同前綴的手動核准也要等料號計數器（ADR-0019 補充）。
- 確認時上傳者已不是物料管理員 → `import.forbidden`，批次不變。
- 物料管理員上傳時可勾「匯入後自動核准」（`IndexModel.CanAutoApprove`；服務層非物料管理員或非物料種類丟 `import.forbidden`）。選項存在 `import_batches.auto_approve`，確認時照同一個值執行。
- 每列呼叫 `ItemWorkflowService.SubmitAsync(…, ItemSubmitOptions, …)`：提出、登錄條碼、核准在同一個 savepoint 內。
  - 沒有疑似重複候選 → 核准、發正式料號，審核意見「提出時自動核准」。
  - 有候選（既有物料或同批前面的列）→ 維持待核准，列為警告「這一列不自動核准」（使用者 2026-10-27 決定）。
  - 條碼已被其他物料使用 → 該列錯誤，整批不匯入。
- 這個多載原本自己開交易，改成 `BeginOrJoinTransactionAsync`；加入外層交易時失敗直接丟出，由匯入回到該列的 savepoint（發號計數器一起回滾，不占號）。

### 24.5 踩過的雷（寫腳本時要注意）
- **子程序輸出的編碼**：`dotnet run` 輸出 UTF-8，直接執行 dll 時用主控台字碼頁 950。要自動判斷，用 `Read-ChildOutput`。
- **dotnet 子程序會改主控台字碼頁**：輸出中文報告前，要呼叫 `Set-ConsoleEncoding`。
- PowerShell 把 `$null` 轉成空字串。所以要真的刪除環境變數，要用 `Set-ProcessVariable`。否則會留下空的 `ConnectionStrings__Warehouse`，蓋過設定檔。
- `postgresql.conf` 字串裡的 `\` 會被當成跳脫字元，路徑要寫成 `\`，例如 `restore_command`。
- **`pg_ctl` 以受限權杖執行**：它不能在受保護的目錄建立記錄檔，所以記錄檔要先建立並授權。
- **閒置資料庫做 PITR**：停不在指定時間，因為 PostgreSQL 要看到晚於目標時間的交易才會停。改用不指定時間，還原到最新。
- **從 Bash 用管線啟動 `pg_ctl start`**：postmaster 會繼承管線，命令一直不結束。要用 `Start-Process -WindowStyle Hidden`。
- **EF 的歷史表是 snake_case**：`__EFMigrationsHistory` 的欄位是 `migration_id`，不是 `MigrationId`。
- **權限**：`C:\Warehouse`、`C:\WarehouseBackup` 只有系統管理員能讀，所以要讀秘密的步驟都設計成「一次 UAC 跑完」的腳本。

### 25.1 刪除倉庫（M8-01，PR #65）
- 入口：「倉庫」頁的刪除按鈕，要確認兩次；「顯示已刪除」可以「還原」，還原後仍是停用。
- `IWarehouseService.DeleteWarehouseAsync` 回傳 `WarehouseDeleteResult`：
  - `Removed`：從未用過，連同儲位、儲位圖片、常用儲位、帳號倉庫範圍一起刪除。
  - `Hidden`：用過但已清空，設定 `deleted_at`／`deleted_by` 並停用。
- 刪除前的條件：結存全部為 0，沒有 Open 預留、草稿或送審中的單據（包含移入這個倉庫的移庫單），也沒有進行中的盤點。
- Migration `M8_01_WarehouseSoftDelete`：
  - 新增 `deleted_at`、`deleted_by` 欄位。
  - CHECK `ck_warehouses_deleted_inactive`：已刪除的倉庫不能啟用。這同時保護 A/B 相容窗口內的舊版。
- **鎖**（`src/Warehouse.Infrastructure/Warehousing/WarehouseLock.cs`）：
  - 寫入路徑先用 `LockUsableAsync` 對倉庫取 FOR SHARE，再檢查。這些路徑包括開單、盤點、期初、儲位、常用倉位、儲位圖片、帳號範圍。

  - **不要把這些路徑改成 FOR UPDATE**，否則會和過帳的「儲位 FOR UPDATE → 倉庫 FOR SHARE」形成死結。
- 查詢：
  - `ListWarehousesAsync()` 不含已刪除的倉庫，選單、篩選、帳號範圍都用這個。
