# 線上更新與回滾設計規格 v0.2

> 此處的「不斷線更新」是指**應用程式正常升版期間不停止正常倉庫作業**，而非單台 NAS／PC／資料庫的全故障高可用。此文件是 PoC 前的設計，不代表功能已實作。

## 1. 更新目標與非目標
### 必須達到
- 使用者存取的內網網址維持不變，升版時不要求所有人先登出或停工。
- 對新請求逐步導向經過健康檢查的版本；進行中的庫存交易完成或安全重試，結果不遺失、不重複。
- 不強制重整尚未送出的網頁／PWA 表單；版本不同的短暫相容窗口可正常處理已有頁面的請求。
- 新版有問題能切回 DB 相容的舊版本；可由紀錄查詢當下 App 版本與回滾動作。

### 非目標
- 不保證單機作業系統重開、磁碟或電源故障、NAS/PC 斷線、DB 故障、網路設備故障時仍完全零中斷。
- 不在未驗證硬體資源前承諾 Blue-Green 一定可在同台 NAS 執行。

## 2. 建議架構
```text
PC / PDA / 手機
      |
固定內網 HTTPS 網址
      |
反向代理（更新時變更新請求路由）
  |                        |
App A（正式舊版）      App B（待上線新版）
  |                        |
  +----------+-------------+
             |
       PostgreSQL（相容 schema）
             |
    獨立備份、附件與日誌
```
反向代理產品與詳細配置需在 M0 選型並記錄；Linux 與 Windows 可使用不同主機啟動機制，但服務端點／版本切換概念一致。

## 3. 發布基本流程（版本 A → B）
1. **建立發布包**：從已審查 Git commit 產生平台適用的 .NET 發布產物；不直接覆蓋 App A 目錄。
2. **驗證與備份**：確定預期資料庫結構差異、相容窗口、回滾限制，完成與驗證備份。
3. **必要的相容 Schema 擴充**：若有 migration，於經核准的獨立步驟套用 Expand 類非破壞性變更，不在 App 啟動自動修改正式 DB。
4. **啟動新版 App B**：在獨立路徑、埠、服務或容器運行，接同一個相容 DB。
5. **進行 liveness/readiness 與冒煙測試**：登入、查料、權限、資料讀取、寫入功能的安全測試（不得任意變動真實庫存）。
6. **切換新請求**：反向代理指向 B；記錄切換時間與版本；持續觀察異常率。
7. **舊版本排空**：等待 A 的進行中請求結束；涉及 SSE/WebSocket/Blazor Interactive Server 時需特別處理重連及會話狀態，不能只切 HTTP 路由。
8. **停止舊 App A**：確認 A 不再有需要服務的連線，仍保留發布檔案供回滾。
9. **更新客戶端與收尾**：透過安全時機提示舊 Web/PWA 版本更新，待相容窗口結束再安排 Contract 類清理。

## 4. 更新期間的 API 與資料庫相容策略
- A/B 必須同時支援部署後的 schema。對欄位改名／刪除採 Expand → Migrate → Contract，不可直接刪除 A 尚使用的欄位。
- API 做版本相容性檢查；不得讓尚未更新的 PWA 頁面因新版 API 刪除欄位而遺失已填內容。
- 若新程式引入新資料格式導致舊版無法正確解析，則**不可宣稱無條件可回滾**；必須擬定資料反向相容或專案維護窗口。
- `Idempotency-Key` 配合唯一約束及交易結果，防止切版／逾時／重試造成重複出入庫。
- `StockMovements` 與 `StockBalances` 在同一 PostgreSQL Transaction 中原子提交；代理重試不得盲目重發非冪等寫入。

## 5. 健康檢查及版本觀察
- `GET /health/live`：應用行程存活；避免不必要的昂貴依賴探測。
- `GET /health/ready`：已完成啟動且能接受請求；必要時檢查關鍵依賴並設定超時。
- 額外提供受控 `version` 資訊或部署標頭（不得洩漏機密），能辨識實際接流量版本。
- 應有 RequestId、部署版本、日誌與錯誤統計，以便追查切版時是否遺失操作。

## 6. 前端與 PWA 更新
- JS/CSS 靜態檔案採可識別版本的檔名或資源清單，避免舊 HTML 與新檔內容不相容。
- PWA Service Worker 可能快取舊版 UI；不得強制 `skipWaiting` / 自動 reload 導致尚未送出的作業遺失。
- 已填未提交的表單應保留至操作完成，之後才提供更新提示；更複雜離線狀況仍不代表已支援離線庫存交易。
- 若採 Blazor Interactive Server，須另外設計 UI circuit/session 中斷、連線重建與狀態恢復；最好降低對長連線互動的依賴。

## 7. 回滾流程與限制
1. 確認 B 出錯，判斷是否仍可安全使用 A（API／schema／資料格式相容）。
2. 反向代理將新請求切回 A（必要時先重新啟動 A 並做 readiness 測試）。
3. 保留 B 的日誌與錯誤版本，確認庫存交易筆數、冪等鍵和結存沒有遺失或重複。
4. 若已執行不可逆 migration 或新資料格式，不可盲目覆蓋 DB／回滾：應啟動事先核准的資料修復／維護計畫。
5. 記錄原因、修復者、時間、相關 Git commit、資料庫版本及後續預防措施。

## 8. 必須測試的案例
- 新版本 ready 失敗 → 流量仍停留 A。
- 新版本接流量後錯誤率升高 → A 可以恢復新請求。
- 兩人在切換前後同時對一筆物料出庫 → 不超量、不重複。
- API 提交成功但用戶端逾時重試 → 同 Key 不重複過帳。
- 使用者尚在編輯表單與 PDA 連續掃碼 → 不強迫重新整理或清除內容。
- PWA 保有舊版快取 → 仍能在相容期呼叫後端或提供安全升級提示。
- 單機 App A/B 同時運行的 CPU/RAM 在指定 NAS/PC 允許範圍。

## 9. 決策前必須提供
- Windows 與 NAS 的具體代理選型及配置範例。
- 伺服器實測可用 RAM/CPU、A/B 運行統計、資料庫與儲存配置。
- 執行更新及回滾的 PowerShell/腳本與明確人工操作步驟。
- 完整整合／負載／失敗注入測試證據，涵蓋庫存資料一致性。
- 發布窗口、舊 Web/API 相容期限、異常通知方式及 RPO/RTO。
