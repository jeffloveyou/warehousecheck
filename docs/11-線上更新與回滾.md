# 線上更新與回滾設計規格 v0.2

> 此處的「不斷線更新」是指**應用程式正常升版期間不停止正常倉庫作業**，而非單台 NAS／PC／資料庫的全故障高可用。§1～§9 為設計規格；M0-12 已實作的部分與實測見 §10。

## 1. 更新目標與非目標
### 必須達到
- 使用者存取的內網網址維持不變，升版時不要求所有人先登出或停工。
- 對新請求逐步導向經過健康檢查的版本；進行中的庫存交易完成或安全重試，結果不遺失、不重複。
- 不強制重整尚未送出的網頁／PWA 表單；版本不同的短暫相容窗口可正常處理已有頁面的請求。
- 新版有問題能切回 DB 相容的舊版本；可由紀錄查詢當下 App 版本與回滾動作。

### 非目標
- 不保證單機作業系統重開、磁碟或電源故障、NAS/PC 斷線、DB 故障、網路設備故障時仍完全零中斷。
- 不在未驗證硬體資源前承諾 Blue-Green 一定可在同台 NAS 執行。

## 2. 建議架構
```text
PC / PDA / 手機
      |
固定內網 HTTPS 網址
      |
反向代理（更新時變更新請求路由）
  |                        |
App A（正式舊版）      App B（待上線新版）
  |                        |
  +----------+-------------+
             |
       PostgreSQL（相容 schema）
             |
    獨立備份、附件與日誌
```
反向代理產品與詳細配置需在 M0 選型並記錄；Linux 與 Windows 可使用不同主機啟動機制，但服務端點／版本切換概念一致。

## 3. 發布基本流程（版本 A → B）
1. **建立發布包**：從已審查 Git commit 產生平台適用的 .NET 發布產物；不直接覆蓋 App A 目錄。
2. **驗證與備份**：確定預期資料庫結構差異、相容窗口、回滾限制，完成與驗證備份（資料庫＋附件目錄 `Storage:AttachmentsDirectory`，M3-08 起）。從 M3 以前的版本更新時，兩個槽位的服務都要先加上環境變數 `Storage__AttachmentsDirectory`（重新執行安裝腳本），否則新版在 Production 會啟動失敗、readiness 不通過，代理不會切過去。
3. **必要的相容 Schema 擴充**：若有 migration，於經核准的獨立步驟套用 Expand 類非破壞性變更，不在 App 啟動自動修改正式 DB。
4. **啟動新版 App B**：在獨立路徑、埠、服務或容器運行，接同一個相容 DB。
5. **進行 liveness/readiness 與冒煙測試**：登入、查料、權限、資料讀取、寫入功能的安全測試（不得任意變動真實庫存）。
6. **切換新請求**：反向代理指向 B；記錄切換時間與版本；持續觀察異常率。
7. **舊版本排空**：等待 A 的進行中請求結束；涉及 SSE/WebSocket/Blazor Interactive Server 時需特別處理重連及會話狀態，不能只切 HTTP 路由。
8. **停止舊 App A**：確認 A 不再有需要服務的連線，仍保留發布檔案供回滾。
9. **更新客戶端與收尾**：透過安全時機提示舊 Web/PWA 版本更新，待相容窗口結束再安排 Contract 類清理。

## 4. 更新期間的 API 與資料庫相容策略
- A/B 必須同時支援部署後的 schema。對欄位改名／刪除採 Expand → Migrate → Contract，不可直接刪除 A 尚使用的欄位。
- API 做版本相容性檢查；不得讓尚未更新的 PWA 頁面因新版 API 刪除欄位而遺失已填內容。
- 若新程式引入新資料格式導致舊版無法正確解析，則**不可宣稱無條件可回滾**；必須擬定資料反向相容或專案維護窗口。
- `Idempotency-Key` 配合唯一約束及交易結果，防止切版／逾時／重試造成重複出入庫。
- `StockMovements` 與 `StockBalances` 在同一 PostgreSQL Transaction 中原子提交；代理重試不得盲目重發非冪等寫入。

## 5. 健康檢查及版本觀察
- `GET /health/live`：應用行程存活；避免不必要的昂貴依賴探測。
- `GET /health/ready`：已完成啟動且能接受請求；必要時檢查關鍵依賴並設定超時。
- 額外提供受控 `version` 資訊或部署標頭（不得洩漏機密），能辨識實際接流量版本。
- 應有 RequestId、部署版本、日誌與錯誤統計，以便追查切版時是否遺失操作。

## 6. 前端與 PWA 更新
- JS/CSS 靜態檔案採可識別版本的檔名或資源清單，避免舊 HTML 與新檔內容不相容。
- PWA Service Worker 可能快取舊版 UI；不得強制 `skipWaiting` / 自動 reload 導致尚未送出的作業遺失。
- 已填未提交的表單應保留至操作完成，之後才提供更新提示；更複雜離線狀況仍不代表已支援離線庫存交易。
- 若採 Blazor Interactive Server，須另外設計 UI circuit/session 中斷、連線重建與狀態恢復；最好降低對長連線互動的依賴。

### 6.1 PWA 實作（M5-02，2026-10-22，ADR-0016）
- `/sw.js` 由伺服器輸出（`src/Warehouse.Web/ServiceWorkerEndpoint.cs`），內容含版本號（`AppVersion`）、`Cache-Control: no-cache`：每次 A/B 切換到不同 commit，瀏覽器下次開頁就會發現新版。
- **快取範圍**：只快取帶版本參數 `?v=` 的 `/css`、`/js`、`/lib`（`asp-append-version` 產生，內容變網址就變）、`/icons`、離線頁。頁面、`/api`、`/files`、非 GET、沒有版本參數的檔案（按需載入的 `camera-scan.js`、`jsQR.js`）一律走網路。所以「新版頁面配到舊版程式」不會發生，舊 SW 等待期間也一樣。
- **更新時機**：新 SW 安裝後停在等待，不自動接手；`pwa.js` 顯示「有新版本，完成目前作業後按這裡更新」。按下才接手並重新載入。掃碼面板送出中不能更新；面板還有未加入的資料時第一次按只提醒。
- **相容**：頁面與 API 不經快取，舊頁面在相容窗口內照常呼叫新 API（§4 的規則不變）；只有離線頁、圖示、帶版本的靜態檔可能是舊版，與 HTML 一一對應不會錯配。
- **版本號必須帶 commit**：快取名與 sw.js 內容都依 `InformationalVersion`（例 `0.1.0+8fae975…`）。在沒有 `.git` 的目錄發布會變成固定的 `0.1.0`，瀏覽器就不會更新 SW（已列 `docs/09` 待辦：發布腳本檢查版本含 `+`）。
- **憑證**：Service Worker 只能在受信任的 HTTPS（或 localhost）註冊；憑證不受信任時註冊失敗，系統照常可用，只是不能安裝到主畫面。

## 7. 回滾流程與限制
1. 確認 B 出錯，判斷是否仍可安全使用 A（API／schema／資料格式相容）。
2. 反向代理將新請求切回 A（必要時先重新啟動 A 並做 readiness 測試）。
3. 保留 B 的日誌與錯誤版本，確認庫存交易筆數、冪等鍵和結存沒有遺失或重複。
4. 若已執行不可逆 migration 或新資料格式，不可盲目覆蓋 DB／回滾：應啟動事先核准的資料修復／維護計畫。
5. 記錄原因、修復者、時間、相關 Git commit、資料庫版本及後續預防措施。

### 7.1 PWA 的回滾與緊急停用（M5-02）
- 回滾到 **M5-02 以後**的版本：照一般流程切換即可；sw.js 內容（版本）改變，使用者按更新後換成該版。
- 回滾到 **M5-02 以前**的版本（沒有 `/sw.js`）：瀏覽器取不到 sw.js 時**不會**自動取消註冊。必須先在現行版本設定 `Pwa__Disabled=true`（環境變數或 appsettings），重新啟動該槽位，並保持至少 24 小時（D-23）或確認所有手機、PDA 都開過頁面；此時 `/sw.js` 改輸出「自我註銷」版（立即接手、刪除 `wh-static-*` 快取、取消註冊，不攔截請求、不重新載入畫面），之後再切到舊版。
- Service Worker 有錯需要緊急移除：同上設定 `Pwa__Disabled=true`。不會打斷正在作業的畫面（不重新載入），下次開頁就不再經過 SW。
- 個別裝置卡住、或停用期間沒有開過頁面的裝置：瀏覽器設定 → 網站設定 → 清除該網站資料（會一併登出）。

### 7.2 M6 的相容限制（2026-10-23，ADR-0017、0018、0019）
- M6 的 Migration（`M6_01_ViewerRole`、`M6_02_UserWarehouses`、`M6_04_Stocktakes`、`M6_05_ImportBatches`）都只新增，舊版可帶著新結構運作。但有兩個「資料」相容限制：
  1. **倉庫範圍**：舊版不讀 `user_warehouses`，A/B 共存或回滾到 M6 以前時，受限帳號在舊版槽位不受限制。→ 新請求全部切到新版、舊版停掉之後，才開始設定倉庫範圍。
  2. **盤點調整單**：舊版不認得 `Adjustment` 類型，讀到調整單的頁面（單據列表、異動歷史、久未處理）會出錯。→ 舊版停掉之前不要核准盤點；回滾到 M6 以前時，若已有調整單，舊版的這些頁面不可用（資料本身不受影響）。
- 回滾**不要**跑 M6 Migration 的 Down：`M6_04` 的 Down 會刪除盤點三張表與 `is_decrease`（盤點歷史消失、盤虧數量的正負號遺失）；類型檢查在 Down 時以 `NOT VALID` 加回，已有的調整單保留。
- 匯入確認是數秒到數十秒的交易，切換排空時被中斷會整批回滾（不會匯入一半），使用者重按「確認匯入」即可（批次冪等）。
- 開發機目前：`warehouse_dev` 已套用到 `M6_05`，伺服器仍是 A 槽位 `8fae975`（M4 版本）；為避免限制 2，`warehouse_dev` 沒有建立盤點資料。

### 7.3 M8-06 的相容（2026-10-26，ADR-0024）
- `M8_06_UserPreferences` 只新增 `user_preferences` 表，舊版不讀它，A/B 共存與回滾都不受影響。回滾**不要**跑 Down，Down 會刪掉所有人的常用設定。
- 共存期間，舊版頁面仍只用 localStorage；新版第一次載入時會把 localStorage 的值上傳一次，所以設定不會遺失。
- 「記住我」Cookie 用的是共用的 Data Protection 金鑰，舊版也解得開，只是舊版的登入頁沒有勾選框。回滾後，已持久登入的人不受影響，到期後才需要重新登入。

## 8. 必須測試的案例
- 新版本 ready 失敗 → 流量仍停留 A。
- 新版本接流量後錯誤率升高 → A 可以恢復新請求。
- 兩人在切換前後同時對一筆物料出庫 → 不超量、不重複。
- API 提交成功但用戶端逾時重試 → 同 Key 不重複過帳。
- 使用者尚在編輯表單與 PDA 連續掃碼 → 不強迫重新整理或清除內容。
- PWA 保有舊版快取 → 仍能在相容期呼叫後端或提供安全升級提示。
- 單機 App A/B 同時運行的 CPU/RAM 在指定 NAS/PC 允許範圍。

## 9. 決策前必須提供
- Windows 與 NAS 的具體代理選型及配置範例。
- 伺服器實測可用 RAM/CPU、A/B 運行統計、資料庫與儲存配置。
- 執行更新及回滾的 PowerShell/腳本與明確人工操作步驟。
- 完整整合／負載／失敗注入測試證據，涵蓋庫存資料一致性。
- 發布窗口、舊 Web/API 相容期限、異常通知方式及 RPO/RTO。

### M0-12 已知限制（審查後記錄）
- **首次升級到 M0-12 的版本**：舊版沒有共用金鑰與固定 ApplicationName，切換前開啟的表單送出會被拒（400）一次，需重新整理；之後的 A/B 切換不再發生。正式上線前已是 M0-12 以後的版本，影響僅限開發機。
- **排空上限**：切換後等待 10 秒（`-DrainSeconds`）再停止舊槽位，停止時主程式再等最多 30 秒；超過約 40 秒的請求會被中斷。M4 有寫入交易後需以冪等鍵驗證（`docs/09` 待辦）。
- **upstream.json 不可手動編輯**：一律用 `switch-release` 腳本改寫。M7-10 起內容無效時代理保留上一份有效目的地（不再 503），但代理重新啟動時無效會啟動失敗。
- ✅ M7-10（2026-10-23）已強化：以 `X-Warehouse-Slot` 確認槽位、同時只能一個切換、`deploy-state.json` 讓 `-Rollback` 只回到曾成功上線的版本、置換遇檔案鎖重試。升級代理本身（`uninstall-service`＋`install-proxy`）期間約數秒無法連線，不在不中斷範圍。

### 資料庫 Migration 的回滾（M1-01 起）
- 目前的 Migration 都只新增表、約束、trigger（Expand），舊版程式不讀取，所以**回滾＝把流量切回舊版，資料庫維持新結構**。
- `dotnet ef database update <舊版>` 會執行 `Down`，**只可用於開發／測試庫**：
  - `M1_01` 的 Down 會刪除全部物料資料。
  - `M1_02` 的 Down 會刪除審核紀錄與料號計數器。
  - `M1_03` 的 Down 會刪除全部帳號。
- 正式環境回滾一律保留資料表，只切回舊版程式。M1-01～M1-03 都是 Expand，舊版可以在新結構上執行。
- **M4-02 例外（2026-10-22 審查 #3）**：結構仍是 Expand，但舊版程式的 `StockDocumentType` 只有 `Opening`。資料庫一旦有進出倉單（`Inbound`／`Outbound`／`Transfer`），舊版讀到這些單據的異動（例如 `/Stock` 的最近異動）會出錯（500）。因此「M4-02 以後」不可回滾到 M4-01 以前的版本，A/B 切換期間舊版也不可是 M4-01 以前的版本。正式環境首次上線就包含 M4-02，實務上不會遇到；開發機目前的 A 槽位是舊版，只要沒有進出倉單資料就不受影響。之後新增列舉值時，要先出一版「讀到不認得的值也不會出錯」的程式，再加資料。
- **M4-04 相容窗口**：舊版不認得 `stock_reservations.expires_at`，並行期間舊版仍把過期預留算進預留（偏保守），也允許沖銷已過期的手動預留（新版會拒絕）；只影響切換的幾分鐘。
- **M4-04／M4-05 的索引不是 `CONCURRENTLY` 建立**（`ix_stock_movements_occurred_at`、`ix_stock_balances_negative`、`ix_stock_documents_status_created_at`、`ix_audit_logs_document_events`）：建索引期間會擋住該表寫入。V1 上線前資料量小可接受；正式庫已有大量異動時，這兩個 Migration 要排維護窗口，或改用 `CREATE INDEX CONCURRENTLY`（`suppressTransaction: true`）手動執行。
- 經代理時，網頁轉址必須用相對路徑。YARP 預設不轉送原本的 Host，槽位看到的主機是 `127.0.0.1:5080`，絕對網址會讓外部裝置連不到（M1-03 審查 R1；登入轉址已改為相對路徑）。
- 搜尋限流（M2）的計數存在各槽位的記憶體；切換期間 A、B 各自計數，同一位使用者的上限暫時最多變成兩倍。這可以接受；若要精確，需要共用儲存（例如資料庫），目前不做。
- `CREATE INDEX` 沒有加 `CONCURRENTLY`，建索引期間會擋住該表的寫入。目前資料量小，可以接受；資料量大之後的索引 Migration 要改用手寫 `CREATE INDEX CONCURRENTLY`（不能放在交易內）。
- 正式資料庫 Migration 以 `migrations script --idempotent` 產生 SQL，經使用者審核、完成備份後另行執行，不在程式啟動時套用。
