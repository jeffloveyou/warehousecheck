# NFR 技術實作規格｜低負載與 Windows PC／Linux NAS 部署 v0.2

> 狀態：規劃文件，尚未進行 PoC。所有數字與硬體能力需 M0 實測後調整；不代表已通過。

## 1. 設計目標與適用範圍
- **使用者端**：舊規格 Windows PC 透過 Edge／Chrome 操作；手機 iOS/Android 及 Android 工業 PDA 可共用查詢與交易。
- **伺服器端**：Windows PC 與符合執行條件的 Linux NAS 二擇一或分離部署。應用核心程式碼須相同，但服務安裝、路徑與發行產物可不同。
- **操作完整性**：效能最佳化不得減少交易授權、庫存一致性或稽核紀錄。

## 2. 前端技術選擇：M0 的性能比較
| 選項 | 預期客戶端負擔 | 需要驗證的風險 |
|---|---|---|
| Razor Pages + 少量 JS | 通常較小，不下載 .NET WASM | 動態介面實作／畫面刷新成本 |
| Blazor 靜態 SSR + 局部 JS | 通常較小，保有 Razor 元件 | 互動型流程要額外處理 JS／API |
| Blazor WebAssembly | 下載 WebAssembly 及應用組件，舊 PC 可能較重 | 初次載入、記憶體、低階 CPU／掃碼相容性 |
| Blazor Interactive Server | 瀏覽器可較輕，但持續連線 | Server 記憶體、長連線、更新時連線重建與狀態恢復 |

**初步傾向** Razor Pages 或靜態 SSR + 精簡 JS，但不在 M0 實測前定案。PWA 是網頁能力與安裝形式，不要求一定採用 WASM。手機相機掃碼需 HTTPS（安全內容環境）與授權；PDA/USB HID 可用鍵盤輸入流程。

## 3. 實作原則
- 搜尋、篩選、排序、歷史查詢使用後端分頁；API 控制最大 page size，不允許任意無限制匯出同步加載至 UI。
- 搜尋框 debounce／按 Enter 送出，避免每個按鍵觸發昂貴 DB 查詢；精確料號與索引有適合的 SQL 索引。
- 唯讀查詢評估 EF Core DTO 投影及 `AsNoTracking()`；識別及改善 N+1 和過多 JOIN。
- HTML/CSS/JS 精簡，避免高頻動畫與不必要的 polling；手機相機程式延遲載入、不用時釋放攝影機。
- 圖片使用縮圖、格式優化、延遲載入；靜態資源使用快取與版本標記，避免使用者每次重複下載。
- 查詢快取需有失效策略；庫存可用量最終決定必須以 DB 交易為準。
- 每個主要作業畫面應有低規格硬體的實測紀錄，而不是僅開發機測試。

## 4. 擬議的測試基線（非承諾）
| 項目 | 建議先以此測量，M0 可調整 |
|---|---|
| 舊電腦 | Windows 10、雙核心 CPU、4 GB RAM、Edge（ADR-0005）；另需長期支援 Windows 7＋Chrome 109／Edge 109（ADR-0006）。M0 以實機確認 |
| 資料量 | 20,000 種物料起測，包含高重複／多索引搜尋條件（ADR-0005） |
| 併發 | 30 名模擬操作員起步，再依實際需求調整（ADR-0005） |
| 使用者首屏 | 預期可用畫面約 3 秒內；須記錄網路條件 |
| 搜尋 API | p95 約 1 秒內；實際畫面總延遲分開量測 |
| 穩定性 | 閒置無不必要 CPU 消耗，長時間使用無持續記憶體累積 |

測試記錄欄位：硬體與 OS、瀏覽器版本、網路品質、同時使用者數、物料資料量、總傳輸量、CPU、RAM、p50/p95 延遲、成功率、查詢計畫、測試人及日期。

> **資料庫版本**：PostgreSQL 必須 ≥ 15（結存唯一索引使用 `NULLS NOT DISTINCT`，M3-03）。開發機是 17.11。

### 4.1 M2-05 搜尋量測（開發機，2026-10-22）
**環境**：
- 開發機：AMD Ryzen 9 8940HX、15.2 GB RAM、Windows 11、PostgreSQL 17.11（本機）。
- 單一使用者，沒有其他負載。
- **這不是目標舊電腦或 NAS 的數據**。

**資料量**（`warehouse_test`）：
- 有效物料 20,000 筆，名稱含 8 種常見詞，每種約 2,500 筆。
- 專屬別名 20,000 筆。
- 共用關鍵字 42,000 筆：每物料 2 筆，另有 1 個關鍵字被 2,000 個物料共用。

**工具與方法**：
- 量測工具：scratchpad `searchbench`。
- 量測內容：呼叫 `ItemSearchService.SearchAsync`。
  - 先暖機 1 次，再量 5 次取中位數。
  - 用相同參數對「計數」「分頁」兩句 SQL 各跑一次 `EXPLAIN (ANALYZE, BUFFERS)`。

| 情境 | 筆數 | 服務耗時中位數 | 計數 SQL | 分頁 SQL |
|---|---|---|---|---|
| 精確料號 | 1 | 42 ms | 17 ms | 16 ms |
| 精確別名 | 1 | 38 ms | 18 ms | 16 ms |
| 共用關鍵字（2,000 筆命中） | 2,000 | 42 ms | 16 ms | 20 ms |
| 同上，第 50 頁 | 2,000 | 47 ms | 19 ms | 25 ms |
| 單一中文字「閥」 | 2,500 | 40 ms | 15 ms | 17 ms |
| 兩個詞「伺服 三菱」 | 2,500 | 40 ms | 17 ms | 18 ms |
| 五個詞 | 2,500 | 62 ms | 25 ms | 26 ms |
| 完全不命中 | 0 | 46 ms | 13 ms | 18 ms |

**執行計畫結論**：
- 別名、關鍵字的精確比對都是 `hashed SubPlan`：用 `normalized_text` 索引查一次，不是逐列執行。
- 只要查詢裡有可做部分比對的詞，`items` 就是全表掃描（`LIKE '%詞%'` 本來就用不到 B-tree 索引），耗時大約與物料數成正比。

**推估與門檻**（待實機確認）：
- 舊電腦或 NAS 若慢 3～5 倍，2 萬筆物料大約是 0.1～0.3 秒，在 §4「p95 約 1 秒」以內。
- 物料到 10 萬筆時，可能接近 1 秒。屆時改用 pg_trgm GIN 索引（`docs/09` 待辦），並以這張表為比較基準。

## 5. Windows PC 部署候選
- .NET ASP.NET Core：Framework-dependent（目標機安裝合適 Runtime）或 Self-contained（隨部署提供 Runtime）。
- Web/API 可使用 Windows Service 或合適服務管理方式；固定網址的反向代理與 HTTPS 規劃需確認。
- PostgreSQL 可同機或另機；應評估磁碟可靠性、備份空間、權限與異機備份。
- App A/B 使用分開發布目錄、埠與服務識別，不可覆寫運行目錄；資料庫／上傳附件與 App 版本目錄分離。
- **M0-10 實測（ADR-0008）**：Windows 服務＋虛擬服務帳號、`C:Warehouse{releases,config,certs,data,logs}`、`WAREHOUSE_CONFIG_DIR` 外部設定；framework-dependent 7.7 MB／37 檔、self-contained 112.9 MB／367 檔；重啟 1.2 秒恢復就緒、服務記憶體約 94 MB。預設採 framework-dependent。
- **M0-12 實測（ADR-0010）**：A/B＋YARP 代理三個程序同時運行（開發機）：A 工作集 116 MB（私有 50 MB）、B 92 MB（39 MB）、代理 86 MB（42 MB）；平時只有「目前槽位＋代理」運行，待命槽位只在更新期間啟動。代理發布檔 0.7 MB／14 檔。舊電腦／NAS 上的量測留待 M0-13。
- **M0-13 實測（2026-10-22）**：正式伺服器就是開發機（使用者決定），NAS 不在這次範圍。
  - 環境：Ryzen 9 8940HX、32 執行緒、15.2 GB、Windows 11、PostgreSQL 17.11 同機，資料庫 `warehouse_bench`，版本 `0.1.0+9590be2`。
  - 負載：FieldBench `load`，30 名虛擬使用者，每人一個帳號，每步思考約 2 秒，操作比例為搜尋 50%、明細 30%、庫存 10%、期初 10%。CPU 與記憶體由 `sample-server.ps1` 每秒取樣。

| 狀態 | 請求數（每秒） | 失敗 | 延遲 p50／p95／最大 | 記憶體（Private Bytes） | CPU（整機） |
|---|---|---|---|---|---|
| 只有一個槽位（A＋代理），120 秒 | 1,757（14.6） | 0 | 24／53／306 ms；搜尋 p95 55 ms | A 平均 92、尖峰 120 MB；代理 47 MB；PostgreSQL 尖峰約 210 MB | 主程式平均 0.3%、尖峰 6.7%；整機尖峰 48%（含負載產生器） |
| 負載中部署並切換 A→B，200 秒 | 2,951（14.8） | **0** | 18／51／360 ms；最大值出現在新槽位剛啟動的那一秒 | A、B 同時運行約 10 秒：A 99＋B 122 MB | 整機尖峰 33% |

  - 合計：A＋B＋代理＋PostgreSQL 約 0.5 GB。
  - **主要風險是這台電腦本身的空閒記憶體**：量測期間其他程式占用，整機可用只剩 0.3～2.2 GB。
  - 限制：負載產生器在同一台電腦上，CPU 數據偏保守；30 人用的是固定的操作比例，實際操作模式要上線後觀察。

## 6. Linux NAS 部署候選
- 核對 NAS 品牌、型號、CPU 架構（x86-64 或 ARM64）、Linux OS、RAM、磁碟空間、可否安裝相容容器平台及權限限制。
- NAS 若支援 Docker/OCI 類型容器，可採兩個 App 容器與代理服務；若不支援，不應假設可照搬 Windows 部署。
- 容器執行需要正確的 CPU 架構與 image；若 DB 容器化，資料必須以持久磁碟掛載，且驗證備份與還原。
- NAS 可能 CPU/記憶體不足以同時跑 App A/B + PostgreSQL；如實際不符，建議 App 放 PC、NAS 用於備份／附件，或另行確定可接受維護窗口。
- NAS 型號尚未決定前，Linux x64 PoC 僅能證明程式具備 Linux 相容性，不代表任一 NAS 已驗收。
- **M0-11 實測（ADR-0009，WSL2 Ubuntu 24.04，非 NAS）**：Linux 上 build／14 個測試通過；systemd 服務 ready 200、重啟 0.7 秒恢復、cgroup 記憶體約 47 MB；Docker x64 映像下載 98.7 MB／解壓 351 MB、約 50 MiB、重啟 1.3 秒；arm64 以 QEMU 模擬可啟動（10.9 秒、約 210 MiB，模擬數據不代表實機）。原生服務記憶體最少，NAS 可裝 .NET Runtime 時優先採用。

## 7. 發布及組態管理
- 預定 `scripts/publish.ps1` 支援 `RuntimeIdentifier`（`win-x64`、`linux-x64`、視需求 `linux-arm64`）及 `SelfContained` 開關。
- 兩種部署型式須分別測試：Framework-dependent 依賴目標 .NET Runtime；Self-contained 視架構與平台產生專屬執行產物。
- 正式資源與機密應使用受控環境設定，不得提交 Git；產物一律放在不受 Git 追蹤的 publish 目錄。
- URL、反向代理、憑證、備份位置、App 版本資訊、監控與更新方式都需記錄。
- **附件目錄（M3-08）**：倉位圖片存在 `Storage:AttachmentsDirectory`（Windows `C:\Warehouse\data\attachments`、Linux `/var/lib/warehouse/data/attachments`、容器 `/data/attachments` 需掛 volume），與發布目錄分開、A/B 共用，**和資料庫一起備份**；只還原資料庫不還原這個目錄會出現破圖。每張圖只存大圖（約數百 KB 以內）與縮圖（數 KB），原檔不保存。
- **SkiaSharp 原生函式庫（M3-08）**：發布輸出含 `libSkiaSharp`（約 12 MB）；Windows 的 90 MB 除錯符號已排除。實測 framework-dependent：win-x64 22.2 MB、linux-x64 21.4 MB、linux-arm64 21.3 MB。ARM64 NAS 需實機確認縮圖可執行。
