- 日期：2026-10-28。
- 使用者需求：「很多地方需要掃碼，但沒看到相機按鈕」、「也要能讀一維條碼，自動辨識」。

- 執行依據：根目錄 `AGENTS.md`。使用者將本計畫交付實作時，確認授權範圍包含新增解碼套件；本文件本身不代表套件、正式部署或其他未授權操作已獲核准。

## 1. 目標與界線

1. 作業頁可以直接開相機掃碼，不必先離開頁面到「掃碼查料」。
2. 同一入口自動辨識 QR 與常用一維碼，使用者不用選碼制。
3. 掃描結果有明確目標欄位，沿用後端精確解析、權限與數量規則。
4. 不可用時看得到原因，不再無聲隱藏按鈕。
5. 不改庫存過帳、冪等、預留、權限或外箱換算規則；預期不需 Migration。
6. 不包含 OCR、GS1 AI 語意拆解、離線交易、批量掃描畫面內所有條碼、正式環境部署。

「自動辨識」分為影像解碼取得文字與碼制，再由後端解析業務意義。讀出條碼不代表物料已登錄；未知碼必須提示，不得猜測或自動建立物料。

| 物料明細新增索引／原廠條碼 | 無相機入口 |

`scan-input.js` 目前只在 `window.isSecureContext` 且有 `getUserMedia` 時顯示按鈕。`camera-scan.js` 優先採原生 BarcodeDetector，否則 jsQR，只讀 QR；不能將「能開相機」視為「能讀一維碼」。

文件有開發相機頁測試紀錄，正式手機作業流程仍有待驗證項目。本計畫沒有實測使用者目前瀏覽器、網址或相機。

## 3. 解碼方案與套件查證

建議：保留原生 BarcodeDetector，新增固定版本 `zxing-wasm/reader`，作為跨裝置多碼制解碼器。

| 方案 | 判斷 |
|---|---|
| 原生＋jsQR | 無法滿足缺乏原生能力裝置的一維碼需求 |
| ZXing JS | 可多碼制，但官方列為 maintenance mode，不作優先方案 |
| 原生＋ZXing WASM reader | 優先驗證；可統一備援一維／QR，須實測 Chrome 109、手機相容性及負載 |

已查閱官方來源：

- 功能、reader 與授權：https://github.com/Sec-ant/zxing-wasm 。上游文件標示 reader WASM 約 1.04 MiB，這不是本專案壓縮傳輸量或實測結果。
- 授權：https://github.com/Sec-ant/zxing-wasm#licenses 。封裝 MIT、ZXing-C++／介接程式 Apache-2.0，專案另列 Zint BSD-3-Clause；必須依實際固定版本與發行檔逐一核對授權、依賴、NOTICE。
- ZXing JS 維護狀態：https://github.com/zxing-js/library#project-in-maintenance-mode-only 。

實作第一階段先確認確切版本、來源、發布／維護狀態、瀏覽器需求、漏洞公告及檔案雜湊。保留授權檔，使用本機靜態資源，不以 CDN 或 `latest` 作執行期依賴。若指定版本不能在 Chrome 109 使用，記錄證據並提出替代版本／方案，不得降低相容基準或默默換套件。

此 WASM 僅供瀏覽器影像解碼，不引入 Blazor WASM 或大型前端框架。

## 4. 操作與資料流

### 4.1 共用相機

- 固定可見的「相機掃碼」入口；HTTPS／API 不支援時停用並顯示原因。JS 未啟用時保留手動輸入與可理解的提示。
- 按下才下載解碼器、開啟相機；優先後鏡頭。影像留在裝置內，不上傳。
- 依能力與測試決定原生／WASM 路徑，支援格式不完整或原生初始化／解碼失敗時可切換備援。不得每一影格同時重跑所有解碼器。
- 掃描時顯示目標，例如「掃入：目的儲位」。避免只依最後焦點猜測。
- 同頁只能有一個相機工作階段；切換目標需明確更新，不能把延遲結果寫到其他欄位。
- 單欄成功一次即停止；查料與明細保留連續模式及既有去重行為。
- 停止、關閉、切背景、離頁時釋放 track；涵蓋尚在申請權限／初始化期間關閉的競態，避免稍後相機又啟動。
- 多碼入鏡時要求對準單一碼或提供明確選擇，不任意取第一筆作庫存操作。
- 拒絕權限、無鏡頭、相機占用、解碼器載入失敗有可理解提示；可重試或手動輸入。

### 4.2 辨識與欄位規則

- 第一批驗收碼制：QR Code、EAN-13、EAN-8、UPC-A、UPC-E、Code 128、Code 39、Code 93、ITF、Codabar。
- 回傳文字與統一碼制識別；維持字串，保留前導零，不以數值轉換。
- 測試 UPC-A／EAN-13 前導零等解碼器差異；以不破壞既有條碼唯一性的方式處理。需要變更識別規則或儲存資料時先提出方案，不得直接修改既有條碼。
- 物料／儲位欄：交給現有 parser／resolver；錯誤類型不可填入。儲位 QR 必須檢查倉庫，移庫目的倉依現有跨倉規則。
- 批號／序號欄：明確指定後才可填原文，沿用長度、追蹤模式驗證，不當成物料解析。
- 新增條碼欄：填原始條碼，不先查成料號，不自動送出整張表單；保留既有英數字、唯一性、核准與包裝量驗證。
- 外箱碼：明細面板依既有規則換算；預留等基本單位欄依既有規則拒絕外箱碼，不偷偷換算。
- 掃描成功只填值／解析；盤點數量由人確認，不新增自動提交交易。既有明細「手動／自動／逐件累加」模式依原規則。

### 4.3 接入矩陣

| 作業 | 接入方式 |
|---|---|
| 查料 | 連續掃描 → 現有查料流程 |
| 進／出／移庫、期初面板 | 共用連掃＋可明確指定物料、來源／目的儲位、批號／序號 |
| 盤點 | 儲位、物料、適用批號／序號各有入口；單次填值，不自動記錄實盤 |
| 預留、期初查建議儲位 | 單次物料解析；與鍵盤路徑共用驗證 |
| 物料提出／修改 | 每列原廠條碼可掃；新增列、刪列後目標仍正確 |
| 物料明細原廠條碼登錄 | Barcode 類型時提供原始條碼填值，避免誤寫其他索引類型 |
| 未登錄條碼的所屬物料 | 掃物料 QR／允許的單件識別碼 → 正式料號；查料相機不可覆蓋登錄表單 |
| 搜尋 | 解析物料碼後以正式料號搜尋；不支援的碼明確提示 |
| 庫存查詢 | 物料碼填料號；儲位 QR 帶倉庫與儲位，避免沿用錯倉庫；保留其他查詢條件 |

## 6. 分階段實作與停止條件

1. **工作區核對**：檢查 `git status`／diff 與適用規範，保留使用者及其他 Agent 的未提交變更。交接時發現新增變更，先辨識再編輯，不 reset、覆蓋或混入提交。
2. **解碼可行性**：固定版本、授權、Chrome 109／手機能力與測試圖驗證。未達相容基準就記錄證據並處理方案，不大量接頁後才發現不可用。
3. **共用元件**：完成單次／連續模式、明確目標與錯誤提示，先接查料與既有面板。
4. **欄位補齊**：依接入矩陣完成盤點、預留、條碼登錄、搜尋與庫存查詢；逐組驗證。
5. **回歸與審查**：主對話執行指令，必要子角色只撰寫／審查不執行；涉及盤點等寫入流程、權限或安全的差異由 `warehouse-reviewer` 審查並處理。
6. **交付**：記錄實際通過／失敗／待驗證項目，供使用者驗證，再依專案規範完成文件同步。正式部署另依使用者授權。

## 7. 驗收與證據

| 類別 | 必驗案例 |
|---|---|
| 碼制 | 每種承諾碼制測試圖與預期文字；前導零、旋轉、QR 與一維切換；原生／WASM 各路徑 |
| 誤判 | 未登錄碼、錯誤類型、不同倉庫儲位、模糊／損壞碼、多碼入鏡不得誤加明細 |
| 目標 | 欄位切換、動態條碼列、背景請求晚到、查料結果重繪後仍填正確欄位 |
| 數量 | 外箱規則、序號模式、既有逐件累加、同碼持續停留不重複計數、移開再掃可計數 |
| 相機 | 允許／拒絕權限、無相機、占用、停止、背景、離頁、初始化中關閉與重試 |
| 既有設備 | Enter／Tab、手動輸入、條碼槍佇列、焦點與不誤提交表單 |
| 相容 | Chrome 109 實跑；iPhone Safari、Android Chrome 實機。模擬影像不代表實體鏡頭已通過 |
| 效能 | 記錄 OS／瀏覽器／CPU／RAM／網路／資料量、初次下載實際壓縮量、啟動／解碼耗時與資源；不重疊解碼、不常駐空跑 |
| 載入 | 未按相機時不請求 camera decoder／WASM；靜態資源同源且固定版本，無 CDN 執行期依賴 |
| 更新 | 舊頁面仍可載入對應資源、保留未送出輸入，回滾後基本查料／條碼槍可用 |

PowerShell 指令由接手主對話依實際工具參數執行並記錄，以下只是預定入口，尚未執行：

