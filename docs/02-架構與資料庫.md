# 架構、資料庫與交易規則 v0.2

## 分層與依賴
```text
Lightweight Web UI ──HTTPS/JSON──> Api ──> Application ──> Domain
                                   │
                                   └──> Infrastructure ──> PostgreSQL
```
Domain 不依賴 UI、資料庫或 HTTP；Application 定義用例和介面；Infrastructure 實作 EF Core 與資料存取；Api 負責 transport、身份驗證與授權；Web 僅存放互動與顯示。架構需透過專案參考驗證依賴方向。

## 重要一致性設計
- ItemCode 為唯一企業料號，ItemId 永久不變。已有交易的物料只能停用、不任意刪除。
- Alias 的 NormalizedText 在有效專屬別名集合中唯一，Keyword 的 `(ItemId, NormalizedText)` 在有效集合中唯一；跨物料共用關鍵字不禁止。
- ItemCode、條碼及專屬別名的精確識別衝突要在設計時統一策略；建議用獨立 `ExactIdentifierRegistry`（NormalizedIdentifier, Namespace, ItemId）統一管理並由資料庫唯一約束保證，避免跨表檢查競態。識別類型有不同正規化規則，GTIN/料號要保留必要字元與前導零。
- StockBalance 的維度：ItemId + LocationId + LotId + SerialId + StockStatus；NULL 唯一語意需以資料庫適當約束處理。
- 若 ItemSerials 表示實際在庫實體，必須保證同一序號不得同時在兩個庫位為在庫；同料號跨倉與追溯關係清楚。
- 物料數量採 decimal，依單位限制小數位；`KG`、`M` 可小數，`PCS` 常需整數。
- 不允許在 Web 或 Api 層直接操作 StockBalances；由 Application 的單一 `InventoryPostingService` 處理。
- 禁止負可用庫存為預設，必要例外需專案獨立 ADR 批准。

## 入庫交易範例（概念流程）
1. 驗證登入與入庫權限；檢查資料格式、單位、批號／序號、儲位可用性。
2. 檢查冪等鍵，避免重送造成雙入庫。
3. 開啟 DB 交易：建立正式單據／明細，鎖定或原子更新目標庫存結存，建立正向 Movement，寫入處理結果鍵。
4. Commit 後才回成功。若失敗 Rollback；回傳可理解錯誤碼。

## 出庫交易範例
1. 伺服器核對可用量（庫存狀態＋已預留量）與序號限制。
2. 在同一 DB 交易用條件式更新／列鎖，保證多人並行不超賣；更新結存、寫負向 Movement、單據狀態、冪等結果。
3. 交易提交後回傳新結存。相同鍵和相同請求回前次結果；相同鍵但不同 payload 拒絕。

## 移庫交易範例
單據明細指向來源與目的庫位。在**同一交易**寫來源負向 Movement、目的正向 Movement；數量守恆。跨倉轉移若需在途狀態，V2 採雙階段流程，不以單次即時移庫假裝已運達。

## 基本 API 草案（需統一 DTO 與錯誤格式）
```text
GET    /api/items?query=伺服AMP
POST   /api/items                # 權限確認後建立正式物料
GET    /api/items/{id}
POST   /api/items/{id}/aliases
POST   /api/items/{id}/keywords
GET    /api/locations/{id}/stock
POST   /api/stock/opening
POST   /api/stock/receipts
POST   /api/stock/issues
POST   /api/stock/transfers
POST   /api/stocktakes
POST   /api/stocktakes/{id}/approve
```
POST 庫存提交需 `Idempotency-Key`，並由 API 實施授權。輸入驗證與伺服器側權限不可只放在前端。

## 身分驗證、例外與操作日誌
使用 ASP.NET Core 標準身份系統與角色／政策授權，正式決定 Cookie 或其他方案前應建立登入與 API PoC；避免把敏感 token 存在不安全的瀏覽器空間。日誌不洩露連線密碼、帳密或個資。使用結構化錯誤碼與 RequestId，讓開發手冊能教使用者追查故障。


## 低負載設計
- 前端採用「伺服器渲染或低負載方案優先」的原則，須先經 M0 比較測試，不預設 Blazor WebAssembly。
- 查詢需限制 page size；複雜篩選、排序在 DB 執行，減少前端記憶體占用與網路傳輸。
- API 回傳精簡 DTO，避免序列化整個 EF Entity graph；唯讀查詢可評估 `AsNoTracking()` 與投影（projection），防 N+1。
- 適當建立 ItemCode、識別碼與常用查詢維度的 DB 索引；所有效能改善須檢查執行計畫與實際資料分布。
- 資料庫快取及前端快取不可繞過庫存最終驗證。介面可顯示快取時應註明時間及重新取得機制。

## Windows PC 與 Linux NAS 部署架構
```text
          PC / 手機 / PDA（同一內網 HTTPS 網址）
                            |
                Reverse Proxy（HTTPS）
                            |
              API/Web A    API/Web B
                    \        /
                     PostgreSQL
                        +
                  附件與備份儲存
```
- 伺服器層盡量採跨平台 .NET。Windows PC 使用 Windows Service 等方式；Linux NAS 依相容性採容器或原生服務。
- 靜態資源、使用者附件、機密組態和 DB 資料應與程式發布版本分離。
- NAS 的 Linux CPU 架構、容器能力、可用記憶體、磁碟 I/O 與檔案權限須先驗證；PostgreSQL 未必適合與 App 同機，須依容量決定。
- 發布至 Windows / Linux 時需使用適用的 RID，且保留 Framework-dependent、Self-contained 選項。
- 每次部署維持同一資料庫 schema 與 API 契約，使用設定差異而不是分叉核心程式碼。

## 藍綠部署與資料庫相容
- 在 A 舊版接流量時，先獨立部署、啟動 B 新版，完成 readiness 檢查才切流量。
- 如有長連線、伺服器端 UI session 或背景工作，需額外設計排空／重連／作業重試，不能只以 HTTP 代理切換聲稱完全無感。
- 同一 schema 在相容窗口內須同時支援 A、B。破壞性資料表變更延至 A 停止且相容期結束後處理。
- 部署及 rollback 過程不允許直接清除資料；Migration 要人工批准、備份、獨立執行。
- 反向代理切換步驟、健康狀態定義、用戶端資源更新策略，見 `docs/11-線上更新與回滾.md`。
