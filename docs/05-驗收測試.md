## D. 測試層級與證據
- Domain 單元測試：數量、追蹤模式、庫存規則、物料編號與搜尋正規化。
- Application 測試：用例、授權、搜尋排序、錯誤代碼、冪等。
- API/DB 整合測試：使用真實 PostgreSQL 測試交易、Unique 約束、併發；只用 SQLite 記憶體模擬不足以驗證 PostgreSQL 行為。
- UI/E2E：標準作業路徑；相機/PDA 必須現場驗證。
- 驗收紀錄含：測試人、時間、軟硬體版本、步驟、預期與實際結果、關聯 commit。

## E. 上線門檻
- 所有高風險測試成功（庫存一致性、身分驗證、資料備份還原）。
- 代表性三種裝置完成實際入出庫。
- 至少一位非開發者依操作手冊完成盤點。
- 開發手冊能讓維護者依照步驟取得、建置、測試並追蹤 API 到資料庫；無須完成指定練習題。

| T-PERF-02 | 10,000 筆模擬物料的搜尋與伺服器端分頁 | API 延遲分位數、查詢計畫、資料量 |
| T-PERF-03 | 不一次傳送全部料號、異動清單或原尺寸圖片 | Network payload／前端記憶體證據 |
| T-PERF-04 | 閒置畫面及長時間使用無不合理 CPU 或 RAM 成長 | CPU／Memory 多時段量測 |
| T-PERF-05 | 鍵盤掃碼不載入相機解碼器、手機相機不用時釋放資源 | Network 載入紀錄／記憶體量測 |
| T-PERF-06 | 初期以 10 名模擬並行使用者測試，不犧牲庫存一致性 | 壓力測試與交易核對結果 |

**討論用起始目標（非已核准、非已驗收承諾）**：雙核心、4GB RAM 的舊電腦；初次頁面約 3 秒內；搜尋 API 的 p95 約 1 秒內；10,000 料號／10 名使用者。實際指標必須依設備、網路與資料分布由 M0 修改後批准，API 延遲與使用者畫面總時間需分開量測。

## H. 線上更新驗收
| ID | 驗收情境 |
|---|---|
| T-UPDATE-01 | A 正在服務時，可另行啟動 B 並獨立完成 readiness 檢查 |
| T-UPDATE-02 | B readiness 失敗，不得將新請求切給 B |
| T-UPDATE-03 | B readiness 成功後切換新請求，A 既有進行中請求可正常完成或有安全重試機制 |
| T-UPDATE-04 | 切換期間至少執行重試、同鍵重送、多人同時出庫，無遺失、重複過帳或負庫存 |
| T-UPDATE-05 | 尚未提交的網頁表單不被強制重新整理、清除；已開啟的 PWA 舊版可安全完成或提示更新 |
| T-UPDATE-06 | 相容期內 A/B 與同一 PostgreSQL schema 協作正確 |
| T-UPDATE-07 | B 發生故障，切回資料庫相容的 A，且記錄操作及異常 |
| T-UPDATE-08 | NAS／PC 的 CPU、RAM 足以執行兩個 App；若不行必須明載限制與替代方案 |
| T-UPDATE-09 | 更新時可查詢目前版本、部署日誌、健康檢查與錯誤紀錄 |

> T-UPDATE 為應用程式升版驗收，不是單一 NAS、PC、資料庫或網路設備故障的高可用性保證。
